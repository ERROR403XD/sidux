# 剩余系统审阅项开发成本评估

基于 0.2.19 / `d3a38ac` 的源码、[原始审阅](20260912-0006-codexapp-0.2系统代码审阅.md)、[账号与出口影响评估](20260912-0011-codexapp-修复对账号与出口调度的影响评估.md)及[0.2.19 验收](20260912-0014-codexapp-0.2.19稳定性收口与验收.md)，评估 SCH-03、SEC-01、MOD-01、PERF-01、DATA-01 的剩余工作。

本页是规划估算，不是报价、交付日期或实际耗时统计。人日按一名熟悉项目的开发者工作一天计，包含分析、实现、调试、相关回归及文档；不能直接换算成 AI 连续运行小时数。估算按维持现有账号、额度、出口和调度契约的要求给出，不以扩大锁范围、强杀共享会话、删防重记录或关闭现有功能来降低成本。

## 总体范围与工作量

| 项目 | 设计与实现 | 定向回归、兼容与迁移验证 | 合计 | 估算不确定性 |
| --- | --- | --- | --- | --- |
| SCH-03 账号准备全程截止与取消 | 2–4 人日 | 2–4 人日 | **4–8 人日** | 高：共享 worker 和底层不可取消操作决定上限 |
| SEC-01 主动预览隔离 | 1.5–3 人日 | 1.5–3 人日 | **3–6 人日** | 中高：相对资源、脚本兼容、浏览器与部署入口 |
| MOD-01 六个主要模块逐步拆分 | 9–15 人日 | 6–10 人日 | **15–25 人日** | 高：状态所有权和生命周期的隐性耦合 |
| PERF-01 已发现重复读取的局部治理 | 0.5–1 人日 | 0.5–1 人日 | **1–2 人日** | 中：部分第二次读取可能是必要同步 |
| DATA-01 历史、索引分段与保留策略 | 2–4 人日 | 2–4 人日 | **4–8 人日** | 中高：实际数据规模、兼容和防重保留语义 |

五项按上述范围合计 **27–49 人日**。另留 **3–5 人日**用于各批完成后的整体验收、包安装/回退演练和交叉功能问题，规划总预算 **30–54 人日**，相当于一人串行约 **6–11 个工作周**。这些范围不是统计置信区间；实现原型后需要重新估算，不能据此承诺所有未知问题均可在上界内解决。

不包含：0.3 项目工作台的新 UI、新产品功能、全面更换数据库、账号体系重写、任意规模历史搬迁、额外浏览器/部署平台认证，以及等待真实账号测试条件或用户验收的日历时间。全套 753 项测试是已有基础，不等于以下新增行为已有覆盖。

## SCH-03：账号准备超时为什么较贵

当前链路包括 `automationEngine.ts:341` 的 acquireAccount、`codexAppServerBridge.ts:5617` 的 acquireTaskAccount、凭据/额度刷新、sessionWorker 分配及 configureSession。`call()` 把 RPC 放进 pending 后等待回复，没有总期限。worker 池的分配还可能等待旧 worker 的空闲探测和退出；它是有串行分配链的共享资源池，不能只检查最外层 acquire。

源码明确同一会话在聊天与自动化之间复用一个进程；后台终端、待审批和 pending RPC 也参与是否可回收的判断。因此，“等了 30 秒就删掉任务并杀进程”不满足现有契约。

4–8 人日包括：

1. 列清准备各阶段、不可逆动作和资源所有者；区分共享只读请求、共享配置写入及本次独占资源。
2. 贯穿截止时间、取消标识、执行代次检查；保证取消或账号移除后，迟到成功不能再 start 或改身份。
3. 正确回收本次 lease、pending 和队列占位；不可确认结束的共享操作保持可观察状态，不能假装已释放，也不能无限堆叠重试。
4. 验证四个准备挂起、第五个排队、取消/移除/默认切换相撞、额度刷新失败、服务停止、迟到成功，以及其他账号和既有会话持续工作。

**可先做 0.5–1 人日的阶段诊断与取消原型**，属于完整估算的一部分，不算修复完成。如果原型证明底层副作用无法取消或隔离，必须重新评估 worker 归属设计；4–8 人日届时不再是可靠上限。不能承诺任何底层永久挂死都可以在不影响共享资源的同时自动恢复。

完成标准：正确结束或安全隔离超时准备；没有迟到发送、错账号、重复释放；资源确实回收后恢复准入，其他账号和会话不中断。只有提示“超时”或外层 Promise 返回不算完成。

## SEC-01：预览隔离的主要成本是兼容与写入边界

当前入口分散在 `httpServer.ts` 的 `/codex-local-file`、`/codex-local-browse`、`/codex-local-image`，以及会话文件链接、技能目录和下载/编辑操作。`localBrowseUi.ts` 生成的目录页包含项目操作，文本编辑器包含保存请求；这些可信应用页面不能与任意仓库 HTML 一起失去管理能力。

3–6 人日包含：

1. 区分可信目录/编辑页面与用户生成的主动文件内容，覆盖 HTML、SVG、直接链接和浏览路径。
2. 选择并验证隔离方案，保留正常 HTML 草案交互、相对 CSS/JS/图片、下载和编辑跳转；受控 sandbox 与独立预览来源均需原型比较，尚未指定某一种为最终方案。
3. 检查预览不能读取管理响应，也不能成功发起有副作用的管理操作；同时验证正常管理请求和 API HTTP/SSE/WS 的现有契约。
4. 覆盖密码/无密码、localhost/家庭网络/现有反代入口、浏览器直接打开、实际安装包和缓存刷新。

浏览器的同源策略通常阻止跨源读取，却不自动阻止所有写入，例如部分表单提交。因此“换端口后读不到 API”不足以证明修复；这是兼容与验证费用的一部分。[MDN 同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)

sandbox 的脚本、表单、下载和来源保留是不同开关；不保留原来源时会变成 opaque origin，不能假定原先的模块脚本、资源请求和存储行为都保持相同。[MDN CSP sandbox](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox)

**可先做 1–2 人日的兼容原型**，包含在总额内；仅禁用脚本、强制下载或加一条 header 的方案不作为本次完整修复估算。若要求所有任意网页的网络、存储、表单行为完全不变，同时绝对不能调用管理功能，则需要先划清权限，不能承诺透明无损隔离。

如果证明必须改动广泛管理认证、部署端口或代理配置才能成立，应回到方案评审重新界定成本，不把它偷偷合入账号调度修复。既有可信内网使用方式不作无依据的全面收紧。

## MOD-01：属于结构工程，不能按移动代码行数估价

本轮只读统计：234 个非测试 TS/Vue 文件，69,390 行；以下六文件合计 34,369 行，占 49.5%。统计不含 CSS，不代表逐行审计深度。

| 文件 | 当前行数 |
| --- | ---: |
| src/server/codexAppServerBridge.ts | 9,823 |
| src/App.vue | 6,261 |
| src/composables/useDesktopState.ts | 5,895 |
| src/components/content/ThreadConversation.vue | 5,194 |
| src/api/codexGateway.ts | 3,608 |
| src/components/sidebar/SidebarThreadTree.vue | 3,588 |

完整 15–25 人日的范围是把主要业务边界拆清并稳定旧入口，包括 bridge 的 RPC/通知/worker 生命周期，前端的账号、项目、会话、设置状态，侧栏业务表单和内容渲染/发送状态。保留 API、数据格式、单例、事件订阅与既有界面行为，不在同一阶段做工作台 UI 重构。

真正需要时间的是识别闭包依赖、重连与订阅清理、缓存失效、响应式引用、资源所有者和模块循环依赖；简单拆成更多文件可能只把耦合藏起来。每批需核对首次加载、进入/退出会话、反复打开面板、断线恢复、多个视图共享状态、账号切换及资源释放，检查重复请求、定时器和监听器。

**首批可限定为 3–5 人日**：确定接口与状态归属，并完成一条业务边界或一组低耦合路由的抽取。这是全量估算的一部分，不应把“目录拆开了”当作六个大模块治理完成。前后端工作台产品重构另外估算，二者在 App/侧栏有交集，可共用已稳定接口，但不能预先承诺具体省时比例。

## PERF-01：最便宜，但不能预设明显体感提升

复查 0.2.19 已保存的 7 秒首页 profile：续跑标记和待处理请求各两次；这份样本没有复现原审阅中的 config/read 和 project-root-suggestion 重复，不能照旧名单全部删。

`useQuotaResume` 同时有 mounted 首次刷新和 ready/changed 通知后刷新；它已有 pending 标志与 150ms 合并。`useDesktopState` 也有初始化、重连后的待处理请求重载。第二次读取可能是连接就绪后的必要一致性同步。

1–2 人日包含：追踪这几个请求的调用原因，给 profiler 补充相关重复计数；只合并确认为相同状态、相同参数、同一生命周期的重复在途读取，并测试失败后恢复、重连、额度续跑开关、审批到达/解决以及页面切换。如果第二次刷新有必要，可以保留并解释，不以请求数必须等于一为完成条件。

已有 profile 显示上述两个重复接口单次较快且响应很小；约 1 秒的提供商加载是另一条路径。没有证据表明删掉这两次请求会显著缩短首屏时间。

若另行扩大到跨账号额度/模型缓存，则是 **3–5 人日的替代范围**，不是这 1–2 人日之外的必做尾项；需要账号 ID、凭据/配置版本和失效事件的正确隔离，回归风险明显增加。总预算采用原审阅的局部 1–2 人日范围。

## DATA-01：历史可以分层，防重契约不能顺带改变

`automationHistory.ts:28` 保存 history-keys，`findByKey()` 通过索引读取完整历史运行；`automationEngine.manual()` 以该返回值阻止同一 requestId 再次执行并返回原运行。只保留索引却删掉正文也不足以维持当前行为，因为缺文件会走 ENOENT，最终可能被当作不存在。

hot state 已有每任务 100 条/30 天限制；问题是冷历史、逐条防重文件与首次枚举缓存的长期增长。现有页面按页读取正文，不能把“历史增长”误判为每次打开都会读取全部正文。

4–8 人日包含：

1. 用仅计数/尺寸的清单和虚构大数据集确认容量瓶颈，定义历史、展示索引、防重信息各自保留与恢复规则。
2. 按任务/时间分段归档与索引，保留旧格式兼容；用可恢复方式迁移，避免一次性遍历/迁移阻塞调度。
3. 原有请求仍能命中防重信息并保持必要返回语义；如压缩为 tombstone，必须同时适配读取契约，不能把缺正文视为新请求。
4. 故障注入覆盖迁移中断、归档后未写索引、写索引后未清旧记录、损坏文件、重复归档、并发手动运行及重启；测试分页与大目录的时间、内存、I/O。

**首步 1–2 人日可只做容量测量与方案，不删除数据**，计入完整估算。实际历史大小本轮未扫描，不能承诺真实迁移的日历时长；如果数据规模超出测试档位，需要另估。

若要求任意旧 requestId 永久精确防重，随着唯一请求不断增多，需要保留相应信息；不能同时承诺总存储永久固定上限。可减少文件数、热内存和重复正文，或把旧信息移到冷存储；若希望到期删除全部证据，就需要明确改变防重期限。当前用户要求核心契约不变，本预算默认继续保留防重能力，不包含擅自采用到期可重放的语义。

## 建议分批方式

以下顺序形成于项目主导 UI 的最终方向反馈之前。用户现已明确大幅替换现有侧栏，最新建议见[项目主导 0.3 与 0.2 收口取舍](20260912-0016-codexapp-项目主导0.3与0.2收口取舍.md)：前端模块与数据加载随新 UI 统一设计；下面的 10–18 人日组合保留为可选后端治理批次，不作为开始 0.3 的统一前置条件。 用户又明确 0.2 可能长期作为主力，且“减少修改”指的是定型后减少返工，并非本轮少投入。因此本轮可以集中完成长期稳定性所需的治理；全量 MOD-01 仍不是必做成本，稳定版范围与冻结规则以最新取舍文档为准。

1. 0.3 开始先用 MOD-01 的 3–5 人日首批把涉及 SCH-03 的接口与资源归属讲清并适度抽取；若取消修复已有清楚边界，不要求先完成全部 MOD-01。
2. SCH-03 独立实现和故障回归 4–8 人日；不与工作台布局、数据库迁移同时提交。
3. PERF-01 局部治理 1–2 人日；若两次读取属必要同步，保留行为并补正确指标。
4. 上述首批合计 8–15 人日，再留 2–3 人日组合验收，规划 **10–18 人日**。它只包含 MOD 的局部抽取，不代表完整清单已处理。
5. SEC-01 可作为独立批次 3–6 人日推进；按用户接受部分已知安全风险的取舍，不把全服务认证重做设为工作台开发前置。
6. DATA-01 先做无删除的盘点与格式方案，再按实际容量实施迁移；其余 MOD-01 跟随 0.3 稳定的功能边界继续拆分。

本次只写评估文档；没有修改运行代码、账号、服务配置或历史数据，也没有再次运行浏览器/调度测试。既有测试与 profile 作为估算依据，未来改动仍需新增对应验证。
