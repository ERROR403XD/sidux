## 4. 页面与入口设计

### 4.1 总体布局

建议左上角从左到右：sidebar 开关 → 搜索 → 新建对话 → 设置齿轮 → 主题按钮。五个图标沿用现有工具条尺寸、间距、悬停及焦点风格。

```text
左侧栏                                  主内容区
[侧栏] [搜索] [新对话] [齿轮] [主题]       设置
技能                                    账号与连接
自动化                                  通用
API 出口                                外观
对话/项目列表                           输入与发送
                                        集成
底部固定：激活 GPT 账号 + 用量摘要        关于与诊断
          点击展开账号操作
```

“进入和技能/自动化/API 出口的界面中”按同层级主内容页面理解：设置有独立路由和标题，复用应用壳层；不嵌入技能页面，也不继续使用左下角长设置弹层。

- 设置页面纵向滚动，由多个标题清晰的卡片区域组成。首期不另加二级设置侧栏或设置搜索。
- 页面采用独立的合理最大宽度，不受聊天宽度偏好限制；聊天宽度仅影响对话及输入区。
- 点击齿轮进入设置并显示激活态；重复点击不重复压入相同路由。浏览器前进/后退、直接访问和刷新 `#/settings` 可用。
- 进入设置前后保留当前对话选择和未发送草稿；导航本身不发送消息、不停止在途回复。
- 侧栏折叠时，设置和主题入口随现有工具条进入内容标题区。移动端进入设置后收起侧栏，让正文可见；避免同时展示两组重复工具条。
- 左下角常驻区固定在侧栏底部，不随长对话列表滚走。侧栏关闭时随侧栏隐藏，重新展开后仍直接显示摘要，无需再打开账号菜单。

### 4.2 ACCOUNT-01：常驻用量与账号弹层

底部触发区建议用两行紧凑布局：第一行显示激活 GPT 账号标识与展开提示，第二行显示主要用量窗口及剩余百分比。较长账号标识截断并提供完整提示；常用窗口优先，其他窗口和重置时间在展开区查看。

- 沿用当前“剩余百分比”口径，明确标注“剩余”，不让已用/剩余混淆。窗口名称按真实数据展示，不把所有账号硬编码为固定周期。
- 摘要绑定服务端确认的激活账号，不能绑定仅选中、正在登录或待切换的账号。切换中展示进行中状态，成功后账号标识与用量一起更新；旧账号异步结果不得覆盖新账号。
- 加载、无账号、无额度数据、刷新失败、数据过期分别展示。未知值不显示为 0%，无账号时仍保留“添加 GPT 账号”入口。
- 当前聊天来源为 OpenRouter/OpenCode/自定义端点时，可继续展示已激活 GPT 账号的额度，但明确其为 GPT 账号，避免被误认为当前第三方来源的额度。
- 点击整个摘要打开账号弹层，包含：激活账号详情、账号列表、添加账号、切换账号、刷新用量、重新认证、移除账号及相关状态/错误。
- 保留现有新增账号不自动切换、激活账号不可移除、操作忙碌限制、不可切换原因和移除确认等行为。
- 底部弹层仅放账号相关内容，并提供“账号设置”跳转至设置页账号分区。普通偏好、Provider 配置、版本等移到设置页面。
- 弹层使用 `AppPopover` 处理边界、外部点击及焦点；登录使用原 `AccountLoginDialog`。覆盖嵌套浮层与登录对话框的 Esc 顺序和关闭后的焦点恢复。

### 4.3 THEME-01：三态主题快捷按钮

建议按用户列举顺序循环：深色 → 浅色 → 跟随系统 → 深色。图标分别为月亮、太阳、显示器；显示器始终表示“跟随系统”这个偏好，即使系统当前实际呈现深色，也不替换成月亮。

- 点击立即应用并保存；提示文字说明当前模式和下一次点击的目标，提供可访问名称。
- 设置页“外观”中提供同一三态选项，与快捷按钮使用唯一状态源，修改任意入口后另一处立即同步。
- 复用原有主题存储与系统监听。跟随系统时响应系统变化，显式深色/浅色时不被系统覆盖。
- 验证刷新首屏、启动恢复界面与正常挂载后的主题一致，避免新增明显闪白；不另起一套主题判定逻辑。

## 5. SETTINGS-02：分区与完整迁移清单

| 分区（从上到下） | 迁入内容 | 展示与行为 |
| --- | --- | --- |
| 账号与连接 | GPT 账号管理、激活账号及额度、登录/重认证/切换/移除/刷新；现有 Provider 选择及配置 | GPT 主区默认展开、位于首位，包含 ACCOUNT-02 定时发送子块；其他连接单独收起，当前来源始终可辨认 |
| 通用 | 界面语言、显示时区 | 下拉沿用已有选项；说明显示时区的作用范围，不暗示会改写自动化调度时区 |
| 外观 | 主题、聊天宽度 | 主题与顶部按钮同步；宽度选择沿用原档位和即时生效行为 |
| 输入与发送 | Enter/组合键发送方式；语音点击切换、语音后自动发送、识别语言 | 分成文字发送与语音输入两组；界面语言和语音识别语言独立 |
| 集成 | Telegram 状态、Bot 配置、允许用户列表及保存/错误提示 | 沿用现有显式保存流程，不因展开、切换路由而保存草稿 |
| 关于与诊断 | 版本、工作树、运行能力、重新检测、反馈入口 | 状态与操作分开；仅描述有证据的能力，检查现有静态能力文案是否过时 |

### 5.1 GPT 优先与可选来源

- 页面名称面向用户使用“GPT 账号（ChatGPT 登录）”，实现中沿用原 Codex provider 标识及账号协议，不重命名后端枚举。
- GPT 主区包含完整管理能力；底部账号弹层是快捷操作，两处复用同一账号数据与操作逻辑，不各建一套轮询、忙碌标志和错误状态。
- “其他连接（可选）”包含 OpenRouter、OpenCode Zen、自定义端点。保留 OpenRouter API key 及 API 格式、OpenCode Zen key、自定义 URL/key/API 格式的现有功能。
- 第三方来源默认收起；若当前正在使用其中一个，标题显示当前来源，并默认展开对应配置，避免隐藏正在生效的连接。
- 展开可选项只是查看；切换来源必须通过明确的选择操作。进入页面不能隐式改回 GPT，也不能触发登录或清除第三方凭据。
- 来源切换沿用现有保存、后端重连、模型目录刷新与失败呈现逻辑。这里调整信息层级，不擅自改变无认证回退策略。
- “账号与连接”管理聊天后端接入；“API 出口”仍保留独立主页面，不把其 key、转发配置和统计全部塞入设置。

### 5.2 其他现有内容的归属

- 当前对话上下文用量属于对话状态，不是全局偏好。优先保留于现有对话状态区域；若搬迁后没有等价入口，则在“关于与诊断”放明确标注当前对话的只读信息，不能直接丢弃。
- 账号额度详情移到账号分区及快捷弹层，不在“关于”再重复一份。
- 工作树/版本从左下角触发按钮迁到“关于与诊断”；底部空间优先用于账号与额度。
- “发送方式”首期迁移现有 Enter/组合键偏好；忙碌时排队/立即/引导等已有对话控件不擅自改成新全局默认项。如后续提出该需求，另列条目。

### 5.3 统一表单规则

每个分块采用标题、必要的一句说明、设置行组成；设置行左侧名称/帮助，右侧控件，窄屏按需上下排列。沿用现有描边、圆角、颜色和间距，避免新增装饰性视觉体系。

普通单选使用 `AppSelect`，操作使用 `AppButton`，确认/登录使用适用的共享对话框。决定性深色规则放在 `src/style.css`，不引入原生 select 或单页专用组件库。

本地偏好继续即时保存；涉及端点、key、Telegram 等表单沿用显式保存及校验。未保存草稿切换页面时不得静默写入，拟保留至本次应用会话结束，或在存在丢失风险时明确提示。保存错误在所属分区可见，不把失败显示成成功。

## 7. 验收与性能计划

以下均为待执行用例，不是已经通过的结果。实施时将精确步骤补到 `tests/` 对应领域文档，`tests.md` 仅维护索引。

| 场景/前置条件 | 操作 | 预期结果 |
| --- | --- | --- |
| 已有对话草稿，含正在回复的线程 | 打开设置，前进/后退，再返回对话 | 草稿与选择保留，回复继续，没有重复发送 |
| 设置路由 | 直接访问、刷新、连续点击齿轮 | 页面可恢复，无重复路由项或对话加载副作用 |
| 至少两账号 fixture；另做获授权的真实账号验收 | 新增、刷新、重新认证、切换、移除非激活账号 | 两入口状态一致；新增不自动切换，忙碌限制和错误保留 |
| 模拟旧额度请求延迟，随后切换账号 | 让旧请求晚于新请求返回 | 激活账号及摘要仍属于新账号，不串用量 |
| 无账号、无额度、过期/失败 fixture | 打开/关闭账号菜单，刷新 | 状态可辨认，未知不显示为零，仍能添加账号 |
| 所有旧设置已有非默认值 | 升级候选、逐项修改、刷新页面 | 原值保留；新值真实保存，旧入口功能没有遗漏 |
| GPT 与可选来源分别配置 | 展开来源但不选择，再执行显式来源切换 | 展开无副作用；实际切换、模型更新及失败恢复符合现有逻辑 |
| 本地偏好与服务端配置故障注入 | 修改主题/语言/时区/发送/语音；保存无效连接配置 | 本地偏好正确生效；配置失败明确显示，不误报已保存 |
| 深色、浅色、跟随系统 | 顶部循环、设置页选择、改变系统主题、刷新 | 图标与偏好匹配，两入口同步，跟随行为正确 |
| 长列表、长账号名、大字体及移动端 | 滚动、展开弹层、打开下拉/登录框、键盘 Esc/Tab | 底部固定，浮层不越界；焦点/嵌套关闭顺序正确 |

UI 必测 1440×900、375×812、768×1024，覆盖浅深主题与系统模式。按仓库规则优先 Browser Use；需要网络拦截、存储/系统主题模拟时使用 Playwright CJS，记录具体原因。检查真实设置控件和账号弹层，保存 `output/playwright/` 下截图、URL、视口、断言与刷新证据。

涉及 Provider/auth 路径时按仓库 Provider/Auth Docker Workflow 构建打包并验证无认证回退、无效/过期认证刷新后错误保留、畸形认证回退及 Zen → OpenRouter 切换；fixture 通过不等于真实网页登录完成。完整登录、真实第二账号切换若未执行，必须留作待验收。

### 性能门槛

- 以相同数据、视口和当前源码 4173 服务比较迁移前后：首页、设置页、对话 → 设置 → 对话、账号弹层反复开关。

## 11. ACCOUNT-02：账号定时发送（5h 窗口启动尝试）

### 11.1 目标及当前结论

用户希望在指定时间对所选 GPT 账号发一条消息，让额度窗口尽早开始计时；不要求精确计算窗口、复杂策略或定时工作流。设置位于“账号与连接 → GPT 账号管理”，只需总开关、账号选择、发送时间。执行时须给账号准备留够等待时间，并尽可能不显式切换账号，以免打断对话任务和 API 出口。

**建议优先采用独立后台发送实例，按指定账号调用，不改变界面的激活账号。源码已有实现基础，但尚未证明整个路径无干扰，也尚未实测这种请求能否启动用户预期的窗口。** 本轮只补充方案，不发消息、不切账号、不创建运行中的定时任务。

官方说明使用五小时周期描述部分套餐的本地消息额度，并要求以用量面板的当前限额和重置时间为准；该说明没有保证“任意一条短消息必定从此刻新建完整五小时窗口”。因此本功能对外使用“定时发送”，说明用途为“尝试启动额度窗口”，不显示未经验证的“激活成功”。来源：[OpenAI 官方额度说明](https://learn.chatgpt.com/docs/pricing#what-are-the-usage-limits-for-my-plan)，核对于 2026-09-07。

若窗口本来已在计时，一条新消息不能被当作重开/延长窗口；使用其他模型的独立额度或普通 API key 计费也不能证明目标 GPT 账号窗口生效。实际效果要按账号、模型及返回窗口分别观察。

### 11.2 最小 UI 与默认行为（建议值，待审阅）

| 控件/信息 | 首期设计 |
| --- | --- |
| 总开关 | “启用账号定时发送”，默认关闭；关闭保留已选账号和时间 |
| 生效账号 | GPT 账号复选列表，以稳定 storageId 保存；可全选/取消，显示不可用原因；账号改名不丢选择，删除后不再执行 |
| 发送时间 | 所选账号共用一个每日 HH:mm 时间，精度到分钟；首期不做每账号独立时间、多个时段或任意 cron |
| 时区 | 与时间一起明确展示；初次保存取当前全局显示时区解析出的 IANA 时区并固定保存。之后改变显示时区不悄悄改变发送时刻，可在本区重新选择任务时区 |
| 发送内容 | 固定短文本“请只回复 OK。”；不加项目、历史、工具、附件或当前对话上下文，首期不开放模板编辑 |
| 执行摘要 | 下一次计划时间，以及每账号最近一次实际时间/结果/简短原因；不建设独立报表页面 |

启用时要求至少一个账号和有效时间。开启/保存本身不立即发送，从下一个计划时点开始。页面关闭不影响执行；调度运行在服务端，应用服务停止期间无法发送。多账号按顺序执行，时间是批次开始时间，后续账号允许相差几十秒或几分钟；页面显示真实执行时间。

模型使用经验证可访问且计入目标窗口的标准速度文本模型，关闭 Fast，不盲目挑“最便宜模型”或切到不同额度池。首期由后端确定并记录所用模型，不增加必须填写的模型控件；无法找到已验证模型时报告不可执行，不随机尝试多个模型。短回复只能减少请求规模，不保证固定 Token 消耗。

### 11.3 现有代码为何有基础，但不能直接复用线上出口实例

| 源码事实 | 可复用能力/限制 |
| --- | --- |
| `AccountAuthCoordinator.getApiCredential(selectedStorageId)` 可读取指定账号；仅参数为空时取 activeStorageId | 已支持不激活目标账号而获得其调用凭据；定时发送必须传明确 ID，账号删除时不能回退到当前账号 |
| `ProxyComponent` 把一份账号 access token 投影到独立 runtime 目录，启动本地 CLIProxyAPI 子进程 | 可复用固定组件、配置生成、校验、就绪等待和请求传输机制，不需要修改主运行时认证 |
| `ProxyGateway` 使用全局出口配置中的 accountStorageId 调用一个 component | 修改出口所选账号会影响对外供给；不能为了定时消息临时改出口设置再恢复 |
| `ProxyComponent.prepare()` 的 10 秒快路径与单个 flight 未按输入账号区分 | 单实例交替 prepare(A)/prepare(B) 可能复用 A 的结果；新用途需固定一实例一账号，不能假定传不同 ID 就一定切换 |
| `getApiCredential()` 在 token 接近到期时主动刷新；刷新使用全局 withOperation | 会设置全局账号忙碌状态；HTTP 准入及 WS 后续轮次有 account_busy 检查，后台刷新仍可能影响出口 |
| `switchAccount()` 要求空闲、写主认证、dispose/re建主运行时，并参与出口变更协调 | 显式切换不是无副作用操作；多等几秒不能消除正在执行任务时的干扰 |
| `automationEngine.ts` 已有调度、时区、执行记录等机制，但通过 runtime 创建线程及启动回合 | 可参考时间换算和去重；不能直接把普通自动化挂到主账号运行时就当作独立账号发送 |

上述为本轮静态核对结果，不是对现有固定账号出口用法报告缓存故障；缓存限制是在拟新增“跨账号轮用单实例”场景下才必须处理的问题。

### 11.4 路径比较与推荐

| 路径 | 干扰与复杂度 | 结论 |
| --- | --- | --- |
| 独立临时 ProxyComponent，每次固定一个目标账号 | 不修改主账号、不改线上出口配置；复用现有二进制。仍需处理刷新锁、账号变更竞态、进程资源 | 首选，先做隔离可行性验证 |
| 为目标账号单独启动隔离 Codex app-server | 可走原生消息路径，但配置/线程/工具环境及刷新回写更复杂、启动成本更高 | 第一条无法验证目标额度效果时再评估，不同时实现两套 |
| 显式切换主账号 → 等待 → 发送 → 恢复原账号 | 必须等待对话、队列、审批、后台终端、自动化和出口均空闲；切换和恢复都可能失败 | 不作为首期自动降级方案；若确有必要，补充方案再决定 |
| 修改正在服务的 API 出口账号，借其发送 | 会改动现有服务的账号选择及组件代际 | 不采用 |

推荐每账号任务创建自己的固定账号组件，使用独立目录和随机本地端口；只在批次执行期间存在，一个完成并清理后再处理下一个。它不是新增用户 API 出口，不要求用户启用现有出口或创建 API key，也不抢占现有出口的配置、实例、会话命名空间、并发槽位或 key 统计。组件缺失时报告原因，不自动开启用户出口。

### 11.5 不干扰原则与凭据刷新处理

首期尽量采用较小改动：为后台任务提供“读取指定账号当前有效凭据、禁止触发刷新”的受控入口，复用 store 的身份/状态校验，不绕过账号管理自行维护 refresh token。返回凭据须包含账号 ID、revision、过期时间，并在发送前再次验证身份和代际。

- 有足够有效期的 access token 时执行；建议要求覆盖准备及请求最大耗时再留余量，例如剩余不少于 5 分钟，具体阈值按最终超时配置核对。
- 需要刷新、登录/切换/移除进行中，或无法确认稳定凭据时，本次后台任务延后。首期不主动调用会占用全局操作锁的刷新或额度探针，也不自动重新登录。
- 如果普通账号维护已完成刷新，延后任务可用新 revision 再尝试。一直无法获得条件则跳过，并显示“凭据需刷新/需重新认证”等原因。可靠执行与绝对不干扰之间，先选择后者。
- 发送前建立针对目标账号的短期使用登记，串行化“最后校验 → 发起请求”与账号移除/切换/凭据更新，不能仅做一次无锁检查。用户操作优先：取消尚未发送的任务；已在途请求尽力取消并记为结果未知，不让后台消息长时间阻挡用户操作。
- 不为整个后台发送设置全局 operation，不 stop/drain 线上出口，不 dispose 主运行时；不写 activeStorageId、不 materializeActive、不把当前来源改成 GPT。
- 更完善的按账号刷新锁属于后续优化：若用户需要更高准点成功率，再评估拆分全局锁，证明不会降低原认证一致性后实施，首期不为这一功能大改协调器。
- 额度观察优先用请求返回信息或已有缓存；需要主动刷新额度时也必须遵守上述约束，不能发送不干扰却在发送后探测时阻断出口。

独立连接仍会占用同一账号的真实额度、服务端并发以及本机资源，不能承诺物理意义上的零影响。验收目标是无显式切换、无主动断流/重启、无本功能引入的 account_busy，并测量资源和请求延迟。

### 11.6 执行等待、调度与失败语义

建议流程：到时 → 持久化本次任务 → 逐账号确认配置仍有效 → 等待可用凭据 → 启动固定账号组件 → 就绪并确认目标身份 → 发送一次短请求 → 读取成功终态 → 记录并清理。

- 等待以身份/凭据代际及组件 readiness 为依据，不靠固定 sleep 后直接发。现有就绪循环次数有限，但每次 fetch 还需明确超时；新 worker 应有覆盖准备全过程的硬截止时间。
- 建议初始上限：准备 30 秒、发送 60 秒、账号间隔 5 秒；忙碌/未发出的准备失败按约 30 秒重查，最多允许计划后 15 分钟延迟。均为内部默认值，先不加高级控件；实测后可调。
- readiness 和模型目录成功仅证明组件可接收请求。发送成功必须有可识别的最终成功事件，HTTP 200 或流开始不能算成功；到达截止时间取消并回收本次组件。
- 仅对确定尚未提交给上游的准备失败做有界重试；请求已发出后超时、断流或重启，记“结果未知”，不盲目重发。明确认证/额度/模型错误结束该账号本次任务，继续其他账号。
- 同一调度服务只启动一个执行队列，跨进程使用持久化租约/单执行者控制；以“计划时点 + 账号 ID”建立唯一执行记录，配置 revision 用于取消过时工作，不让修改设置生成同一时点的重复消息。
- 发送前先持久化 started/发送意图；崩溃恢复时对可能已发送的记录标未知而非重放。首期接受偶尔漏发，不能宣称跨网络 exactly-once。
- 服务重启只恢复未来时点，已经错过的批次不补发；当时在线但因冲突延后的未发送任务可在 15 分钟窗口内执行。关闭总开关清除待发工作；已发送请求不能撤回，仍结算其结果。
- 修改账号/时间会取消尚未发送的旧计划并计算下一次时间；日光节约重复时刻只执行一次，不存在的时刻跳过当天；时间回拨不重复发，时间大幅前跳不追赶发送。
- 配置和执行记录持久化在当前实例 CODEX_HOME 下独立子目录，例如 `codexapp-account-schedules/`。建议记录最近 30 天且最多 1000 条，保留时间、账号 ID、模型、状态、原因及可用的 usage/窗口信息，不保存凭据或对话正文。
- 复用现有时区换算和调度去重思路，采用轻量服务端定时检查，不建立浏览器定时器，不接外部调度服务，也不为每账号常驻一个进程。

### 11.7 验证顺序和可行性门槛

1. **隔离调用验证**：主运行时使用测试账号 A，后台固定账号 B；验证 B 的身份及实际成功响应，主 activeStorageId、认证文件、运行时实例和出口配置不变。再测顺序 A/B，排除缓存串号。仅使用获授权的测试账号。
2. **目标窗口验证**：选择已知未在计时或已重置的测试账号，记录调用前后的目标窗口 ID、重置时间及用量；若信息有延迟，做少量有界复查。成功响应但没有充分窗口证据时写“发送成功，窗口效果未确认”；原本计时中的窗口不能证明启动能力。
3. **业务并发验证**：普通线程持续回复、队列/自动化工作、API JSON/SSE 与长连接 WS 同时存在时运行后台发送，确认无断流、无重复回复、无额外全局 busy 和组件替换；比较延迟及错误率。
4. **认证竞态验证**：近过期 token、刷新中、登录/重认证/切换/删除目标账号、revision 改变；应延后/取消/跳过，不能误发给当前账号或阻挡用户操作。验证“后置额度刷新”同样不引入全局锁。
5. **调度验证**：开关、账号选择、共同时间/时区、刷新保留、关闭网页、服务重启、时钟跳变、重复 tick、多实例争用、发送后崩溃和超时，确认无无界补发/重试。
6. **资源与清理验证**：记录单账号准备耗时、批次总时长、最大子进程数、CPU/RSS、临时目录、定时器及并发 API 的延迟变化；完成/失败/取消均释放进程与目录，API key 账本不混入内部定时消息。

UI 测试沿用第 7 节的主题/视口规则，补充开关、复选列表、时间保存、下一次时间和执行结果。Provider/auth、模块加载相关改动按仓库要求做打包 Docker 矩阵及 CJS smoke。

首个门槛未通过时停止增加设置界面，先报告独立调用限制；窗口验证不成立时不能以请求成功交付“激活 5h”目标，应记录观察结果再决定保留通用定时发送还是延期该条目。

### 11.8 范围和回滚补充

不开发自动算最佳启动时间、自动绕限额轮换、模型回退连发、账号独立 cron 或复杂通知。通用输入框、普通自动化及线上 API key 功能保持各自语义。

回滚先关闭本功能并停止其队列/worker，取消尚未提交的请求，保留执行记录供检查；只清理本功能临时目录，不删除账号池。已消耗额度不能撤回；不需要“切回原账号”，因为推荐方案从未修改主激活账号。

当前状态：静态可行性分析完成，独立发送、定时调度、真实额度窗口及并发无干扰均未实施/未验证。后续实施须先完成上述可行性门槛，再推进 ACCOUNT-02。
