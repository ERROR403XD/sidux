本文是 0.2.11 的持续开发方案，从日常使用测试中积累修改项，不预设需求收集截止日期。当前先确定账号入口、设置页面、主题切换及账号定时发送的设计，后续反馈继续补充本文；同一问题更新原条目，不重复创建方案。

## 4. 页面与入口设计

### 4.1 总体布局

用户已确定左上角从左到右：sidebar 开关 → 主题按钮 → 设置齿轮 → 搜索 → 新建对话。五个图标沿用现有工具条尺寸、间距、悬停及焦点风格。

```text
左侧栏                                  主内容区
[侧栏] [主题] [齿轮] [搜索] [新对话]       设置
技能                                    账号与连接
自动化                                  通用
API 出口                                外观
对话/项目列表                           输入与发送
                                        集成
底部固定：激活 GPT 账号 + 用量摘要        关于
          点击展开账号操作
```

“进入和技能/自动化/API 出口的界面中”按同层级主内容页面理解：设置有独立路由和标题，复用应用壳层；不嵌入技能页面，也不继续使用左下角长设置弹层。

- 设置页面纵向滚动，由多个标题清晰的卡片区域组成。首期不另加二级设置侧栏或设置搜索。
- 页面采用独立的合理最大宽度，不受聊天宽度偏好限制；聊天宽度仅影响对话及输入区。
- 点击齿轮进入设置并显示激活态；重复点击不重复压入相同路由。浏览器前进/后退、直接访问和刷新 `#/settings` 可用。
- 进入设置前后保留当前对话选择和未发送草稿；导航本身不发送消息、不停止在途回复。
- 侧栏折叠时，设置和主题入口随现有工具条进入内容标题区。移动端进入设置后收起侧栏，让正文可见；避免同时展示两组重复工具条。
- 左下角常驻区固定在侧栏底部，不随长对话列表滚走。侧栏关闭时随侧栏隐藏，重新展开后仍直接显示摘要，无需再打开账号菜单。

### 4.2 ACCOUNT-01：常驻用量与账号弹层

底部触发区建议用两行紧凑布局：第一行显示激活 GPT 账号标识与展开提示，第二行显示主要用量窗口及剩余百分比。较长账号标识截断并提供完整提示；常用窗口优先，其他窗口和重置时间在展开区查看。

- 沿用当前“剩余百分比”口径，明确标注“剩余”，不让已用/剩余混淆。窗口名称按真实数据展示，不把所有账号硬编码为固定周期。
- 摘要绑定服务端确认的激活账号，不能绑定仅选中、正在登录或待切换的账号。切换中展示进行中状态，成功后账号标识与用量一起更新；旧账号异步结果不得覆盖新账号。
- 加载、无账号、无额度数据、刷新失败、数据过期分别展示。未知值不显示为 0%，无账号时仍保留“添加 GPT 账号”入口。
- 当前聊天来源为 OpenRouter/OpenCode/自定义端点时，可继续展示已激活 GPT 账号的额度，但明确其为 GPT 账号，避免被误认为当前第三方来源的额度。
- 点击整个摘要打开账号弹层，包含：激活账号详情、账号列表、添加账号、切换账号、刷新用量、重新认证、移除账号及相关状态/错误。
- 保留现有新增账号不自动切换、激活账号不可移除、操作忙碌限制、不可切换原因和移除确认等行为。
- 底部弹层放账号相关内容和 Codex/CodexApp 双版本摘要，并提供“账号设置”跳转至设置页账号分区。普通偏好、Provider 配置和完整运行能力详情移到设置页面；版本布局见第 15 节。
- 弹层使用 `AppPopover` 处理边界、外部点击及焦点；登录使用原 `AccountLoginDialog`。覆盖嵌套浮层与登录对话框的 Esc 顺序和关闭后的焦点恢复。

### 4.3 THEME-01：三态主题快捷按钮

建议按用户列举顺序循环：深色 → 浅色 → 跟随系统 → 深色。图标分别为月亮、太阳、显示器；显示器始终表示“跟随系统”这个偏好，即使系统当前实际呈现深色，也不替换成月亮。

- 点击立即应用并保存；提示文字说明当前模式和下一次点击的目标，提供可访问名称。
- 设置页“外观”中提供同一三态选项，与快捷按钮使用唯一状态源，修改任意入口后另一处立即同步。
- 复用原有主题存储与系统监听。跟随系统时响应系统变化，显式深色/浅色时不被系统覆盖。
- 验证刷新首屏、启动恢复界面与正常挂载后的主题一致，避免新增明显闪白；不另起一套主题判定逻辑。

## 5. SETTINGS-02：分区与完整迁移清单

| 分区（从上到下） | 迁入内容 | 展示与行为 |
| --- | --- | --- |
| 账号与连接 | GPT 账号管理、激活账号及额度、登录/重认证/切换/移除/刷新；现有 Provider 选择及配置 | GPT 主区默认展开、位于首位，包含 ACCOUNT-02 定时发送子块；其他连接单独收起，当前来源始终可辨认 |
| 通用 | 界面语言、显示时区 | 下拉沿用已有选项；说明显示时区的作用范围，不暗示会改写自动化调度时区 |
| 外观 | 主题、聊天宽度 | 主题与顶部按钮同步；宽度选择沿用原档位和即时生效行为 |
| 输入与发送 | Enter/组合键发送方式；语音点击切换、语音后自动发送、识别语言 | 分成文字发送与语音输入两组；界面语言和语音识别语言独立 |
| 集成 | Telegram 状态、Bot 配置、允许用户列表及保存/错误提示 | 沿用现有显式保存流程，不因展开、切换路由而保存草稿 |
| 关于 | 版本、工作树、运行能力、重新检测、反馈入口 | 状态与操作分开；仅描述有证据的能力，检查现有静态能力文案是否过时 |

### 5.1 GPT 优先与可选来源

- 页面名称面向用户使用“GPT 账号（ChatGPT 登录）”，实现中沿用原 Codex provider 标识及账号协议，不重命名后端枚举。
- GPT 主区包含完整管理能力；底部账号弹层是快捷操作，两处复用同一账号数据与操作逻辑，不各建一套轮询、忙碌标志和错误状态。
- “其他连接（可选）”包含 OpenRouter、OpenCode Zen、自定义端点。保留 OpenRouter API key 及 API 格式、OpenCode Zen key、自定义 URL/key/API 格式的现有功能。
- 第三方来源默认收起；若当前正在使用其中一个，标题显示当前来源，并默认展开对应配置，避免隐藏正在生效的连接。
- 展开可选项只是查看；切换来源必须通过明确的选择操作。进入页面不能隐式改回 GPT，也不能触发登录或清除第三方凭据。
- 来源切换沿用现有保存、后端重连、模型目录刷新与失败呈现逻辑。这里调整信息层级，不擅自改变无认证回退策略。
- “账号与连接”管理聊天后端接入；“API 出口”仍保留独立主页面，不把其 key、转发配置和统计全部塞入设置。

### 5.2 其他现有内容的归属

- 当前对话上下文用量属于对话状态，不是全局偏好。优先保留于现有对话状态区域；若搬迁后没有等价入口，则在“关于”放明确标注当前对话的只读信息，不能直接丢弃。
- 账号额度详情移到账号分区及快捷弹层，不在“关于”再重复一份。
- 左下角常驻触发按钮优先用于账号与额度；展开弹层后显示 Codex/CodexApp 双版本摘要，工作树及完整版本/能力详情放在设置“关于”分块。
- “发送方式”首期迁移现有 Enter/组合键偏好；忙碌时排队/立即/引导等已有对话控件不擅自改成新全局默认项。如后续提出该需求，另列条目。

### 5.3 统一表单规则

每个分块采用标题、必要的一句说明、设置行组成；设置行左侧名称/帮助，右侧控件，窄屏按需上下排列。沿用现有描边、圆角、颜色和间距，避免新增装饰性视觉体系。

普通单选使用 `AppSelect`，操作使用 `AppButton`，确认/登录使用适用的共享对话框。决定性深色规则放在 `src/style.css`，不引入原生 select 或单页专用组件库。

本地偏好继续即时保存；涉及端点、key、Telegram 等表单沿用显式保存及校验。未保存草稿切换页面时不得静默写入，拟保留至本次应用会话结束，或在存在丢失风险时明确提示。保存错误在所属分区可见，不把失败显示成成功。

## 7. 验收与性能计划

以下均为待执行用例，不是已经通过的结果。实施时将精确步骤补到 `tests/` 对应领域文档，`tests.md` 仅维护索引。

| 场景/前置条件 | 操作 | 预期结果 |
| --- | --- | --- |
| 已有对话草稿，含正在回复的线程 | 打开设置，前进/后退，再返回对话 | 草稿与选择保留，回复继续，没有重复发送 |
| 设置路由 | 直接访问、刷新、连续点击齿轮 | 页面可恢复，无重复路由项或对话加载副作用 |
| 至少两账号 fixture；另做获授权的真实账号验收 | 新增、刷新、重新认证、切换、移除非激活账号 | 两入口状态一致；新增不自动切换，忙碌限制和错误保留 |
| 模拟旧额度请求延迟，随后切换账号 | 让旧请求晚于新请求返回 | 激活账号及摘要仍属于新账号，不串用量 |
| 无账号、无额度、过期/失败 fixture | 打开/关闭账号菜单，刷新 | 状态可辨认，未知不显示为零，仍能添加账号 |
| 所有旧设置已有非默认值 | 升级候选、逐项修改、刷新页面 | 原值保留；新值真实保存，旧入口功能没有遗漏 |

## 11. ACCOUNT-02：空闲满额账号的定时激活

### 11.1 已明确的简化规则

用户补充：到指定时间仍有活动的账号不需要激活。只考虑已开启此功能、目标额度仍为 100% 且没有连接的账号；只需保证启动激活时不冲突，不必等待忙碌账号空闲后再补发。

这里的“100%”按现有界面口径理解为**目标 5h 窗口剩余 100%（原始 usedPercent 为 0）**，不是已用完 100%。不根据四舍五入后的显示文本判断，也不拿周额度或另一个模型的额度池替代目标窗口。

执行规则固定为：

```text
到达计划时间
  └─ 检查已勾选账号
       ├─ 有活动/连接 → 跳过本次
       ├─ 目标额度不是剩余 100% → 跳过本次
       ├─ 额度、连接或凭据状态不明 → 跳过本次
       └─ 剩余 100% 且无连接 → 列入本次候选
            └─ 启动前再次检查并登记本账号任务
                 ├─ 出现冲突 → 跳过本次
                 └─ 无冲突 → 独立发送一条短消息 → 记录结果并清理
```

**删除上一稿的 15 分钟延后窗口、每 30 秒重查和等待凭据恢复后补发。** 忙碌或不满足条件即结束该账号本次计划，下一次计划时间再重新判断；不为精确启动窗口增加持续监测或复杂调度。

本轮仅修订方案，未发送消息、切换账号或创建运行中的定时任务。

### 11.2 设置页面与最小交互

位置：“账号与连接 → GPT 账号管理 → 定时激活”。

| 控件/信息 | 首期设计 |
| --- | --- |
| 总开关 | “启用账号定时激活”，默认关闭；关闭保留选择和时间 |
| 生效账号 | GPT 账号复选列表，保存稳定 storageId；删除账号后不再执行，不回退到当前账号 |
| 激活时间 | 支持添加、删除多个每日 HH:mm 时刻，例如 08:00、13:00、18:00；所选账号共用这组时间，按时间排序并去重；时区清楚显示并保存，不做每账号独立时间或 cron |
| 执行摘要 | 下次计划时间、每账号最近实际时间及结果：发送成功、已使用跳过、有连接跳过、状态不明跳过、失败或结果未知 |

时区初次取当前显示时区解析后的 IANA 值并随计划固定保存；更改全局显示时区不悄悄改动计划，可在本区重新选择任务时区。开启要求至少选中一个账号、至少保留一个有效时刻；开启/保存不立即发送，从整组时间中最近的未来计划时刻开始。每个时刻独立筛选账号：上一个时刻被跳过不影响下一次检查，上一个时刻发送成功也不保证下一次符合条件。

固定发送“请只回复 OK。”，不携带项目、历史、工具和附件，不开放消息模板编辑。使用经验证可访问且计入目标窗口的标准速度文本模型，关闭 Fast；不随机切换不同额度池的模型。模型选择与实际窗口效果留待可行性测试，首期不增加高级配置。

设置文案明确：“到点仅对目标额度剩余 100% 且没有活动连接的账号发送；其他情况跳过，不补发。”调度在服务端执行，关闭网页不影响；服务停止期间错过的计划不补发。

### 11.3 如何判断“100% 且没有连接”

- 先查本机活动，明显忙碌的账号直接跳过，不再为它查询额度或准备发送组件。
- 额度必须来自可归属到目标账号、目标窗口的原始数据，并具有可接受的新鲜度。建议将快照最长有效期设为内部常量（初值 60 秒，待实测）；快照过期时只允许一次不会干扰现有服务的只读查询，无法安全取得就跳过。
- 有效额度为剩余 100% 只是本功能的筛选条件，不据此推断该窗口一定从未启动；不另做复杂的窗口推演。
- “连接/活动”包括该账号上的在途 HTTP/SSE、仍打开的 WebSocket（即使暂时没有生成）、正在执行的对话/自动化、待执行队列、待处理交互及后台任务占用。不能仅凭“当前没有输出”判断空闲。
- API 出口启用或空闲组件进程存在，本身不等于有用户连接；仅打开网页、存在历史对话或账号被选为当前账号，也不自动算业务占用。
- 活动归属按实际请求使用的账号/组件 generation 记录，不能只看当前激活账号或出口最新配置。若现有记录无法确定归属，保守跳过可能受影响的账号，首期不为此建设完整连接监控系统。
- 本机不能完整获知其他设备的连接；它们的使用可能反映在额度数据中，但不能据此承诺跨设备无连接。首期范围是本实例可观察的活动与可用额度信息。

到点只生成一次候选集合，已因活动/用量而跳过的账号不在本批次重新入选。对候选逐个启动时再复核条件，避免前一个账号执行期间后一个账号已经开始工作。

### 11.4 实现路径与启动防冲突

推荐继续复用 API 出口的独立账号调用方式：**一个临时发送组件固定一个账号，按顺序执行，不修改主激活账号或线上出口设置。** 这样目标账号可以空闲，而另一账号仍正常提供聊天/API 服务；无需为了这次功能搭建“切换主账号再恢复”的流程。

已核对的源码约束：

| 位置 | 与本方案相关的事实 |
| --- | --- |
| `AccountAuthCoordinator.getApiCredential(selectedStorageId)` | 可以读取指定账号凭据，但 token 接近过期时会自动刷新 |
| `ProxyComponent.prepare()` | 单实例的 10 秒快路径和单个 flight 没按目标账号区分；不能跨账号轮用同一个实例 |
| `accountAuthCoordinator.ts` / `apiProxy/gateway.ts` | 刷新使用全局账号操作锁，出口准入会检查该锁；目标账号空闲并不能保证其他账号不受此刷新影响 |
| `apiProxy/activity.ts` / `gateway.ts` | 已有活动记录和组件代际，可据此补齐必要的账号归属；总连接数不能直接当作某个账号的连接数 |

因此首期仅增加一个禁止主动刷新凭据的后台读取路径，保留身份、状态、revision 和有效期校验；需要刷新或重新认证时直接跳过。不为此拆分全局刷新锁，也不自动重新登录。额度查询同样不能触发影响其他账号的全局操作；必要时跳过本次。

启动防冲突只保留必要的短临界区：

1. 确认账号仍被勾选、额度仍符合条件、没有活动或账号操作。
2. 将检查与后台任务登记做成原子准入，并与该账号的新请求准入/账号变更使用同一协调点；单纯“先查空闲，再异步发送”仍有竞态。
3. 准备组件期间有前台工作进入时，前台优先，尚未发送的后台任务取消；真正发出前再做一次短检查，不把组件准备时间当作已占用全局账号锁。
4. 请求已发出后只做常规超时和清理；无需阻止后续正常请求直到激活结束，也不因新连接出现而重发、切号或追求绝对独占。

“只检查启动冲突”不要求长时间锁住目标账号，更不要求其他账号全部空闲。只要不改变主认证、不重启主运行时、不 drain 线上出口，就不需要恢复原账号；独立发送仍会正常消耗目标账号额度。

若固定账号组件不可用，记录失败并跳过；首期不自动降级为显式切换，也不依赖用户手动启用 API 出口或创建 API key。后台消息不计入现有用户 API key 的调用账本。

### 11.5 等待、去重与执行记录

只等待本次发送必需的组件准备和响应，不等待其他任务结束。建议内部上限：组件准备 30 秒、请求 60 秒；必须确认 readiness 与账号身份，不能仅固定 sleep 后发送。内部就绪探测也要有单次超时和总截止时间。

- 一次计划每账号最多发一条，账号逐个处理；准备失败、超时、冲突均跳过/结束，不循环补发。账号数导致顺序执行略有延迟可以接受，不追求同时或秒级准确。
- 成功需确认请求最终成功状态；HTTP 200、模型目录成功或流开始都不等于消息成功。已发送后断流/超时记“结果未知”，不自动重发。
- 保留简单持久化去重：以具体计划日期时间（含时区换算后的时刻）和账号 ID 唯一标识执行，发送前记意图；重启后不重放可能已发出的请求。服务端保持单执行者，不新增复杂任务编排系统。
- 重复输入同一时刻只保存一项，不重复执行；不同计划时刻分别判断、分别去重。如果前一次激活请求尚未结束，下一时刻将该账号视为有活动并跳过，不叠加发送。
- 保存配置后只计算未来时间；删除某个时刻取消其尚未发送的候选，新增已过时刻从次日开始；关闭开关取消未发出的候选。时间回拨和重复调度不重复发，错过的时点不补发。
- 配置和少量执行摘要保存在当前实例 CODEX_HOME 的独立目录；建议最近 30 天、最多 1000 条，不存凭据或消息正文。完成、失败、取消均清理本次临时组件及目录。

### 11.6 聚焦验收

| 条件/操作 | 预期 |
| --- | --- |
| 已勾选，目标原始 usedPercent=0，额度新鲜且无连接 | 启动一次独立请求 |
| 原始已用比例大于 0，但 UI 四舍五入仍显示剩余 100% | 跳过，不能按显示文本误判 |
| 有 HTTP/SSE、空闲 WS、对话/自动化或其他业务占用 | 跳过；后来空闲也不补发 |
| 未勾选、快照过期无法安全更新、窗口缺失、连接归属不明或凭据需刷新 | 跳过并显示原因 |
| 初次检查后、组件准备中出现同账号前台请求 | 后台尚未发出则取消，前台正常继续 |
| 另一个账号正在提供聊天/API 服务 | 符合条件的目标账号可独立发送；无全局 busy、断流、账号切换或出口重建 |
| 顺序处理 A/B、目标账号被删除或认证代际变化 | 不串号，不回退主账号；不满足条件直接结束 |
| 添加多个时刻、删除时刻、重复输入同一时刻并刷新 | 时间列表正确保存、排序去重，下一次时间正确；各时刻独立检查满额与空闲条件 |
| 相邻时刻触发时，上次激活请求仍在途 | 后一次跳过该账号，不并发叠加发送 |
| 重复 tick、设置变更、关闭、重启及已发送后超时 | 不重复发、不补发；未知状态如实记录 |

先用隔离 fixture 验证筛选、原子准入和去重，再使用获授权的真实账号验证独立消息及窗口变化。记录调用前后的账号、目标窗口、重置时间和用量；**发送成功与已确认窗口启动分别验收**。无需为本功能做持续窗口追踪。

上一稿查阅的[OpenAI 官方额度说明](https://learn.chatgpt.com/docs/pricing#what-are-the-usage-limits-for-my-plan)描述五小时周期并要求以实际限额/重置时间为准，没有保证任意短消息必然新建完整五小时窗口。该边界保留，不扩大成额外产品逻辑。

UI 沿用第 7 节主题/视口和刷新持久化验收。性能只聚焦到点查询次数、准备耗时、临时进程/内存、其他账号 API 延迟与错误率，确认不是每账号常驻轮询或进程；相关打包、Provider/auth、CJS 检查仍按仓库规则执行。

### 11.7 范围、回滚与状态

首期不做忙碌等待、延迟补发、复杂窗口判定、按账号刷新锁重构、跨设备连接监控、模型回退连发或显式账号切换兜底。

回滚关闭本功能、停止未发任务并清理专用 worker 即可，保留账号池和执行摘要；已发送的消息及消耗无法撤回。

当前状态：用户已明确“到点满额且无连接才激活”的筛选规则，并要求支持每日多个激活时间，文档已同步更新。功能实现、真实窗口效果、启动竞态及性能均未验证；后续从最小筛选与启动准入验证开始。


## 12. CHAT-01：问题回答疑似未送达，卡片未处理且回答进入待发送区

### 用户反馈与状态

用户最新修正：在对话中回答问题后，回答好像也没有成功发送；问题卡片没有完成处理，整个回答信息被当作待发送信息暂存，提供“编辑、引导、删除”等操作。撤回先前“回答本身已成功发送”的判断，实际送达状态必须核实。

当前状态：已完成初步静态链路核对，确认代码存在只入队但调用正常返回的路径；用户当时那一条回答是否仍排队、后来送达或失败，尚无对应运行记录证明。实际发生版本、问题类型、刷新后表现和复现频率仍待核验。

建议优先级 P1：问题回答可能未及时送达，且 UI 未正确区分排队和已回答，容易阻碍任务继续或诱导重复提交。

### 预期行为

- 回答确认已投递到对应会话/运行时后（仅服务端队列接收不算），原问题卡片结束待回答状态；按现有卡片风格显示“已回答”或收起输入控件，保留必要的问答记录。
- 保留问题与答案的关联及当前任务可接收的回答路径，不作为普通聊天草稿或可编辑/引导/删除的通用队列项展示。异步问题底层允许使用普通用户消息，不能仅凭传输形式判错；应核对是否送入正在等待该答案的任务。
- 不为消除卡片而再发送一次普通消息，不清空其他真实待发送消息或用户原有草稿。
- 提交尚未确认时保留提交中状态，避免重复点击；确实失败时保留答案和明确重试入口，不能提前标记已回答。
- 刷新或重连后，已处理的问题不恢复为待回答，也不重新生成回答对应的待发送项。

### 本轮静态核对依据

- `src/composables/useDesktopState.ts` 的 `answerAsyncQuestions()` 将回答经 `buildQuestionReply()` 编码后交给 `startTurnForThread()`，未指定 steer，沿用 immediate 投递模式。
- `src/server/deliveryService.ts` 先保存投递记录，再尝试 dispatch；非 steer 且 `canStart()` 不满足时直接返回，记录仍可能处于 queued，并未调用运行时发送。
- `src/api/codexGateway.ts` 的 `startThreadTurn()` 在结果无 turnId 时返回空字符串；`startTurnForThread()` 对此刷新队列并正常返回，没有向问题卡片暴露“仅排队”的区别。
- `src/components/content/AsyncQuestionCard.vue` 在 `await props.answer()` 正常返回后设置 submitted=true；这不能证明答案已送达。该局部状态也不能单独解释用户反馈的“卡片仍未处理”，需继续核对组件更新/重挂载及 questionReply 关联。
- `src/userQuestions.ts` 明确使用带问题引用标记的普通用户消息表达异步回答。因此排查重点是投递时机、结果语义和原问题关联；不能未经核对就改为另一种阻塞问题响应协议。

以上证明“提交调用成功不等于实际发送成功”在当前源码中确实成立，不等于已复现用户当时的具体请求。后续以 delivery ID、status、turnId、运行时回执和历史中的 questionReply 交叉核对；queued 只能说明待发送，不能记作已回答。

### 拟定排查与修复步骤

1. 复现一条带唯一标记的问题与答案，记录 thread/turn/request 标识、问题类型及对应的提交确认、问题完成事件、队列变化和渲染结果。证据使用测试内容，不保存真实敏感回答。
2. 沿“问题卡片提交 → 响应请求 → 服务端确认/通知 → 客户端状态更新 → 卡片及待发送区渲染”检查。重点核对问题响应是否误用了普通发送的乐观消息/队列路径，或确认后未清理关联占位项；这些仅为排查方向，尚不是根因结论。
3. 检查 request ID 与线程/轮次关联，以及确认、问题完成通知、消息回显的乱序和重复处理，确保成功结果能正确结束原卡片。
4. 按实际根因修复最小状态流。若需清理错误暂存项，仅清理能通过原问题/响应标识可靠关联的项，不用文本相似度批量删除；先核实它是纯 UI 占位还是持久化队列记录。
5. 增加对应回归测试及手工验收步骤，记录性能证据：一次回答仅提交一次，不额外触发普通消息发送、引导、全量线程读取或重复队列刷新。

### 验收用例

| 场景 | 预期结果 |
| --- | --- |
| 提交一个问题的答案并得到成功确认 | 原卡片结束待回答，答案不进入待发送区，没有“编辑/引导/删除”队列操作 |
| 原本已有真实待发送消息和未发送草稿 | 回答后这些内容保持，不被误删或覆盖 |
| 双击提交、确认与完成通知乱序或重复到达 | 只提交一次，最终卡片状态正确，不生成重复消息 |
| 多个问题或不同线程同时存在 | 仅更新对应问题，不结束其他未回答问题 |
| 确认延迟、明确失败、提交期间断线 | 状态与真实结果一致；重连先核对结果，不盲目重发已成功答案 |
| 回答成功后刷新、切换线程再返回 | 卡片保持已处理，不复活错误暂存项 |

实际问题卡片和待发送区需要浅深主题验证；涉及发送/回复处理时按仓库 Provider/Auth 验证规则执行。完成后分别记录“回答成功”“卡片已处理”“未产生错误待发送项”的证据，不以其中一项代替其余验收。

本条已完成需求修正及静态投递链路核对，未修改代码、清理既有消息、复现发送或执行运行时测试。


## 13. CHAT-02：发送成功后用户消息未即时显示，刷新后恢复

### 用户反馈与状态

用户反馈：有时发送消息后，无法即时在对话中看到刚发送的用户消息，但消息实际已成功发送，随后能够收到回复；刷新页面后，刚发送的消息才显示出来。

当前状态：Bug 已登记，待复现定位。成功发送、收到回复及刷新可恢复是用户观察，本轮尚未取得对应请求和运行时证据；实际版本、频率及触发条件待记录。与 CHAT-01 的问题回答投递异常分开跟踪，不先假定共用根因。

建议优先级 P1：实时消息列表漏显已发送内容，影响对话上下文判断，并可能诱导重复发送。刷新可恢复是排查线索，不代表修复完成。

### 预期行为

- 普通消息提交后及时显示对应用户消息；提交中、排队、失败和已送达状态按真实投递结果区分，不把乐观显示当作发送成功证据。
- 已确认送达的用户消息在收到助手回复时仍可见，不能因清理乐观占位或合并通知短暂消失，也不能只能刷新后看到。
- 运行时正式消息与乐观消息按稳定投递/消息标识合并，最终只保留一条；刷新前后正文、附件、顺序和所属线程一致。
- 正在查看较早历史时保留用户滚动位置，并提供现有的新消息提示；不要把“不在当前视口”误判为消息未进入列表，也不为解决漏显强制滚动所有场景。

### 拟定排查与修复步骤

1. 用唯一文本标记记录提交前、提交确认后、助手首条回复到达后、刷新后的消息列表；同时记录线程、delivery/clientUserMessageId、turnId、消息 ID 和事件顺序，区分真实列表缺项与滚动/虚拟列表可见性问题。
2. 检查“乐观消息插入 → 投递确认 → 通知同步 → 持久化历史合并 → 乐观项清理”链路，重点关注正式用户消息尚未到达时是否提前删除占位项，以及迟到历史快照是否覆盖较新本地消息。以上仅是排查方向，不是已确认根因。
3. 比较用户消息事件与助手回复事件的处理，核对乱序、重复、缺失后补偿、线程切换及组件重挂载；确认 reply 先到时用户消息仍能正确保留和补全。
4. 按实际问题修复状态合并或渲染，不用再次发送消息、强制整页刷新或持续全量读取历史作为补救。关联及去重不只比较正文，避免相同文本的两次独立发送被误合并。
5. 补充针对性回归和真实页面验收，分别证明消息已送达、实时列表可见、最终只有一条；检查修复与 CHAT-01 的投递状态处理是否相互影响。

### 验收用例

| 场景 | 预期结果 |
| --- | --- |
| 普通文本成功发送并开始收到回复 | 无需刷新即可看到对应用户消息，收到回复时消息不消失 |
| 正式用户消息事件晚于投递确认或助手首段回复 | 用户消息保留，迟到事件正确合并，不重复或错序 |
| 历史快照延迟、通知重复、短暂断线重连 | 较旧快照不吞掉已发送消息，恢复后内容和条数一致 |
| 连续发送相同文本、快速发送多条 | 按独立投递标识保留每条真实消息，不误去重 |
| 带图片/文件发送、队列消息实际出队 | 正文与附件在正确轮次显示，只有确认出队送达才按已发送呈现 |
| 切换线程再返回、刷新页面 | 刷新前后内容、顺序和条数一致，不串线程 |
| 浏览较早历史时发送或接收消息 | 新消息确实进入列表，滚动策略符合原交互，不强制跳动掩盖问题 |
| 发送失败或结果未知 | 状态如实显示并保留可恢复内容，不误标成功、不自动重复发送 |

UI 验证覆盖实际对话行的浅深主题及移动端。性能审计记录每次发送/首段回复的通知与历史请求次数、合并耗时及相关载荷；不得引入重复轮询、无界列表拷贝或每个流式片段全量读取历史。涉及发送/回复处理时按仓库 Provider/Auth 工作流验证；若改动消息解析，按规则补充 TestChat 验证。

当前仅登记需求和验收计划，未修改代码、复现发送或执行测试。修复提交应独立；回滚仅撤回对应消息状态/渲染变更，不删除真实对话历史或待发送内容。
