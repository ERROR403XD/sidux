# CodexApp 0.2 系列代码审查与开发路线图

> 进入 0.2 的封测基线已在 [0021 最终封版](20260906-0021-codexapp-0.1.90白屏修复与最终封版.md) 固定。Goal/compact、自动化执行和本轮 UI 修复已经属于 0.1.90；PWA 错误首页缓存污染与跨版本 HTTP 缓存白屏均已关闭。后续路线图仅推进尚未完成的优化，保留各小版本独立实施方案与授权边界。

> 最新进度：用户已授权在 59001 开启 0.2.0。模型能力、兼容快照与轻量工具摘要已实施，范围、验证证据和交接见 [0023 模型能力实施与验收](20260906-0023-codexapp-0.2.0模型能力实施与验收.md)。下方审查表保留当时基线，不能据此判断当前生产版本或把已关闭问题重新列为待修。

## 1. 规划结论

0.2 应围绕“更可靠、更流畅、能完整呈现新版 Codex 的工作过程”展开。先解决新版协议已经进入运行时、界面却仍按旧假设处理的问题，再逐步接入目标模式、原生历史分页、任务引用和扩展状态。

建议首批推进 0.2.0 模型能力与兼容底座、0.2.1 异步提问与等待状态、0.2.2 长会话与搜索性能。它们的收益覆盖日常使用，且是后续新特性的前提。0.2.3 以后按真实反馈调整，不把整张路线图视为一次性实施授权。

0.1.90 的自动化和命令选择器已完成候选验证；封测修订又补齐 22 项内置命令、原生 Goal 管理与压缩入口，见 [0014 封测反馈修订](20260906-0014-codexapp-0.1.90封测反馈修订与命令目录.md)。后续 [0015 目标入口与自动化修订](20260906-0015-codexapp-0.1.90目标入口与自动化封测修订.md) 已补齐 Goal 常驻卡片、侧栏标记、自动化模型/强度配置与弹窗统一。0.2 规划继续维护，具体实现从验收后的 0.1.90 基线分支推进。避免两条分支同时改写同一份队列或消息状态。

沿用用户最新要求：59001 尽量在内部完成测试。使用候选内部目录、fixture 与独立状态，不新增 Vault/NAS 业务挂载；真实模型验证也使用虚构数据。原生产日历任务的路径及自然执行结果在上线后单独验收。

方法数量不能换算成“支持率”：其中包含弃用/兼容接口、实验接口和不适合本机的远端功能。支持一种能力必须同时核实协议、请求构造、状态归一化、UI 和刷新恢复。

本轮协议命令在独立临时 CODEX_HOME 中运行，只生成文件，不登录、不启动会话、不升级 CLI：

~~~bash
CODEX_HOME=/tmp/codexapp-0190-plan-review/isolated-home codex app-server generate-json-schema --out /tmp/codexapp-0190-plan-review/schema-stable
CODEX_HOME=/tmp/codexapp-0190-plan-review/isolated-home codex app-server generate-json-schema --experimental --out /tmp/codexapp-0190-plan-review/schema-experimental
~~~

两次均成功；CLI 提示拒绝在 /tmp 下建立 PATH alias，不影响 schema 文件生成。关键能力已摘录到同目录 evidence/codex-cli-0.153.4-capability-snapshot.json，便于后续对照；完整临时 schema 不作为持久接口保证。

### 3.2 0.1.90 实施后的实测补充

以下为 2026-09-06 的新增事实，不改写原 0.1.89 审查基线；完整材料见 [0013 实施结果与封测交接](20260906-0013-codexapp-0.1.90实施结果与封测交接.md)。本轮没有实施 0.2 功能。

- 自动化已补齐常驻调度、运行关联和轻量历史，三次内部真实模型运行通过；0.2 不再将这些列为未实现功能。Docker CLI 固定 0.153.4，原生终端编译依赖也已补齐。
- 新斜杠搜索 100/1000 条候选的浏览器过滤与更新 p95 为 1.3/1.4 ms，逐键 API 为 0，最多渲染 12 行。无需先为选择器引入远端搜索服务。
- 4173 有效首屏采样中 thread/list=1、skills/list=1，但 rateLimits=2、provider-models=2、prompts=2；provider-models 最慢 1003.6 ms。应将重复获取与缓存失效的测量、合并放入 0.2.0 的能力缓存工作，不宣称本次已全部消除首屏重复请求。
- 59001 的真实内部验收线程加载：resume=1、全文 read=0、列表=1，总 API 64.8 KB，profiler warnings 为空；单次 resume 1159.2 ms。这个短线程结果不能代替 0.2.2 的长历史分页压力测试。
- 主 JS 从 535209 增至 545658 字节，新增自动化历史为懒加载块；构建仍提示主块超过 500 KB。0.2.2 按实际首次加载、切换和长线程画像优化，避免仅按源码行数大拆分。
- 物理手机软键盘、真实中文输入法、PWA 旧标签页恢复仍需人工长期反馈，继续归入 0.2.8；本次模拟 IME 与视口截图不取代真机验收。

封测修订补充：0.1.90 已实现 Goal 的原生保存、暂停/继续、清除、用量状态，以及默认 M、显式 M/B 预算；原生压缩已在内部真实线程验证。忙碌输入固定排队，编辑后仍排队，显式引导立即发送，旧模式设置移除。执行历史改为长期归档、预览 5 条、每页 100 条。1 万条归档的 100 条分页平均耗时分布 P95 为 3.67 ms；命令搜索 100/1000 技能 P95 为 2.4/2.6 ms、逐键请求为 0。修订后 59001 短线程采样 resume=1、全文 read=0、总 API 64.1 KB、warnings 为空；4173 首页仍有 rateLimits=2、provider-models=2。0.2 继续处理这些已有性能债务与复杂状态，不重复建设已经交付的入口。

### 4.2 暂不进入必做清单

| 方向 | 暂缓原因 | 后续判断条件 |
| --- | --- | --- |
| 实时语音全双工 / realtime | 当前已有 dictation；实时音频还涉及权限、音频生命周期、网络和移动浏览器，不是小改 | 文本体验稳定，且出现明确日常需求后独立试验 |

| 原生 project/environment 全量迁移 | 本机仍标 experimental；已有项目路径/标签系统刚稳定 | 先验证迁移、引用和回滚，收益足以覆盖状态迁移风险 |
| 实验性新上下文管理 | 0.153 配置默认关闭，模型/账号/后端有适用限制 | 有对应 fixture、刷新一致性证据并可回退后单独试用 |
| /recap 自动回顾 | 官方 TUI 有功能；本轮 schema 未确认独立 recap RPC | 确认公开稳定接口或明确采用应用自有总结，再排期 |
| 插件分享、远端控制、云端基础设施 | 与当前单用户家庭服务器主用法关系较弱 | 明确需求再做，不能因接口出现在 schema 就全部接入 |
| Vim 全套编辑模式 | 对本用户中文、移动使用的收益低于 IME/焦点/草稿恢复 | 获得明确使用反馈 |
| 自动账号故障转移、全仓重构 | 扩大运行风险且偏离既有边界 | 独立立项，不塞进体验小版本 |

## 5. 建议小版本安排

评分：实用价值与难度均为 1–5，5 最高；“工作量”为有效开发/验证工作日的粗估，不含等待真实账号、自然定时或长期使用反馈。后续拆分可调整版本号。

| 版本 | 用户可见结果 | 价值 | 难度 | 工作量 | 依赖 / 主要风险 |
| --- | --- | ---: | ---: | --- | --- |
| 0.2.0 | 新模型的推理强度/Fast 正确显示，模型切换不悄悄丢参数；显示应用与 CLI 版本、实际能力 | 5 | 2 | 2–4 日 | 0.1.90 稳定；旧类型多处枚举须一致修改 |
| 0.2.1 | 边工作边提问，回答卡片清楚，普通输入不被误当成回答；审批/恢复原因可理解 | 5 | 3 | 3–5 日 | 0.2.0；实时与刷新两条数据路径一致 |
| 0.2.2 | 长会话按需加载更快，搜索结果不陈旧，历史分支减少中间操作 | 5 | 4 | 4–6 日 | 0.2.0；原生分页兼容旧线程和附件 |
| 0.2.3 | 断线/刷新后发送和队列状态可信，结果不明的消息先核对再重发 | 5 | 4 | 4–6 日 | 0.2.1/2；原生队列可选，稳定自建适配保留 |
| 0.2.4 | Goal 阻塞原因、预算边界与子任务用量；完整压缩进度和错误反馈 | 4 | 3 | 3–5 日 | 0.1.90 已有 Goal/compact 入口、常驻卡片和侧栏标记；依赖 0.2.0/1/3 |
| 0.2.5 | 子任务进展可折叠查看，相关任务可搜索引用，切换后返回主任务 | 4 | 4 | 4–6 日 | 0.2.2/4；避免全量订阅和多任务状态串线 |
| 0.2.6 | 插件/技能/MCP 的安装、连接与实际可用状态清楚，当前项目目录切换后及时刷新 | 4 | 3 | 3–5 日 | 0.2.0/1；尊重已有插件体系，不新建市场 |
| 0.2.7 | 看得到 Hooks 的开始/结果/耗时，以及 Codex 后台终端的状态和输出 | 3 | 3 | 3–5 日 | 0.2.1/3/6；先可观察，再讨论配置编辑 |
| 0.2.8 | 手机键盘、焦点、草稿、复制和发布后旧页面恢复进一步收敛 | 4 | 2 | 2–4 日 | 随前述版本反馈排序；已有 UI 不能重复立项 |
| 0.2.9 | 0.2 系列候选收口，跨功能长会话/升级/回滚验证与使用文档完整 | 5 | 3 | 3–5 日 | 前述已选范围；以完整体验验收而非接口数量验收 |

这些版本不要求十个全部完成才有价值。首批三版验收后复盘，决定是否优先做队列、Goal 或插件；后续版本允许删减。若某实验接口不稳定，取消该接口迁移但保留当前版本的用户体验目标。

### 5.1 0.2.0：模型能力与兼容底座

交付动态推理强度、service tier、输入能力和模型默认值；能力缓存以 CLI 版本、实际 provider/账号上下文和目录变更为失效条件。型号显示不能依赖型号正则，客户端支持度也不能仅看方法目录。

具体更新控制在使用到的协议类型和适配器，不一次替换全部历史兼容层。未知通知保留受限诊断信息，有意义的新消息至少显示可折叠摘要；不要把未经支持的原始 JSON 大包暴露在日常聊天中。

验收：标准/自定义 provider、不同模型和旧配置值，切换/刷新后发出的真实参数一致；模型不公布的强度不强行展示；认证/配置变化只刷新相关缓存。当前 GPT-5.6/Astra 的速度能力有官方依据，但具体可选项以模型目录和账号返回为准，不硬编码定价。[Speed 文档](https://learn.chatgpt.com/docs/agent-configuration/speed)

### 5.2 0.2.1：提问与等待状态

区分阻塞问题、异步问题、审批与凭据恢复。对 isBlocking=false 的问题保持正文输入可用；agentMessage.questions/delivery 的结构化问题显示选项和自由回答，默认选中不自动提交。

回答明确绑定 question/item/turn，避免把所有普通消息猜成回答；刷新后恢复待答或已答状态。保留现有 MCP elicitation 和权限批准功能，补较新载荷与拒绝原因、重试入口，不默认扩大权限。

验收：边运行边提问、多个问题、回答后继续、跳过不答、切换线程、刷新、旧版阻塞问题、输入法。既有 approval UI 不得被新问题层盖住或错误清空。

### 5.3 0.2.2：历史、搜索与分支

优先原生 turns/items 游标分页，并保留旧版本/不支持分页线程的受限 fallback；消息顺序、展开位置、图片路径和技能引用在加载旧页后仍正确。从历史响应分支使用真实 turn ID，避免完整复制后回滚。

搜索先修“新消息、重命名、归档后索引陈旧”，再评估原生搜索替换。列明标题/正文搜索覆盖范围，不对只覆盖最近线程的结果暗示全局完整搜索。

验收：10/100/1000 turn 虚构长线程、连续新消息和旧历史交替、图片与文件链接；采集初次加载、旧页加载、切换线程、搜索取消的请求次数/字节/耗时。性能收益目标在第一次有效 profiler 基线后设定，不能预先宣称快了几倍。

### 5.4 0.2.3：可靠发送与队列

将已发送、待发送、等待确认是否送达、执行中、失败做清楚区分。重连先核对 clientUserMessageId/turn 状态；不确定投递不能自动重放可能已执行的任务。

原生 thread/queue 先在隔离环境验证。若通过，分线程选择一种队列实现；不同时双写；明确旧队列迁移和版本回退。0.1.90 的自动化运行 ID 通过适配器衔接，保持同一个任务的运行记录连续。

验收：断网前后响应丢失、后台刷新、多标签页、取消、队列编辑/重排、模型变更和账号切换；只验证可实现的去重语义，不承诺所有外部工具都有 exactly-once。

### 5.5 0.2.4：Goal 与长任务

0.1.90 已交付目标弹窗、暂停/恢复、编辑、清除、M/B 预算和实际用量状态，并补齐输入框＋入口、会话常驻卡片、侧栏标记与刷新恢复。0.2.4 在此基础上完善阻塞原因、预算到达和复杂状态反馈，完善重新连接和跨重启的状态恢复，并核对多代理子任务的用量归属。继续区分暂停 Goal 和中止当前 turn。

继续复用 0.1.90 的 /goal 与 /compact 命令。已有上下文用量显示继续使用，增加完整的压缩开始/完成与错误呈现；不把实验性上下文管理开关默认打开。

验收：用户新建目标、跨重启、完成/阻塞、预算变更、手动聊天 steer、子任务用量归属；清除目标不删除会话。[Long-running work](https://learn.chatgpt.com/docs/long-running-work)

### 5.6 0.2.5–0.2.8：逐步完善工作过程和日常使用

- 0.2.5：优先子任务身份、状态、简短输出和跳转，其次任务搜索引用；跨任务关联采用本地协议验证过的输入形状。子任务可能独立耗费资源，不把“更多子任务”本身作为优化指标。[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- 0.2.6：沿用基础 plugin 安装体系，改善 cwd 感知、刷新和错误状态，区分“已安装”“已启用”“已连接”“本线程可调用”。官方插件体系可含技能和连接器，实际宿主支持范围不同。[Plugins](https://learn.chatgpt.com/docs/plugins)
- 0.2.7：Hooks 先只读展示事件、耗时与简短输出，点击查看详细结果；后台终端优先精确区分本应用 xterm 会话和 Codex 启动的进程。编辑 Hooks 或停止进程是独立明确操作。[Hooks](https://learn.chatgpt.com/docs/hooks)
- 0.2.8：根据真实使用反馈补复制代码块/响应、草稿恢复、移动软键盘、页面焦点、主题、错误重试及旧页面更新。Service Worker 采用版本和失败恢复证据评估，不能把未复现白屏当成已知根因。

### 5.7 0.2.9：收口

选择已经稳定的特性形成封测范围，完成长会话、多账号、自动化、任务/工具状态、移动端和升级回退的联合验收。实验功能默认按能力隐藏或清楚标注，兼容旧线程，不迁移认证数据。

## 6. 性能与工程约束

每个行为版本都要报告一项以上与改动直接相关的性能证据，文档修改本身无需性能测试：

| 场景 | 要测什么 | 防止什么 |
| --- | --- | --- |
| 首屏 / 路由 | 当前线程和空首页的请求数、重复数、总字节、可交互时间 | 重复 model/list、重复目录扫描、懒加载失效 |
| 流式渲染 | 长文本连续 delta 的合并次数、主线程长任务、滚动位置 | 每个 token 重读全历史、全树重渲染 |
| 历史与搜索 | 不同线程规模、冷/热缓存、更新后搜索、取消过期请求 | 整体 JSONL 反复解析、陈旧索引、无界全量列表 |
| 原生队列 / 自动化 | RPC 次数、重试次数、到期延迟、重复运行标识 | 每线程高频全文读取、重启后任务风暴 |
| Git / 终端 | 100/1000 未跟踪文件并发峰值；输出持续流量 | 无界 Promise.all、子进程爆发、累积输出过大 |
| 插件 / MCP | 按需列表次数、目录切换时失效、失败加载时间 | 多处重复扫描、安装/启用后仍用旧缓存 |
| 内存 / 缓存 | 线程切换与订阅释放、缓存条目和大小上限 | 持久订阅、旧快照、无限日志积累 |

有效 profiler 使用当前代码、隔离状态和正确的 4173 服务，先确认监听 PID/cwd，复用兼容 node_modules，不触碰 5173。检查 duplicateCounts、warnings、totalApiKB、topApiSummary、slowestApiRows；旧 worktree、错误页、零 API 或无限 Loading 的报告作废。

代码拆分随场景进行：先能力目录/命令，接着 pending requests、history/queue，最后工具事件和目录。每个拆分只追求明确依赖和局部测试；保持 live 与 persisted 的数据契约共用，不新建重复状态中心。

包/运行模块更改先 build，再跑实际 CJS 公共依赖入口与 CLI 加载检查；涉及 provider/auth/chat 路径按仓库规定做隔离打包 Docker 验证。UI 变更覆盖浅深主题；聊天解析、文件/浏览链接必须做 TestChat。

## 7. 版本治理与完成定义

1. 每个小版本先更新真实 CLI 稳定版与能力快照，引用明确日期；固定候选镜像中的 CLI 版本，不自动升级生产。未来新版本不得直接套用本轮 0.153.4 的结论。
2. 每个小版本单独写范围和验收；按离散任务本地提交。只有明确请求才 push/PR/发布，GitHub 合并遵循项目规则。
3. 同时保留“当前稳定版 / 候选版 / 已准备待激活 release”三种状态；已有账号池、active 和会话在升级及回滚中保持。
4. 一项能力完成需要真实请求、实际 UI、刷新恢复、失败路径、性能证据和回滚说明；schema 中有名字不等于已完成。
5. 测试记录区分：本轮已验证、代码推断、隔离验证、真实账号待验收、自然任务待观察。不用旧测试数量为新代码背书。
6. 0.1.90 的调度补齐属于运行行为变化；0.2 自建队列迁移前复核其并发、持久化和发布 drain，不能认为两个阶段完全无耦合。
