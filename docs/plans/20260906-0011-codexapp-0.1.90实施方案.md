# CodexApp 0.1.90 实施方案

## 1. 目标与版本边界

0.1.89 作为当前稳定版；0.1.90 作为 0.1 系列收口的封测版本，只交付两项用户功能：真正可执行的自动化任务，以及不干扰正常输入的斜杠命令选择器。0.2 系列另按路线图逐项立项。

本方案已获用户确认并实施。0.1.90 候选已在 59001 完成内部验证，5900 仍为 0.1.89。下文“基线/当前实现”保留方案制定时的审查事实；最终实现、测试结果、范围调整和交接见 [0013 实施结果与封测交接](20260906-0013-codexapp-0.1.90实施结果与封测交接.md)。

**用户补充边界：59001 不需要访问外部路径，尽量在内部完成测试。** 本方案据此采用容器内部目录和虚构数据，不新增 Vault/NAS 或真实日历挂载，不复制真实日记。当前 /home/Code 的既有开发挂载不扩展为业务数据测试入口。

自动化补齐涉及常驻调度、后台发起 turn 和文件写入，会改变运行行为，不能按纯 UI 小改跳过可靠性验收。范围仍保持集中，不引入外部调度平台、自动账号轮换或通用工作流引擎。

### 3.2 实现程度与缺口

| 链路 | 当前实现 | 0.1.90 处理 |
| --- | --- | --- |
| 项目 cron 创建、修改、删除、列表 | 已有；支持 multi-cwd 保留其他关联 | 沿用并补调度校验 |
| 线程 heartbeat 创建、修改、删除 | 已有；同线程可有多项 | 沿用 |
| 线程“立即运行” | 已有；向持久队列加入 heartbeat，再安排 drain | 复用执行链，增加运行关联和真实状态 |
| 项目“立即运行” | 没有路由和执行流程 | 新增，共用自动执行入口 |
| RRULE 定时触发 | 当前应用源码没有该执行循环 | 增加服务端调度器 |
| 下一次执行时间 | 解析及保存均置 null | 后端计算具体时间和时区 |
| 运行结果 | 手动 API 只返回 queued:true | 区分入队、执行、成功、失败、等待和中断 |
| 失败处理 | 通用队列异常恢复消息并约 5 秒重试；没有自动化专属上限 | 自动化运行改为分类、有限重试和结果核对 |
| 重启 / 重复触发 | 通用队列可恢复，但没有计划时点唯一键 | 持久化运行记录及领取状态 |
| 可读日志 | 没有独立自动化运行记录 | 最小记录必做，详情列表建议做 |
| 候选实际文件访问 | Vault 不在容器内 | 保持此边界；内部 fixture 模拟日记与日历结构 |

依据：src/server/codexAppServerBridge.ts 中 parseAutomationToml（约 4849 行）、任务读写（4988–5228）、buildHeartbeatQueuedMessage（5580）、BackendQueueProcessor（约 6880）、共享桥接初始化（7270）和自动化 HTTP 路由（9296–9468）；前端 AutomationsPanel.vue、SidebarThreadTree.vue；wiki 的 project-cron-automations 与 thread-heartbeat-automations。

结论：当前版本没有完成“保存计划 → 定时触发 → 执行 → 可核对结果”的闭环，这是该任务不能按时运行的明确实现缺口。当前文件时间和旧排查也没有提供成功证据；本轮没有逐条重放历史日志，因此不进一步断言历史上绝无人工执行。

## 4. 自动化设计

### 4.1 最小架构

~~~text
automation.toml + 应用侧计划元数据
          ↓ 读取、校验、计算到期时间
一个常驻 AutomationScheduler
          ↓ 持久化领取计划时点
AutomationRunner ← 项目/线程“立即运行”
          ↓ 项目创建运行线程；heartbeat 排入目标线程
现有 app-server / turn 执行链
          ↓ turn/item/approval 事件 + 重启后结果核对
运行记录 → 自动化列表状态 → 打开执行会话
~~~

调度器由共享 bridge 生命周期管理，服务启动时运行，不依赖网页打开或某次 GET。热重载、dispose、候选重建和服务退出必须释放定时器及订阅。使用 CODEX_HOME 范围的单实例锁，第二个调度实例不能领取任务；不做分布式调度。

沿用现有定义目录；新增调度、运行和存储小模块，不继续把完整实现塞进约 9580 行的 bridge。自动化经专用适配层接入通用队列，不改写所有普通聊天的调度语义。

### 4.2 时间语义

| 项目 | 建议默认值与规则 |
| --- | --- |
| 时区 | 新任务默认服务器检测的 IANA 时区并明确显示；本机及旧“整理日历”明确为 Asia/Shanghai |
| 旧任务兼容 | 读取已有 TOML，保留 ID、prompt、cwds、额外字段；不覆盖其他任务或 memory.md |
| 元数据 | 应用自有目录保存 timezone、稳定 dtstart、规则版本、调度游标；避免要求旧程序理解新增 TOML 字段 |
| 规则支持 | 使用成熟 RRULE 库；先验证现有 MINUTELY/HOURLY/DAILY/WEEKLY 与 INTERVAL/BYDAY/BYHOUR/BYMINUTE 组合；其他合法规则只有通过支持测试才接受，不支持时显示明确错误 |
| 解析 | 当前按行手写 TOML 解析需补兼容测试；多行 prompt、数组、未知字段必须可保留。无效定义在 UI 中显示问题，不能静默消失 |
| 初次接管旧任务 | 记录首次启用时点，从下一个未来计划开始；不回补几周前从未调度过的任务 |
| 已接管任务停机恢复 | 24 小时内最多补最近一个漏跑时点；更旧记录为 missed，显示可手动补跑，不连续追赶 |
| 暂停 / 删除 / 修改规则 | 暂停停止未来触发，删除取消未派发运行；已运行 turn 不被隐式杀死。修改产生新规则版本，废止尚未派发的旧时点 |
| 时钟变化 | 根据绝对 UTC 时点重算；防回拨重复，验证 DST 的跳过/重复时刻与所选库语义 |

正常运行中每个时点都需可追溯。高频任务上次未结束时不堆积无限新 turn；最多保留一个待执行时点，其余记为合并/跳过。默认同时执行 1 个自动化运行，手动和定时共用互斥；不限制用户正常聊天。多个 cwd 按各自执行目标分别计状态，按有限并发执行；总状态不得掩盖部分失败。

### 4.3 运行与可靠性

1. 项目任务每次建立独立运行线程，名称包含任务名与计划日期；cwd 使用真实绝对目录，沿用已激活账号和明确记录的模型配置。新线程读取项目 AGENTS.md 与可用技能，不复制任意旧对话历史。heartbeat 保持在原线程排队，不打断正在进行的工作。
2. 计划运行使用 automationId、规则版本、target、scheduledAt 的唯一键。手动运行使用客户端 requestId 防双击重发；对已经结束的计划，明确的“重试”建立新 attempt 并关联原记录。
3. 先以原子写入保存 queued 运行，再派发；关联 queueMessageId、threadId、turnId。在“上游已收到 turn/start、客户端还没收到响应”时先对账，不直接重发。单实例锁和原子领取解决本机重复领取，不承诺对任意外部操作实现分布式 exactly-once。
4. 通知到达时持久化状态。收到 turn/start 的响应只代表已启动；仅 turn/completed 且无错误才标记执行完成。等待 approval 或用户回答标为 waiting_input，不能标成成功，也不自动替用户批准。
5. 明确区分认证无效、cwd 不存在、NFS 不可达、规则错误、模型/工具不可用、暂时网络错误和执行失败。只对确定未提交的短暂失败退避重试，最多 3 次；凭据和业务错误等待修复。不通过换账号、换 provider 或改权限偷偷绕过失败。
6. 重启后读取非终态运行并核对真实线程；能恢复的继续跟踪，无法确认是否产生副作用的标为 interrupted/需检查。超时先请求中止并核对状态；建议默认运行上限 60 分钟、作为高级配置可调整，等待处理的任务明确显示占用原因。
7. 后台任务也纳入账号切换和 release 空闲检查。生产交接需要先进入 scheduler drain：停止领取新计划，待已运行任务结束后停止服务。避免“检查时空闲，停止前又触发”的竞态。

运行记录字段至少包括 runId、automationId、target、trigger、scheduledAt、timezone、startedAt、finishedAt、status、attempt、threadId、turnId、简短错误码和摘要。prompt/日记全文仍保留在任务或执行线程，不复制到运行列表；凭据永不进入日志。

### 4.4 执行日志的取舍

**推荐实现轻量执行记录及最近运行列表。** 它复用调度器必须保存的状态，增量开发量相对较小，无需另建日志平台。

- 列表显示最近结果、下一次运行和时区；详情显示最近 20 次，支持分页到更早记录。
- 每项显示开始时间、耗时、状态、简短原因和“打开会话”；失败项可按明确语义重试。
- 默认每任务保留最近 100 条已结束运行且不超过 30 天；当前运行不清除。旧数据清理在任务完成或低频维护时进行。
- 如果独立详情列表导致工期显著增加，可后移；最小持久记录、最近状态、错误原因和执行会话链接仍属于正确性验收，不能仅依赖易丢失的控制台输出。
- 本版不做全文日志搜索、无限滚动终端日志、日志导出或外部推送。

建议页面：

~~~text
整理日历                        已启用
每周一 01:00 · Asia/Shanghai
下次运行  09-07 01:00       [立即运行] [编辑]
最近运行  完成 · 42 秒      [打开会话]
─────────────────────────────────────
时间             触发方式    结果       耗时
09-07 01:00      定时        完成       42 秒
09-06 14:20      手动        路径不可用  —
~~~

时间和结果为设计示例，不是本轮实际执行证据。

### 4.5 “日记 → 日历”的业务验收

调度执行完成不等于日历整理正确。59001 使用容器内部完整文件链验收，原任务的真实路径和自然周任务结果留到生产交接后核对：

1. 以 scheduledAt 在 Asia/Shanghai 的日期推导上一完整周，采用左闭右开边界：上一周一 00:00 到本周一 00:00。比如计划 2026-09-07 01:00，读取 2026-08-31 至 2026-09-06；即使补跑也不把“过去一周”漂移到执行当天。
2. 在 /test-workspace/automation-0190 建立虚构日记、跨月日期、现有日历事件和测试 AGENTS.md。该目录使用候选独立 named volume，验证重建后保留；不映射宿主业务目录。任务 prompt 和 cwd 都指向内部路径。
3. 采用可判定的样本：明确的重要事件、普通日常、日期不确定、重复事件、空周；检查只选规定时间内事件，保留现有 front matter 和日记链接，不把不确定日期补成确定日期，不把没有重要事件误判为失败。
4. 先用 mock/虚拟时钟覆盖精确边界，再通过候选已激活账号运行真实 Codex turn，读写上述虚构文件；另做无浏览器打开时的短间隔自然触发。真实模型请求不等于需要真实个人数据或外部文件路径。
5. 同一周重跑验证去重，保留样本中的人工条目。输出列出新建/更新/跳过路径，核对文件真实存在、日期字段和日记双链。按日期、来源与事件内容判断重复，不能只看标题或调度唯一键。
6. 路径不存在、只读目录、临时不可达等失败在容器内部模拟；不操作 NFS 挂载、不故意破坏真实路径。清理仅删除本轮 fixture/测试任务和对应测试 volume，保留原候选认证 volume。
7. 生产原任务保持不动，不在 59001 创建指向真实 Vault 的任务。0.1.90 生产交接后，按原宿主路径核对依赖并观察至少一次自然到期任务及实际日历文件；有真实写入时先限定该周与日历文件的备份/回滚范围。
8. 候选通过时准确报告“内部端到端、真实模型及短间隔调度验证通过；原生产周任务待上线后验收”。不把内部样本、mock 或 HTTP 200 当成原日历任务已成功。生产验收属于交接后的阶段，不作为要求 59001 新增外部路径的理由。

## 5. 斜杠选择器设计

### 5.1 输入规则

| 情况 | 行为 |
| --- | --- |
| 光标前在行首或空白后输入 / | 打开浮层，焦点始终留在 textarea |
| 继续输入命令名、中文名称或描述关键词 | 本地即时过滤；不增加另一个搜索输入框 |
| 初次打开 / 每次查询变化 | 不主动高亮命令，防回车误选 |
| 按 ↓ / ↑ | 显式进入候选选择，首个 ↓ 选第一项，首个 ↑ 选最后一项，之后循环 |
| 有键盘选中项时按普通 Enter | 确认候选；拦截本次发送 |
| 没有显式选中项时按 Enter | 沿用发送/换行设置，即使文本恰好为 /plan 也不强制执行命令 |
| 点击候选 | 确认该候选；单纯鼠标悬停不改变键盘选择状态 |
| Esc / 点击外部 | 关闭浮层，完整保留原文字；当前 token 在继续输入时不立即重新弹出 |
| Shift+Enter、Ctrl/Cmd+Enter、Tab | 保留现有换行/发送/焦点习惯，修饰键 Enter 不被浮层冒领；Tab 不自动补全 |
| 无结果 | 轻量显示“无匹配命令，可继续输入”，不截获上下键与 Enter |
| 中文输入法正在组合 | 不开关或确认候选、不发送；先处理 composition 状态和 keyCode 229 兼容 |
| 粘贴长文本 | 不因粘贴内容包含 / 自动抢开；后续用户在有效 token 位置主动输入仍可搜索 |
| URL、路径、日期、代码和普通斜杠 | https://、foo/bar、2026/09/06、/mnt/a、代码区等保持文字；出现第二个路径分隔符关闭候选 |
| @ 文件选择、模型/技能菜单、展开编辑器 | 同时只展示一个主动候选菜单；保留已有附件、选区、滚动和焦点行为 |

触发基于光标附近 token，不扫描全部历史或改变整段草稿。对于单段绝对路径 /tmp，与命令形式天然相似，允许短暂显示无选中提示；路径文字和发送结果必须不变，不尝试“智能纠正”。

### 5.2 UI

浮层贴合输入框左边缘，默认在输入区上方，和输入框间隔约 8 px；桌面宽约 380 px，移动端不超出内容区。默认最多显示 6 行，剩余内部滚动；高度不超过可视区域约 40%，在展开编辑器或软键盘出现时按实际可视空间翻转/收缩。

每项由命令名、简短中文描述和必要的来源标记组成。浅色采用现有白色表面和细边框；深色使用现有深色 token，关键覆盖写入 src/style.css。保持现有圆角、间距、文字和图标，不增加遮罩、全屏搜索页或新工具栏。

~~~text
┌─────────────────────────────────────┐
│ 命令                                │
│ /plan       切换到计划模式           │
│ /default    切换到默认模式           │
│ /model      选择模型与推理强度       │
│ /skills     选择本次使用的技能       │
~~~

采用 textarea combobox/listbox 语义，aria-expanded、aria-controls、aria-activedescendant 与实际选择状态一致；触摸点击保留输入焦点。颜色之外用背景和选中标记表达当前候选。

### 5.3 首版命令范围与执行语义

不直接把未知 /xxx 字符串交给 app-server，假定它会执行 CLI TUI 命令。采用很小的命令注册表，连接本应用确实已有的操作。

| 命令 | 描述 | 选择后 |
| --- | --- | --- |
| /plan | 切换到计划模式 | 复用当前上下文模式切换；不发送草稿 |
| /default | 切换到默认模式 | 同上 |
| /model | 选择模型与推理强度 | 打开现有自定义模型菜单，沿用当前能力限制 |
| /skills | 选择本次使用的技能 | 打开既有技能菜单 |
| /prompts:名称 | 插入已保存提示词 | 在当前 token 位置替换为对应内容，等待用户发送 |
| /技能名 | 使用已启用技能 | 沿用现有 skill attachment 的真实名称/路径，不自动发送 |

内置动作、技能和提示词使用稳定的分类 ID；同名技能显示来源，冲突时不覆盖。搜索覆盖命令名、别名和描述，结果优先精确、前缀，再描述匹配；不增加模糊搜索服务或搜索依赖。

对打开后还需选择的菜单，在完成选择前保留原 token，取消则恢复原草稿；确认后仅移除触发 token，保留其前后文字、附件和光标位置。模式切换成功后直接消费 token，失败保留原文及可理解原因。提示词替换和技能附加都不触发发送。

二级菜单打开期间用户若继续修改草稿，则取消过期的待选择上下文；不得用旧的光标下标替换已经变化的文字。

/goal、/recap、/compact 等没有完整现有 UI 操作链的能力留给 0.2；不为了凑齐官方命令列表扩大封测范围。若今后增加自动识别“手打完整命令并回车”，必须单独讨论，因为这会改变本方案的字面文本保留约定。

官方斜杠命令体现了持续过滤和技能/提示词入口，但可用命令随环境不同；本方案的默认不选中和字面发送是按用户要求制定的产品选择。[官方 Slash commands](https://learn.chatgpt.com/docs/reference/slash-commands)

### 5.4 代码落点

建议新增 composerCommands.ts、useComposerCommandPicker.ts 和 ComposerCommandPicker.vue，分别负责目录、输入状态与浮层；ThreadComposer.vue 只接入现有输入/快捷键链，App.vue/useDesktopState 复用现有动作。不要直接复用会把焦点移入独立搜索框的 ComposerSearchDropdown。

保持数据按需加载：内置命令纯本地；技能和提示词复用现有请求及缓存，目录/cwd 改变后失效。逐字输入不发 HTTP，不重新读取技能文件。

方案制定时只做文档审查，188 项通过是 0.1.89 的历史基线。实施后为 27 个文件、225 项单测通过，并完成浏览器、内部真实模型、调度和性能验证；详见 0013，不能将本节的原计划视为所有项目都已实测。

后续 UI 实施涉及新浮层、浅深主题和响应式，按项目规则做真实 UI 检查。浏览器自动化使用隔离 CODEX_HOME 的当前 4173 验证服务，不触碰 5173；需要改 page context、断网或 API stub 时使用 Playwright CJS。报告实际 URL、视口、断言及截图绝对路径，保存至 output/playwright；最终 59001 再核对构建资源与真实输入流程。若涉及会话 Markdown/链接渲染变更，补强制 TestChat 的 hrefOk/titleOk/textOk。

调度器采用一个到期计时器和最多 60 秒一次的定义元数据校对；无修改不重复解析所有文件、不扫描历史线程。UI 历史按页读取，页面关闭停止刷新；优先复用现有事件通道。性能报告列明 duplicateCounts、warnings、totalApiKB、topApiSummary、slowestApiRows，不能用 HTTP 200 或旧 trace 代替。

容器启动脚本目前固定 Codex 0.147.0，与真实 0.153.4 不一致。P0 将候选配方显式固定到已核实版本并验证平台二进制，避免依靠启动时在线自升级；修改启动/运行模块时按 AGENTS.md 的 Provider/Auth Docker Workflow 做隔离打包测试，并记录唯一 localhost 端口、重载后错误保留及重复 live overlay 数量。具体端口实施时先查监听再分配，5900 不作故障测试。

## 8. 回滚与生产交接

1. 候选失败时仅停止新候选并回退到保留的 0.1.89 镜像；沿用原候选 volume，不用旧快照覆盖正常轮换后的认证。
2. 自动化自有元数据和运行记录向后兼容；回退代码前停止 scheduler、核对正在执行的 turn，必要时只恢复本轮自动化相关文件。普通聊天、skills、memories、项目及账号不在恢复范围。
3. 候选业务回滚仅覆盖内部 fixture 和测试任务。生产交接后的首次日历执行另留目标文件备份；如需恢复，逐项检查运行后用户修改，仅处理该次日历产物，日记和其他日历不动。
4. 生产使用现有 prepare → 结束当前 turn → 独立终端 activate 流程。0.1.90 的 release 开关需增加 scheduler drain 协调，防止后台任务在空闲检查后新启动；激活前保证只有一个实例负责真实任务。
5. 0.1.90 回退到 0.1.89 会恢复稳定交互，但自动定时执行会停止，应明确显示/记录这一限制，不留下“旧版继续有调度”的假象。

## 9. 确认范围与交接摘要

确认本方案即按 P0–P4 开始隔离实施，含轻量运行记录和建议的最近运行列表、所列斜杠输入契约、容器内虚构数据的完整测试；随后准备 P5 封测交接。59001 不新增外部业务路径，不访问真实日记或写入真实日历；生产 activate 和原任务验收仍安排在当前 turn 结束后的独立终端交接及上线后阶段。
