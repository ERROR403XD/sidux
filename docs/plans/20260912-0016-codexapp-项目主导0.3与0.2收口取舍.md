# 项目主导 0.3 与 0.2 收口取舍

用户已明确：0.3 将大幅重构为项目主导的 UI，替换当前以原生 Codex 风格侧边栏组织项目和会话的方式。沿用此前“一个项目在一段时间主要通过一个会话推进”的使用习惯，重点是活跃项目、当前主会话与回到工作的路径；具体 A/B/C 布局、首页默认落点及字段尚未确定。

用户随后补充：0.2 已足够好用，0.3 不保证成功，可能长期继续使用 0.2；希望留下稳健版本，同时尽量减少修改。这是本页最终取舍的优先条件，不能用“很快会被 0.3 替代”来降低 0.2 的验收要求。

## 建议结论

**建议以已验收的 0.2.19 作为长期稳定版候选，停止新增功能与结构性整改；优先补充稳定性验证、固定可复装产物和恢复验证，只有明确必要且能独立验证的局部修复才改业务代码。0.3 独立推进，不承担兜底责任。**

前端 MOD-01 的必要部分与项目数据加载方式应直接纳入 0.3；SCH-03、SEC-01、DATA-01 属于被新 UI 继续使用的后端或安全/数据能力，界面替换不会自动消除它们，但它们也不都是工作台第一版的前置条件。

这调整了[上一轮成本评估](20260912-0015-codexapp-剩余系统审阅项开发成本评估.md)中“先做局部模块抽取、SCH-03、PERF-01”的推荐顺序。那一组合可作为独立后端治理批次，**不应作为开始项目 UI 前必须投入 10–18 人日的门槛**。完整六模块拆分的 15–25 人日同样不应再作为新 UI 之外的一份必做账单；两者应按实际保留/替换边界统一规划，不能把两个上界直接相加。

## 对当前与 0.3 的影响

影响等级区分现有体验、触发后后果和开发风险，不代表已测得生产故障概率。依据来自当前源码、已有故障探针与验收记录；本轮没有注入真实账号挂死或进行新的浏览器测试。

| 项目 | 对当前 0.2 的影响 | 对项目主导 0.3 的影响 | 是否值得继续投入 0.2 |
| --- | --- | --- | --- |
| SCH-03 账号准备无总期限 | **触发后影响高，实际发生率未知。** 准备不返回会占名额，极端情况下四槽全占并拖住停止；已有模拟探针证明缺保底，未据此证明当前生产正在反复发生 | **UI 实施关联低，执行可靠性关联高。** 复用原后端就会继承。项目变多不必然增加并发；若以后增加多项目后台自动化或无人值守，重要性上升 | 列为唯一优先深入核对的条件性功能修复。先用隔离探针检查生产适配器的取消/回收边界；能证明只影响本次准备才进入稳定版。实际出现长时间 starting 或停止受阻时提高优先级，不能用强杀共享进程换取表面恢复 |
| SEC-01 主动预览有同源管理权限 | **已证实的条件性安全风险。** 打开不可信/生成 HTML 等主动文件可能访问管理接口；无证据表明发生过实际攻击。家庭内网并不消除这个来源边界 | **基本项目导航关联低；成果内嵌/自动预览关联高。** 界面重构不修复底层文件来源问题；若新工作台增加更频繁、更自动的预览，暴露机会会扩大 | 长期使用会延长风险暴露时间，但原有“核心功能优先，可接受部分不安全”的取舍仍适用。无兼容性损失的局部隔离经验证后可考虑；不为此重做全局认证/端口架构。扩大内嵌自动预览前应解决隔离 |
| MOD-01 大模块与职责耦合 | **直接体验影响低，维护影响高。** 文件大不等于运行慢，但定位和验证改动成本高 | **前端部分影响很高。** App/useDesktopState/Sidebar 中的导航与状态正是新 UI 要改的区域，直接叠新布局容易重复订阅、状态错归属、切项目丢草稿。服务端大模块不因换 UI 消失，但不要求同步全面拆分 | 不值得先完整整理旧侧栏再重写。抽出要保留的会话/项目状态与行为，随 0.3 边实现边拆；放弃的旧展示结构不再精修 |
| PERF-01 局部重复读取 | **当前实测影响低。** 最近样本仅确认续跑标记与待处理请求各两次，部分刷新可能有必要；不能据此认定全系统性能无问题 | **数据设计影响中高，可在首版避免。** 项目卡片若逐个加载会话正文、Git、额度与历史，会放大请求；项目概览应使用轻量摘要、共享订阅和按需分页 | 不值得专门为旧首页少量请求延长版本。保留测量基线，在新工作台重新检查调用来源；不趁机合并跨账号敏感缓存 |
| DATA-01 自动化冷历史与防重索引增长 | **当前该项容量压力低，有本次元数据核对支持。** 生产自动化 state.json 约 12 KB，冷历史与 history-keys 尚无积累；不代表全部会话数据很小 | **长期影响中，基础工作台影响低。** 原自动化历史继续增长；若首页做跨项目运行历史/统计，首次索引和分页成本会更明显。新项目元数据与自动化执行历史应分开 | 当前不清理、不迁移；长期保留容量检查办法与防重契约。若实际增长成为瓶颈，0.2 也应能独立获得容量维护，不能假定届时已经换到 0.3 |

## 哪些工作会保留价值，哪些容易返工

| 范围 | 0.3 的处理方式 |
| --- | --- |
| 原侧栏树的布局、排序控件与导航容器 | 按新项目工作台重新设计；旧展示代码可逐步替换，不需要先完整整理 |
| 会话状态、草稿、未读、审批、运行通知 | 抽为稳定的共享状态与操作接口；项目切换仍通过真实 threadId 定位，不能因视图卸载丢失或重复处理 |
| 消息渲染、输入框、终端、diff、账号/API 与自动化页面 | 优先保留已验收能力，再调整接入位置；不因导航重构同时重写执行协议 |
| 账号协调、执行归属、额度准入、API 流与发送去重 | 沿用后端契约；前端项目模型不新增全局账号锁、不改变默认/固定出口规则 |
| SCH-03、SEC-01、DATA-01 的正确后端修复 | 可跨 UI 版本复用，具有长期价值；是否放入 0.2 取决于眼前实际问题和可隔离程度 |
| 旧首页请求合并与将被替换组件的缓存 | 只保留可证明通用的逻辑；新 UI 应根据自己的生命周期重新测量 |

“一个项目一个当前主会话”只定义默认继续入口。查看历史不应自动更换主会话；搁置项目只改变活跃列表，不应顺带停止执行、删除历史或切换全局账号。已有固定会话/出口仍按原账号归属工作，默认选择仍按现有准入规则处理。

## 0.3 首版真正需要先明确的边界

1. **项目身份与主会话关系。** 明确稳定 ID、目录/worktree 关系、主会话删除后的恢复；新增少量项目元数据，不把 UI 活跃状态混入自动化执行台账。
2. **视图与运行状态生命周期。** 新工作台离开/返回、切项目、刷新时，草稿、焦点、阅读位置、未读和审批归属正确；通知订阅与后台运行不随卡片重复创建。
3. **列表只取摘要。** 活跃项目页面使用项目元数据、主会话标题与现有可验证状态；打开项目后再加载正文、历史和 Git。项目数量增加时不自动创建更多执行 worker。
4. **保留全局可见的运行与待处理入口。** 项目被搁置、主会话被更换，也能找到该处理的审批与后台任务；活动意图、运行状态、未读状态分开。
5. **新旧入口兼容。** 旧会话链接能继续定位，原账号/API/自动化功能可访问；用真实切换路径验证，不以静态卡片截图作为完成。

这些是前端 MOD-01 和 PERF-01 在新产品结构中的必要部分。SCH-03 不是画面和导航接入的统一前置；SEC-01 与是否扩大主动预览相关；DATA-01 的完整清理与基础项目入口无直接依赖。

## 0.2 长期稳定版的最小收口方案

### 先做验证，业务代码变更默认不增加

已有 753 项回归、实际包安装、锁文件复装和 PTY 验收作为基础。长期保留还值得补的是持续运行、重连与恢复、账号/出口竞争边界的验收证据；不是把全部 P2/P3 整改都做一遍。这些验证只在隔离候选或用户日常自然使用中观察，不通过干扰生产任务制造故障。

具体边界：默认账号切换与固定出口相互独立，A 账号异常不堵 B，同会话冲突仍被拒绝，激活向正常工作让出；服务重启后的任务恢复、未知结果不重发；浏览器刷新/断线不重复投递、不丢草稿；正常部署失败后的恢复。应覆盖“该放行的仍放行”和“该挡住的仍挡住”，不能以全部阻塞来证明没有重复。

本轮没有补做上述运行验收，也没有据已有测试数量宣称长期稳定性已经证明。后续若验证通过，允许以零新增业务修改结束本批；若出现确定问题，再对该问题做最小修复。

### SCH-03：单独验证可处理边界，不许简化成危险补丁

可先投入上一轮估算中的 0.5–1 人日，检查从引擎到真实 adapter 的准备等待、取消、迟到副作用及共享资源归属。只有明确可以限制在本次准备的修复才进入 0.2；若必须大改共享 worker 生命周期或全局调度，不把完整 4–8 人日工程强塞进稳定版。

若保留风险，必须说明它仍可能占槽/拖住停止；可复用现有诊断记录等待阶段，并保留恢复步骤。增加诊断不能算完成自动恢复，安全恢复也不能预设立即强制重启正在工作的服务。

### SEC-01：有限且明确的安全取舍

保留旧版并不使已证实的来源风险消失。用户接受一定程度不安全，允许本轮暂不更改预览能力和认证架构。只有通过相对资源、编辑、登录及管理/API 回归的局部隔离才考虑进入稳定版；若做不到，就如实保留风险，不宣传“加了 header 就安全”。本轮不新增复杂权限弹窗或默认关闭既有功能。

### MOD-01 / PERF-01 / DATA-01：退出常规收口范围

大模块治理、旧侧栏整理、收益不明确的请求/缓存优化、历史迁移不进入 0.2 稳定版。保留当前正常工作实现。DATA-01 当前量小，长期按实际增长处理，保留防重信息；无需为未来容量可能性先运行清理任务。

### 固定产物和后续维护

保留已验证源码提交、准备包、部署锁文件、代理组件版本和独立恢复步骤；开发目录继续变化时，长期运行目标不应依赖一份随构建被覆盖的 dist。是否切换到精确准备目录、何时切换生产，需要另行按既有发布流程安排；本评估不执行切换。

0.2 后续维护仅针对实际阻断、错账号/重复发送/数据损坏、明显的兼容故障或使用方式变化后不可接受的安全风险。0.3 中形成的局部修复，只有依赖少且对旧版独立验证后才回补。长期稳定意味着持续保留可维护与可恢复能力，不意味着一律永不修改，也不意味着继续加入新功能。

本评估不授权自动切换生产或启动全面重构。本轮仅更新规划文档与元数据层面的只读核对，未改运行代码、配置、账号状态或用户历史。
