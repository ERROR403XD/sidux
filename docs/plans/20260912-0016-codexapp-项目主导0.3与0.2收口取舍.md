# 项目主导 0.3 与 0.2 收口取舍

用户已明确：0.3 将大幅重构为项目主导的 UI，替换当前以原生 Codex 风格侧边栏组织项目和会话的方式。沿用此前“一个项目在一段时间主要通过一个会话推进”的使用习惯，重点是活跃项目、当前主会话与回到工作的路径；具体 A/B/C 布局、首页默认落点及字段尚未确定。

用户随后明确：0.2 已足够好用，0.3 不保证成功，可能长期继续使用 0.2；希望留下稳健版本。“尽量减少修改”指的是**定型后少返工、少补丁、避免三天两头重构**，并非这轮尽量少改代码。允许本轮集中完成必要的长期稳定性治理。这是本页最终取舍的优先条件，不能用“很快会被 0.3 替代”或“当前尚未发生”替代生命周期评估。

## 建议结论

**建议以已验收的 0.2.19 为基础，集中完成有限范围的长期稳定性收口，再冻结 0.2 的核心接口、执行语义和数据契约。范围以减少未来返工为目标，允许为明确问题做必要的定点结构调整；不开展六个大模块的全面重构。0.3 独立推进，不承担兜底责任，也不持续向 0.2 回补结构改动。**

前端 MOD-01 的必要部分与项目数据加载方式应直接纳入 0.3；SCH-03、SEC-01、DATA-01 属于被新 UI 继续使用的后端或安全/数据能力，界面替换不会自动消除它们，但它们也不都是工作台第一版的前置条件。

这调整了[上一轮成本评估](20260912-0015-codexapp-剩余系统审阅项开发成本评估.md)中“先做局部模块抽取、SCH-03、PERF-01”的推荐顺序。那一组合可作为独立后端治理批次，**不应作为开始项目 UI 前必须投入 10–18 人日的门槛**。完整六模块拆分的 15–25 人日同样不应再作为新 UI 之外的一份必做账单；两者应按实际保留/替换边界统一规划，不能把两个上界直接相加。

## 对当前与 0.3 的影响

影响等级区分现有体验、触发后后果和开发风险，不代表已测得生产故障概率。依据来自当前源码、已有故障探针与验收记录；本轮没有注入真实账号挂死或进行新的浏览器测试。

| 项目 | 对当前 0.2 的影响 | 对项目主导 0.3 的影响 | 是否值得继续投入 0.2 |
| --- | --- | --- | --- |
| SCH-03 账号准备无总期限 | **触发后影响高，实际发生率未知。** 准备不返回会占名额，极端情况下四槽全占并拖住停止；已有模拟探针证明缺保底，未据此证明当前生产正在反复发生 | **UI 实施关联低，执行可靠性关联高。** 复用原后端就会继承。项目变多不必然增加并发；若以后增加多项目后台自动化或无人值守，重要性上升 | 建议在本次集中收口中优先处理。先验证真实适配器的取消/回收边界，再完成必要的执行所有权与迟到结果防护；不要求先发生生产故障。必须保留已有会话与出口行为，不能用强杀共享进程换取表面恢复 |
| SEC-01 主动预览有同源管理权限 | **已证实的条件性安全风险。** 打开不可信/生成 HTML 等主动文件可能访问管理接口；无证据表明发生过实际攻击。家庭内网并不消除这个来源边界 | **基本项目导航关联低；成果内嵌/自动预览关联高。** 界面重构不修复底层文件来源问题；若新工作台增加更频繁、更自动的预览，暴露机会会扩大 | 本轮一次明确长期预览边界，优先完成兼容的独立隔离；若无法保持必要功能，可按既有风险取舍保留并明确记录。避免后续不断叠加临时 header、权限例外或全局认证限制；扩大自动预览前应解决隔离 |
| MOD-01 大模块与职责耦合 | **直接体验影响低，维护影响高。** 文件大不等于运行慢，但定位和验证改动成本高 | **前端部分影响很高。** App/useDesktopState/Sidebar 中的导航与状态正是新 UI 要改的区域，直接叠新布局容易重复订阅、状态错归属、切项目丢草稿。服务端大模块不因换 UI 消失，但不要求同步全面拆分 | 不做全量整理；本轮只为 SCH-03、数据生命周期等确定问题抽取必要接口、固定资源归属。0.2 的现有 UI 保留，0.3 所需前端重组在独立分支进行 |
| PERF-01 局部重复读取 | **当前实测影响低。** 最近样本仅确认续跑标记与待处理请求各两次，部分刷新可能有必要；不能据此认定全系统性能无问题 | **数据设计影响中高，可在首版避免。** 项目卡片若逐个加载会话正文、Git、额度与历史，会放大请求；项目概览应使用轻量摘要、共享订阅和按需分页 | 本轮一次核对和定型：确有冗余的低风险请求合并，必要的重连/状态同步保留并写明原因。之后不做反复微调，不引入跨账号敏感缓存框架 |
| DATA-01 自动化冷历史与防重索引增长 | **当前该项容量压力低，有本次元数据核对支持。** 生产自动化 state.json 约 12 KB，冷历史与 history-keys 尚无积累；不代表全部会话数据很小 | **长期影响中，基础工作台影响低。** 原自动化历史继续增长；若首页做跨项目运行历史/统计，首次索引和分页成本会更明显。新项目元数据与自动化执行历史应分开 | 本轮确定长期归档、索引与防重契约，必要的分段与兼容读取一起实现，利用冷历史尚无积累的阶段降低未来迁移成本。无需引入自动删除或全面更换数据库，也不能删掉防重证据 |

## 哪些工作会保留价值，哪些容易返工

| 范围 | 0.3 的处理方式 |
| --- | --- |
| 原侧栏树的布局、排序控件与导航容器 | 按新项目工作台重新设计；旧展示代码可逐步替换，不需要先完整整理 |
| 会话状态、草稿、未读、审批、运行通知 | 抽为稳定的共享状态与操作接口；项目切换仍通过真实 threadId 定位，不能因视图卸载丢失或重复处理 |
| 消息渲染、输入框、终端、diff、账号/API 与自动化页面 | 优先保留已验收能力，再调整接入位置；不因导航重构同时重写执行协议 |
| 账号协调、执行归属、额度准入、API 流与发送去重 | 沿用后端契约；前端项目模型不新增全局账号锁、不改变默认/固定出口规则 |
| SCH-03、SEC-01、DATA-01 的正确后端修复 | 可跨 UI 版本复用，具有长期价值；是否放入 0.2 取决于眼前实际问题和可隔离程度 |
| 旧首页请求合并与将被替换组件的缓存 | 只保留可证明通用的逻辑；新 UI 应根据自己的生命周期重新测量 |

“一个项目一个当前主会话”只定义默认继续入口。查看历史不应自动更换主会话；搁置项目只改变活跃列表，不应顺带停止执行、删除历史或切换全局账号。已有固定会话/出口仍按原账号归属工作，默认选择仍按现有准入规则处理。

## 0.3 首版真正需要先明确的边界

1. **项目身份与主会话关系。** 明确稳定 ID、目录/worktree 关系、主会话删除后的恢复；新增少量项目元数据，不把 UI 活跃状态混入自动化执行台账。
2. **视图与运行状态生命周期。** 新工作台离开/返回、切项目、刷新时，草稿、焦点、阅读位置、未读和审批归属正确；通知订阅与后台运行不随卡片重复创建。
3. **列表只取摘要。** 活跃项目页面使用项目元数据、主会话标题与现有可验证状态；打开项目后再加载正文、历史和 Git。项目数量增加时不自动创建更多执行 worker。
4. **保留全局可见的运行与待处理入口。** 项目被搁置、主会话被更换，也能找到该处理的审批与后台任务；活动意图、运行状态、未读状态分开。
5. **新旧入口兼容。** 旧会话链接能继续定位，原账号/API/自动化功能可访问；用真实切换路径验证，不以静态卡片截图作为完成。

这些是前端 MOD-01 和 PERF-01 在新产品结构中的必要部分。SCH-03 不是画面和导航接入的统一前置；SEC-01 与是否扩大主动预览相关；DATA-01 的完整清理与基础项目入口无直接依赖。

## 0.2 长期定型的集中收口方案

### 本轮允许必要投入，定型后减少变动

目标是冻结后长期使用的版本，不是让当前 diff 尽可能小，也不是把审阅清单每一项都做到最复杂。每项代码调整必须回答：消除什么长期失效模式、稳定哪个契约、如何证明无关账号与出口仍正常、如何回退。对已能工作且不会妨碍上述目标的模块，不因规模或风格而重构。

建议本批聚焦：SCH-03 的准备退出与回收；SEC-01 的长期预览边界；DATA-01 的稳定归档/索引与防重策略；少量 PERF-01 请求取舍。MOD-01 仅作为这些明确问题所需的局部结构手段，不另开全面拆分工程。具体设计与实施范围尚待细化，本轮没有开始代码修改。

### SCH-03：优先在定型前完成正确治理

先以隔离探针确认真实 adapter 的等待阶段、可取消性和资源归属；随后贯通总期限、取消、执行代次及迟到资源清理。允许为此抽取准备生命周期或资源所有权接口，但不改变账号选择、全局准入、既有四槽与会话 worker 复用契约。

不能只套外层超时或提前释放名额；不能关闭共享进程来制造“第五条能跑”的表面通过。若底层能力确实不支持所需保证，应明确列出无法满足的部分和替代恢复边界，再调整方案，不能以诊断提示冒充自动恢复。此前 4–8 人日为规划估算，原型发现更深依赖时需重估。

### SEC-01：一次确定预览策略

优先做与管理来源隔离、同时保留必要预览/编辑能力的完整局部方案，并验证正常管理/API 通路。用户已接受一定程度不安全，若所需隔离明显破坏现有工作流，允许明确保留特定风险；关键是给出固定且可解释的边界，避免定型后零碎堆叠 header、例外和权限开关。

此项有独立安全价值，不依赖 0.3 是否成功；也不借机把可信内网应用整体改造成另一套认证体系。

### DATA-01：先把长期格式和恢复边界定稳

当前冷历史尚无积累，有条件在本轮减少未来大数据量迁移风险。确定并实现必要的分段归档/索引、旧格式兼容、可中断恢复与防重查询；不为追求固定空间而删除仍需永久防重的证据，不引入自动删用户历史或全面更换数据库。

不同生命周期的数据分开：展示/分页索引可以优化，原运行记录与防重事实按既有契约保留。冻结数据格式前必须覆盖归档中断、旧请求重放、索引缺失/损坏、重启和旧布局读取，避免后续不断修补数据迁移。

### PERF-01 与 MOD-01：范围一次限定

PERF-01 只解决已证实的重复请求和失效问题；若第二次读取是正常同步，就保留并记录，不制造新缓存框架。MOD-01 只做上述治理所需的边界整理；旧侧栏与 App 的产品结构保持稳定，0.3 在另一条开发线上重新组织。

### 用验收和固定产物结束收口

已有 753 项回归、实际包安装、锁文件复装和 PTY 验收作为基础。新增治理分别验证后，再做一次组合验收与持续使用观察：默认账号切换与固定出口隔离、A 异常不堵 B、同会话冲突、正常工作抢先于激活、未知结果不重发、浏览器重连/草稿保留、进程重启恢复、部署失败恢复。只在隔离实例做故障注入，不中断生产任务。

保留精确源码提交、准备包、部署锁、代理组件版本和恢复步骤，长期服务指向固定构建产物；0.3 开发不覆盖其运行目录或数据契约。当前评估没有实际执行上述新验收或切换。

定型后不再接受常规结构重构、样式翻新、性能微调或对齐 0.3 的架构变更。仅对明确严重缺陷、必要兼容和不可接受的安全问题做独立维护；不能承诺软件从此永不需要修复，但应显著减少因边界未定、反复迁移和结构摇摆造成的修改。

本评估不授权自动切换生产或启动全面重构。本轮仅更新规划文档与元数据层面的只读核对，未改运行代码、配置、账号状态或用户历史。
