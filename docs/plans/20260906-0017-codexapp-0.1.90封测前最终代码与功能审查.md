## 2. 按优先级列出的发现

优先级口径：P1 为容易造成消息丢失、运行中断，应在冻结前处理；P2 为功能缺口或受条件限制的错误，应修复或明确纳入后续范围。这里没有把未接入的每个 CLI 方法都列成缺陷。

### R01 · P1 · 刷新账号列表会清空服务器队列

- **触发**：当前存在排队消息，用户刷新账号列表。`App.vue:2688` 调用 `stopPolling()` 再 `startPolling()`；该刷新没有要求队列为空。
- **问题**：`useDesktopState.ts:5603–5605` 把 `queuedMessagesByThreadId` 设为空对象，并调用 `persistQueueState()`。后者通过 PUT 将空对象写回服务器，删除已保存的队列。
- **影响**：本来只想刷新账号信息，却取消了所有尚未发出的排队消息，且没有取消确认或提示。相同清理函数也用于登录完成、移除账号及组件卸载；不能因此声称每次浏览器刷新都会触发 Vue 卸载，需要分别验证触发条件。
- **证据**：入口调用链已核对；提取真实后端写入函数，在内存文件夹具中验证空 PUT 删除 `thread-queue-state`。没有操作真实账号来复现。
- **来源**：原始基线已存在这段清理逻辑，属于继承问题。
- **建议**：把停止订阅与删除用户队列分开。停止订阅只清理临时状态，恢复连接时重新读取队列；只有明确的取消动作可以删除消息。
- **验收**：有排队消息时刷新账号列表，确认消息 ID、顺序和后端内容不变；之后能正常发送一次。

### R02 · P1 · 队列整份覆盖会丢失或重新加入消息

- **触发**：两个浏览器页面从相同旧快照分别修改队列，或者前端旧快照与后端出队交错。
- **问题**：`useDesktopState.ts:4200` 每次提交整个 `threadId -> messages[]`；`codexGateway.ts:2712` 使用 PUT；`codexAppServerBridge.ts:5348` 忽略锁内读取到的当前队列，直接替换为客户端提交的快照。写锁能串行写文件，不能合并不同客户端的过期状态。
- **复现**：用真实归一化和持久化函数，依次保存 A 页面 `{thread-a:[a]}`、B 页面 `{thread-b:[b]}`，最终只剩 `thread-b`，A 的消息丢失。夹具中的读写全部在内存完成。
- **其他影响**：若后端已取走某条消息，前端旧快照再提交可能把它重新放入队列。这一后果来自同一替换语义，本轮没有在真实模型上制造重复执行。
- **来源**：原有队列设计；0.1.90 固定默认排队后，这条路径更常被使用。
- **建议**：改为按消息 ID 的增删改、排序操作，或加入版本号并拒绝过期快照；以服务器为队列权威，失败时保留草稿并显示错误，避免 `best-effort` 静默吞掉保存失败。
- **验收**：两个页面交错添加/编辑/删除不同线程的消息都保留；后端出队与前端排序交错时，已发送 ID 不复活；仍满足“编辑后继续排队，只有显式引导立即发送”。

### R03 · P1 · 59001 更新脚本在构建成功前移除旧容器

- **位置**：`scripts/run-multi-account-dev.sh:14–45`。
- **问题一**：先执行 `docker stop`、`docker rm`，再 `pnpm build`、打包及 `docker build`。任一步构建失败都会留下没有服务的 59001。
- **问题二**：替换前只查看自动化 `activeCount/queuedCount`，没有检查普通会话活动、普通消息队列和待审批请求。如果运行状态接口失败或格式不含 `activeCount`，还会跳过该检查。
- **复现**：执行原脚本，但将 `docker/curl/lsof/pnpm` 全部替换为本地桩；模拟构建以 42 退出，调用顺序确定为 inspect → stop → rm → build。没有执行真实 Docker 写操作。
- **来源**：开发环境部署流程遗留；0.1.90 增加了自动化保护，普通会话保护和构建顺序仍未补齐。
- **建议**：新镜像先构建成功；替换前读取完整、最新的空闲状态，检查失败则终止；保留旧镜像和恢复命令，再执行有界切换。正式发布脚本已有更完整的空闲检查，可复用其规则。
- **验收**：构建失败时旧候选仍可访问；普通 turn、队列或待审批非空时禁止替换；状态读取失败也保持旧实例。

### R04 · P2 · 新自动化消息不再显示“自动化发送”标识

- **位置**：`automationEngine.ts:278`、`normalizers/v2.ts:108/174/429`、`ThreadConversation.vue:266`。
- **问题**：调度器发送 `[CodexApp automation run:<runId>]` 和时间上下文；归一化器只识别旧 `<heartbeat>` 信封，因此新消息的 `isAutomationRun=false`，也无法生成 `automationDisplayName`。
- **复现**：同一真实归一化函数输入旧 XML 得到 `true`，输入当前格式得到 `false`。
- **影响**：运行会话中缺少自动化来源标识，内部运行标记也按普通提示词显示。这不表示任务没运行，也不是侧边栏绑定图标的同一个问题。
- **来源**：0.1.90 执行协议变化后，旧 UI 解析没有同步迁移。
- **建议**：增加明确的运行消息元数据/解析契约，保留旧 XML 兼容；不要仅删除运行标记，它还用于执行结果不明时的对账。
- **验收**：手动和定时运行都显示来源；刷新后仍然存在；普通文本包含相似片段时不误标；原有历史消息继续可读。

### R05 · P2 · 新版异步问题尚未完整支持

- 本机已安装 CLI 0.153.4 的既有隔离 schema 摘录包含 `agentMessage.questions/delivery` 和 `ToolRequestUserInputParams.isBlocking`；本次依据本机快照讨论，不代表所有模型一定产生这些事件。
- `normalizers/v2.ts:403–411` 和 `useDesktopState.ts:3503` 附近的实时完成处理只保留文本。夹具确认 `questions/delivery` 被丢弃，历史无法重建可选问题卡片。
- `App.vue:1040–1048` 遇到任意 selected pending request 都用请求面板替换输入框；`ThreadPendingRequestPanel.vue:371` 使用必须回答后才能继续的文案，没有区分非阻塞问题。
- `automationRuntime.ts:23/64` 将同线程任何 pending request 都视为等待。实际函数夹具中，一个 `isBlocking:false` 的问题会让空闲线程的 `canStart()` 返回 false。
- **建议**：沿用 0.2 异步问题计划，区分阻塞审批、阻塞问答、非阻塞问题，保留可继续输入的入口和问题 ID；不要用一个全局“等待用户”状态承载三种语义。
- **范围说明**：现有同步审批和普通 requestUserInput 面板已经实现，不能整项列成“问答功能未实现”。

### R06 · P2 · 部分工具事件在会话历史中没有可见表示

- **位置**：`normalizers/v2.ts:402–526`、`:631–648`；所有历史读取最终使用该归一化器，见 `codexGateway.ts:806/839`。
- **复现**：给真实归一化器分别输入 `mcpToolCall`、`dynamicToolCall`、`collabAgentToolCall`、`subAgentActivity`、`webSearch`、`contextCompaction` 的类型夹具，每个得到 0 条消息。当前实时处理也没有对应的完整专用卡片。
- **影响**：这些执行过程无法通过历史消息查看，刷新后也不能恢复；CLI 原始存储未因此被删除。文本回答、命令执行、已完成文件变更、计划、图片仍有实际支持。
- **建议**：先提供轻量的未知类型摘要/折叠原始信息，再按实用价值增加工具结果和子任务卡片；实时与历史共用事件映射。`reasoning` 的历史隐藏应另作产品决定，不直接等同于未知事件丢弃。
- **来源**：原始版本已有有限类型映射，新 CLI 类型增多后缺口扩大。属于 0.2 工具可观测性方向。

### R07 · P2 · 模型能力仍由固定枚举和名称规则决定

- `codexGateway.ts:2113–2134` 读取 `model/list` 后只保存 ID，丢弃模型的推理强度、默认值、服务档位等信息。
- `ThreadComposer.vue:739` 的 Fast 开关仅匹配 GPT-5.4/5.5；`useDesktopState.ts:94`、`automationOptions.ts` 和服务器归一化器限定六个推理强度。
- 本机 schema 已把 ReasoningEffort 定义为非空字符串，模型目录有 `supportedReasoningEfforts/serviceTiers`。前端尚不能自然承接新目录值。
- **影响**：可能隐藏新模型已声明的档位，或让自动化和手动会话选择不适配某模型的强度。不能仅根据模型名字断言某个 Fast/max/ultra 档位一定可用，本轮未做这样的实机推断。
- **建议**：按模型目录构造选项，保留未知合法已保存值，并展示实际执行设置；沿用 0.2.0 能力目录计划。

### R08 · P2 · PWA 导航错误会污染离线首页缓存

- **位置**：`public/sw.js:49–57`。
- **问题**：导航请求只要 fetch 返回就缓存为 `/`，没有检查 `response.ok`；HTTP 500 不会进入 catch。
- **复现**：将有效 200 首页作为初始缓存，模拟下一次网络返回 500，再模拟离线；真实 service worker 函数返回缓存的 500 错误页。
- **建议**：仅用成功响应更新外壳，明确错误返回与离线回退；另审查固定 `codexweb-shell-v2` 下历史哈希资源的清理策略。后者是代码路径上的容量风险，本轮未测长期磁盘增长。
- **范围说明**：PWA 注册、安装元数据和离线外壳已经实现；联网模型对话不等于离线可用能力，不把离线 AI 列成原有承诺。
