# 修复对账号与出口调度的影响评估

## 结论

修复[首轮审阅](20260912-0006-codexapp-0.2系统代码审阅.md)的问题，确实可能影响账号切换、账号定时激活、API、自动化出口，以及相互阻塞/放行。风险最高的是调度锁拆分、账号准备超时和激活发布门禁；大模块重构的影响范围同样很大。可以分步修复，但不能承诺只改局部函数就没有跨功能影响。

本轮核对 0.2.18 运行代码，未切换账号、发送真实模型请求、改变计划或启动生产交接。补跑 9 个相关测试文件、132 项全部通过；它们确认现有基线，不代表尚未实施的修复已经安全。源码仍为 f9a3b9494893 的运行行为，后续提交仅增加文档和审阅脚本。

## 当前有四种不同范围的限制

| 范围 | 当前作用 | 修复时不能混淆 |
| --- | --- | --- |
| 默认账号选择/凭据变更 | 短暂限制依赖当前默认身份的新提交 | 不是所有固定账号的全局停机 |
| 指定账号 | 移除、凭据版本、额度保护、该账号激活优先级 | A 的问题不能默认禁止 B；正常工作不是一账号只能做一件事 |
| 指定会话或出口 | 会话自动化占用、消息 sending/unknown、key/出口绑定、并发限制 | 同账号不同会话，与同一会话并发写入是不同问题 |
| 整个服务发布 | 应冻结所有新执行，核对所有活动后才可停止进程 | 这是全局范围；不能直接复用成日常账号切换规则 |

关键代码：`accountAuthCoordinator.ts:237-249` 分别提供广义账号操作状态、指定账号 API 准入、默认会话新提交限制。尤其 `isAccountOperationInProgress()` 包含任何账号刷新，不能代替 `blocksApiAccount(id)`，否则 B 的后台额度刷新也会堵住 A 的 API。

`getAccountSwitchSnapshot()` 与发布的 `checkIdle()` 也不是同一判断。前者有意排除自动化 worker，且会话队列主要关注 sending/unknown；后者检查整服务运行和队列。把两者统一成“任何活动都禁止”会恢复已经避免的无关阻塞。

## 当前行为与应保留的边界

以下是源码与既有测试支持的基线，不表示真实云端所有组合均已实测。

| 情形 | 当前行为/应保留规则 |
| --- | --- |
| A 有前台任务，自动化显式选择 B | B 可独立申请运行，不改默认账号或根 auth；仍受额度、并发和目标会话状态限制 |
| 默认账号切换期间，API key/出口固定到 B | 固定 B 的新请求不应仅因默认账号切换被拒绝 |
| 默认账号切换期间，API 跟随默认选择 | 新接入短暂受阻；当前代码还会中止匹配的既有连接并清除关联 continuation 归属，不是所有流都无缝保留 |
| 自动化已经取得账号，随后默认选择变化 | 已领取运行保持其账号归属；后续未领取且未显式绑定的任务按准入时规则选择，不能偷偷让已领取运行改身份 |
| 前台会话仍活跃/存在待审批或相关发送变更 | 当前账号切换检查仍可拒绝；不能把“固定 B 独立”误解成所有情况下都允许切换 |
| 正常 API/聊天/自动化使用账号 A | 可以有独立执行；仍保留会话占用、额度保护、资源池及各自并发上限，不新增账号级万能互斥锁 |
| A 正在定时激活，A 的正常工作到来 | 正常工作优先，A 激活让出；不能为了完成可选激活而堵住正常工作 |
| A 激活时 B 有工作 | 不因 B 的占用无条件取消 A；按账号判断资源冲突，仍考虑共享池容量 |
| 移除 A | 撤销 A 的 lease、连接和关联任务；不等待 A 的慢流，也不关闭 B；迟到刷新/准备不得复活 A |
| 同一会话正在执行自动化 | 继续保留对冲突 turn/start、steer、compact、goal 修改的阻止，不能因缩短锁而出现双重提交 |
| 修改一个 key 或 API 默认出口 | 只处理受影响的路由/连接，固定到其他账号的 key 流保留；它与默认账号切换、整服务发布是不同动作 |
| 正式发布交接 | 应覆盖自动化、普通会话、API、激活及其准备/收尾；现有 SCH-01 正是遗漏激活，需补全而非放松门禁 |

依据：`accountAuthCoordinator.ts:695,823,980,1018`，`codexAppServerBridge.ts:5614,6292,6494,6554`，`apiProxy/gateway.ts:124,175,200`，`accountExecution.ts:44-83`。默认账号切换对跟随 key 的影响沿 `beforeMutation → invalidateKeys → activity.abortKey` 可见；此次修复不顺带把该策略改成另一种流迁移策略。

## 每项修复的回归风险

| 修复 | 对这些功能的风险 | 可能误伤 | 控制改动范围 |
| --- | --- | --- | --- |
| SEC-01 预览权限隔离 | 低至中 | 如果把 CSP/CORS/认证限制加到整个服务，可能影响管理登录、浏览器请求或 WS | 只隔离主动文件内容；验证管理/API 和相对资源不变。若另开来源，同时验证打包/反代路径 |
| SCH-01 激活纳入发布门禁 | 高 | 把日常账号切换也变成等待所有账号；激活占用普通 API 并发；drain 失败后永久不放行 | 独立的发布冻结与活动统计；复用固定身份和激活优先级，不共用普通 API 流量名额 |
| SCH-02 慢查询移出串行队列 | 高 | 旧查询晚到覆盖已完成/已取消状态；重复释放账号或提前空出运行槽；新旧提交竞争 | 锁内领取快照、锁外查询、锁内按 runId/revision/预期状态提交；新活动优先于过期结果 |
| SCH-03 账号准备总超时 | 高 | 只结束等待却让后台继续发出任务；过早释放名额；错误关闭复用 worker，连带正常会话/API；让任务改用新默认账号 | 端到端取消、固定执行身份、明确资源所有者；清理只针对本次准备，晚到成功必须回收并禁止提交 |
| SCH-04 续跑公平轮转 | 中 | 一次放行大量会话；绕过原有队列或额度条件；与用户新消息竞争 | 只改变遍历顺序，保留每批八条、每次 tick 最多一条提交及现有投递台账 |
| RED-01 未用代码与旧模块 | 低；若按名称批删则升高 | 删除有副作用的导入、协议动态入口或仍被旧路径引用的代码 | 逐项引用/构建图确认；旧激活模块与现行 Runtime/Request 分开处理 |
| MOD-01 大模块拆分 | 高、范围广 | 生命周期重复创建，单例变多实例，重复刷新/调度；多个模块各拿一把锁但保护同一数据 | 单独进行结构重构，先保留旧入口与状态所有权；不和调度行为修复混一批 |
| PERF-01 请求合并/缓存 | 中，账号额度路径较敏感 | 不同账号共用缓存，旧额度误放行；切换后仍读旧模型/身份 | 按账号、凭据/配置版本、方法与参数隔离；只合并等价 in-flight，保留失效条件 |
| REL-01 固定依赖/最低环境 | 中、影响全运行环境 | 顺带升级 HTTP、WS、PTY 依赖改变连接行为 | 首先固定本次已验证版本，不夹带依赖升级；CLI/PTY/流/账号矩阵复验 |
| DATA-01 历史保留与索引 | 中，幂等误改时影响严重 | 删除防重索引后旧手动请求再执行；清理与调度争用存储；误删未结束记录 | 热记录、展示历史、防重标记分开；保留 tombstone，分批 I/O，不清理运行中记录 |

SCH-03 特别需要谨慎：当前 bridge 的 `call()` 将请求放进 pending 后等待回复，函数本身没有总超时。修复不能仅给外层加一个 Promise.race；“调用者已超时”不等于“账号连接已经停止准备”。

## 必须分别验证“该挡住”和“该放行”

只检查没有重复运行还不够：把全部请求拒绝也能做到“不重复”，却会破坏可用性。每个场景必须同时断言：拒绝谁、允许谁、何时恢复、真正发出了几次请求、用了哪个账号、释放了哪个资源。

| 回归组 | 该阻止 | 该放行/保持 | 必须观察 |
| --- | --- | --- | --- |
| 默认 A → B 切换 | 依赖默认身份的新接入、已有切换冲突 | 固定 C 的 API/独立自动化按既有规则继续 | activeStorageId、执行账号、根 auth 不被任务路径改写、各流关闭原因 |
| A 凭据/额度刷新 | 确有冲突的该账号凭据变更 | B 工作继续；不能因广义 refresh 状态关掉全部 API | 每账号 refresh 次数、revision、A/B 请求结果 |
| 同账号多个正常出口 | 同会话冲突、超配额/并发 | 无冲突的 API/自动化继续 | 账号选择、会话 ID、独立计数与保护值 |
| 激活与正常工作相撞 | 可选激活不得抢占正常工作 | 同账号正常工作进入；其他账号不被连带清理 | activation abort、generation 引用释放、实际发送次数 |
| 准备超时后迟到 | 超时任务不得迟到 start，不得自行换账号 | 其他任务继续；资源释放后后续任务可进入 | create/start 计数、worker 归属、是否遗留 lease/pending |
| 删除 A 与晚到回调相撞 | A 的新提交、旧 lease 和复活 | B 流/任务不中断；不等待 A 的网络结束 | account registry、credentialRevision、A/B 生命周期 |
| 慢 inspect 与完成/取消相撞 | 旧结果覆盖新终态、双重释放 | manual/通知/drain 及时处理 | 状态版本、最终 run、四槽计数 |
| 续跑第九条 | 忙碌/额度不足会话错误提交 | 尾部符合条件会话最终轮到 | 每轮检查集合、每轮最多一次提交、deliveryId 去重 |
| 修改单个 API key/默认出口 | 已失效路由继续提交 | 不受影响的 fixed-key SSE/WS 继续 | HTTP、SSE、WS 的连接和 continuation 归属 |
| 发布 drain | 所有新执行、查询失败或未知状态下切换 | 已在进行的清理可结束；失败撤销 drain 后恢复原准入 | 激活 preparing/sending/cleanup、普通活动、失败后是否仍卡 busy |
| 历史清理/依赖锁定 | 旧请求重放、未结束数据删除 | 原有账号/API/自动化行为保持 | request key、依赖版本清单、HTTP/SSE/WS/PTY smoke |

还应组合注入：在账号切换、移除、额度保护触发、服务 drain 的同一时刻，让准备成功/失败、inspect 完成、WS 新回合到来。仅按顺序点击几次无法覆盖这些竞态。

## 实施顺序与完成门槛

1. 先把上述现行规则固化为回归用例，特别是固定账号隔离与“切换账号”和“发布服务”的区别。
2. SEC-01 单独修，验证文件预览和管理来源隔离；不改账号调度。
3. SCH-01 单独补发布准入冻结/活动统计，验证失败恢复以及激活仍向正常工作让出。
4. SCH-03、SCH-02 分别做取消与状态竞争治理；每次一个可回退提交，不趁机改账号选择规则或并发数。
5. SCH-04 只修轮转公平性，保留原有提交条件。
6. 冗余、依赖锁、缓存及历史策略分别实施。大模块拆分放到行为修复稳定之后。

风险等级是根据调用链推断的工程评估，没有测得回归概率，不提供虚假的百分比。“修复通过”的标准必须包含持续放行无关工作、拒绝确有冲突的工作、失败后可恢复，而不是只看测试数量和一次成功请求。
