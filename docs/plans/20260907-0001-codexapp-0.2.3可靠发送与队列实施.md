# CodexApp 0.2.3 可靠发送与队列实施

## 基线与协议证据

0.2.2 候选已完成验收，见 0030；代码 ea3bcf1、验收提交 308db61。当前分支 feature/0.2.3-reliable-delivery。沿用 0028 的逐版连续授权，本版只更新 59001，生产 5900 仍为 0.2.0，不推送或合并。

现有应用队列先从全局 JSON 移除再发送，RPC 报错后放回并定时重试；存在结果不明时重复执行、崩溃时丢失已出队消息的路径。编辑同样先删除原条目，临时编辑状态只在内存中；引导失败也会放回队列。空闲判断每五秒读取完整历史。当前状态文件写入也不具备原子替换。

CLI 固定 0.153.4。在独立 59015 和专用卷中探测：thread/queue/add 会自行启动任务；相同 clientUserMessageId 再次提交不能作为去重保证。原生 queue/add 只有 threadId、clientUserMessageId 和 input，不能保存现有每条消息的 model/effort/serviceTier。故本版保留应用队列，不迁移到原生队列，不双写。

直接 turn/start 的 clientUserMessageId 会作为历史 userMessage.clientId 保留，userMessage.id 则是另一 ID。重复提交仍可能返回另一个 turn，不能把 client ID 视作 exactly-once API。原始探测见 output/0203/native-probe.json、delayed-id.json；均为无有效认证的虚构任务。立即中断可能来不及持久化用户项目，这种缺失不能证明请求没有被接受。

## 实施范围

1. 增加持久发送记录。每次明确发送生成稳定 ID，重试同一次请求沿用 ID；同 ID、不同内容拒绝覆盖。实际 RPC 前落盘 sending，收到 turnId 后落盘确认；不确定错误和重启遗留 sending 进入 unknown。确认记录不因队列出队而消失，并设置保留范围和过期 ID 拒绝规则，避免清理后旧请求重新执行。
2. 用历史 clientId 或已保存 turnId 核对结果，优先最近原生页面；读取范围和并发有界，无法确认保持 unknown。提供明确核对入口；不能靠相同正文、时间邻近或“当前空闲”判断已经/尚未投递。不确定条目不自动重发；已知在发送前失败的条目允许用户重试。
3. 队列待发送、编辑中、发送中、待确认、发送前失败清晰区分。发送前保留条目，确认后才移出待发送区。编辑保留原条目及位置，按版本号更新；刷新保留编辑关联，过期页面不能覆盖已发送条目。引导改为服务端同一投递流程，不先删除再发送。删除待确认记录明确表示停止跟踪，不声称中止已执行任务。
4. 发送参数按用户提交时保存，包括模型、推理等级、速度档位、协作模式和附件；排队后切换模型不改写旧条目。账号操作与待发送/待确认状态纳入现有空闲判断，投递前核对上下文，禁止悄悄换账号或供应方重放。普通空闲发送和忙时引导也使用同一发送记录，不仅修复后台队列。
5. 队列改存独立版本文件并原子替换，复用 CODEX_HOME 单写者租约；启动时只迁入旧队列一次，成功后移除旧队列字段，保留其他全局设置。数据损坏或租约未取得时停发并显示错误，不按空队列处理。降级前必须清空/处理待发送与待确认；保留新记录，旧版不会读到可能已执行的条目。
6. 自动化保留 runId 和既有运行记录归属；核对 clientId，并使用有界历史读取。自动化已有不明结果处理不改为普通队列的自动重试。删除不确定发送的自动模型 fallback 重放路径，明确失败和人工后续选择。

## 验收门槛

先完成持久状态及竞争回归，再接入桥接和界面；各子任务提交。故障测试覆盖：请求到达前断网、已接受但 HTTP 响应丢失、CLI 结果不明、发送前/后崩溃、重启核对、同 ID 并发、多页面编辑/重排/删除、后台刷新、模型及账号边界、已确认消息不再次发送。

必须区分服务器已接收、CLI 已接受、执行完成；网络错误本身不能归类为未送达。核对范围之外或旧 CLI 缺少 clientId 时保留待确认，不降级为文本猜测。

完成单测、类型检查、构建/CJS/PTY；4173 和最终 59001 浅深 UI、刷新持久化与必要的移动视口；消息字段/归一化变更按仓库规则增加 TestChat。聊天发送变化完成打包认证矩阵。性能记录每次投递/核对的 RPC 次数、无全文轮询、队列/记录大小、并发上限、取消后的后台行为；不要从工具夹具推断任意外部副作用恰好一次。

59001 替换前共同空闲检查，构建产物与运行文件逐字节核对。完成验收报告和 Obsidian 同步后进入 0.2.4；当前不把本版计为完成。

## 基础模块验证

持久存储模块提交 `023e20d`；后续投递服务增加发送前保存、原生结果核对、通知确认、同 ID 合并和全局最多 4 个投递/核对任务。22 项定向测试与类型检查通过，涵盖第二写入者、损坏文件、发布失败停发、发送期间中断、确认文件与待发送文件之间崩溃、编辑跨重启、旧队列迁移中断、过期请求、模型快照及 ID/线程隔离。

待处理记录最多 500 条、序列化内容 32 MB；确认和取消记录独立保存，7 天后可清理，过期 ID 不能在清理后再次执行。租约使用现有 CODEX_HOME 写入者机制。存储采样用本地临时目录和小型虚构正文：10/100/500 条对应 7.5/74.5/372.9 KB，快照约 0.12/0.22/1.09 ms，新增 P95 约 9.21/1.06/2.71 ms（10 条包含冷启动）。结果见 output/0203/store-performance.json；这是基础模块开销，不是候选接口或模型响应性能。

本地基础模块已单独打包为 CJS 并确认 `DeliveryStore` 导出；辅助 esbuild 命令包装异常时，使用现有依赖中的真实二进制完成打包，没有改动依赖或权限配置。基础模块测试不等同于整版验收；最终结果与边界见本文末节。


## 源码接入与候选前验证

接入提交 `b321983`、`230d8d6`。当前源码版本 0.2.3，浏览器普通发送、排队、引导均走持久记录。新浏览器请求先读取不含凭据的账号/供应方摘要，保存到每次提交；断网后重试保留原摘要，不把旧意图绑定到后来切换的账号。服务器直接 HTTP turn/start/steer 和旧队列写法不再绕过保护；Telegram 和自动化保留各自已有运行归属。

浏览器未确认记录最多 20 条，先核对写入成功再发 HTTP；HTTP 丢失后保留同一请求及 ID。服务器确认记录可用于恢复；核对成功仅清空仍与原消息一致的草稿，不清空用户后来输入的其他内容。队列编辑仍保留服务器原条目和版本；编辑关联保存在各标签页的 sessionStorage，编辑草稿使用独立键，避免另一个标签页保存后使旧编辑稿在刷新时转成普通新消息。没有更改普通草稿的全局策略。

CLI 原生探测还复现了新会话尚无 rollout 时再次 resume 失败（3 次 thread/read 均成功，resume 均报 no rollout）；修复为只对 notLoaded 会话 resume，既修复首条消息，也减少已加载会话的一次 RPC。桥接与自动化均采用此规则。原始证据 output/0203/native-preflight.json；尚不能用单测替代真实 CLI 验收。

### 真实发送与故障证据

最终 59001 的 Astra 验收会话为 `01a077d8-504b-7343-9740-719826644610`，回合 `01a077d8-53ca-7820-b077-d1e84378b648`。服务器接收约 335 ms，同 ID 重试读取确认记录约 6 ms；模型实际返回 `CODEXAPP_0203_ACCEPTED_1788717060733`。刷新后仅一条对应用户消息，队列为空，工具执行 0。它证明本次完整发送/回复链路可用，不代表所有远端副作用具备 exactly-once 语义。

独立虚构无效认证实例中，主动丢弃成功提交的 HTTP 响应体，再重启并用同 ID 请求，仍返回同一原生 turnId。另将已停止的虚构测试卷复制到新卷，构造“sending 已保存、确认文件未写入”的崩溃窗口；启动后通过最近历史的 userMessage.clientId 找回原回合，回合数前后均为 1。该窗口是受控构造的磁盘夹具；真实 HTTP 丢失和实例重启则实际发生。无效认证回合在持久化用户项目后由测试中断，不将其记作成功执行。最终这组提交约 323 ms、重启后确认读取约 5 ms。

### 性能与边界

最终浏览器采样：首页 API 90.3 KB，千回合会话 144.2 KB；thread/list、skills/list、rateLimits 各 1 次，线程页 resume 1 次且仅约 59.8 KB，带 turns 的额外 read 为 0，无重复历史请求警告，无长期 Loading threads。实际页面和截图已检查。千回合 resume 本次约 234 ms；配额读取是最慢请求（首页约 2379 ms、线程页约 956 ms）。这些是单次采样，不作为稳定 P95 或跨版速度提升的证明。

发送新增一次账号摘要 HTTP 读取；RPC 侧在保存时与投递前核对身份。已加载会话不重复 resume，闲忙判断只读取元数据；不明结果每次最多读取 50 回合，自动核对最多三次，未证实就保持 unknown。普通投递和核对共享最多 4 个工作，记录最多 500 条 / 32 MB；历史缓存与队列容量均有界，不按队列长度同时发起任意数量模型请求。确认/取消记录保留 7 天，过期 ID 清理后仍不能重新执行。内存核对计数随待处理条目移除清理。

既有 `/prompts` 首页重复请求（2 次）和外部配额读取耗时保留到 0.2.9 最终审核。文件以原子替换处理进程崩溃；没有以本次验证承诺断电事务、磁盘硬件持久性，或旧 CLI 缺少 clientId 时的精确核对。不同明确发送动作可以生成不同 ID，相同正文不作为去重依据。

### 使用与回退

普通消息照常发送。看到“提交结果待确认”时先点击“核对提交”；服务器队列出现“等待确认是否送达”时使用“核对结果”。发送前失败可重新排队；编辑会保留原队列位置和执行设置。停止跟踪不会中断已经运行的任务，后续消息可以继续发送。

降级前必须先处理待发送、编辑中与待确认记录，并确认共同空闲。保留 codexapp-delivery 及确认文件；不得把 unknown 重新导入旧队列。0.2.2 已验收镜像 `3b2018181c9f76080bd725d466c5772c8e5341355a7f70be7961065df42624b5` 保留作回退产物，认证与用户状态不倒退。4173 已从当前源码重启，5173 未操作。
