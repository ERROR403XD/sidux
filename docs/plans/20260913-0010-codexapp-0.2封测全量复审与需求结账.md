## 2. 确定问题，按优先级排列

### REV-01 / P1：保存自动化状态时可能丢掉已经受理的新运行

位置：`src/server/automationEngine.ts:119–126`，并发入口为 `manual()`、后台 `dispatch()` 及各自的 `persist()`。

`persistNow()` 先从当前运行列表取出 `hot`，再等待锁检查和历史归档，最后直接 `this.state.runs = hot`。保存串行队列与调度控制串行队列是两条队列；后台 dispatch 的保存等待 I/O 时，manual 可以进入另一条队列并向列表添加运行。旧保存随后覆盖整个列表，把刚添加的运行丢掉。下一次保存不能恢复它，manual 仍返回先前对象的“queued”。

隔离复现使用真实 `AutomationEngine` 和临时磁盘状态，通过一次延迟归档模拟 I/O 交错，不替换入队/调度逻辑：先让第一条任务在获取账号阶段等待；释放后挂起其状态保存；从公开 `manual()` 提交第二条；确认列表出现两条后放行保存。结果：

- 第二条请求返回 `queued`，但返回的 runId 在内存、`state.json` 和历史页中均不存在。
- 第一条任务正常启动，第二条没有启动；相同 requestId 再请求返回不同 runId。
- 没有重现“第一条重复执行”，不能把幂等身份丢失扩写为已经证明了重复发送。

**来源：旧有问题。** 0.2.18 基线已经包含相同“异步前截取、异步后整体覆盖”顺序，以及后台 dispatch 与控制队列分离的入口；本轮未引入这一结构。当前版本已动态重现，旧包来源通过源码对照确认，未把当前探针冒充对旧包的动态重跑。本轮历史分段和准备所有权测试均未覆盖此交错。

影响：自动化任务可能表面受理、实际丢失，直接影响核心执行可靠性；不能以全套现有测试通过为由继续忽略。并未证明它会切换账号、绕过额度或解除 API 占用。当前生产存在相同潜在代码缺陷，不表示已在生产观察到丢任务。

最小处理方向：修正保存期间运行集合的并发所有权，保证等待期间新加入的运行不被旧列表覆盖；补“后台保存 × 手动/定时入队 × 通知完成”的确定性测试。不能把整个慢 dispatch 放回控制串行区，否则会重新引入 SCH-02 的互相阻塞。修正后用相同请求检查内存、磁盘、历史、重启及实际仅执行一次。

### REV-02 / P2：移除仅名称项目会使保留的自动化失去执行目标

位置：`src/server/codexAppServerBridge.ts:9422–9427`、`:4341–4345`、`:7378`；前端 `src/composables/useDesktopState.ts:5425–5430`。

项目移除只删除组织元数据和排序。项目自动化的 TOML 仍然引用该 `virtual:` ID；运行时解析目录会先查询组织，因其已删除而失败。普通目录项目移除后真实 cwd 仍然存在，原有自动化可以继续定位目录；新组织项目在这里有不同待遇。

本次使用当前构建包启动唯一 localhost 端口的独立服务，使用合成账号和不会连接云服务的原生 IPC fixture，经过真实 HTTP 路由与调度器验证：

1. 创建仅名称项目和暂停的自动化，通过“手动运行”正常完成。
2. 移除项目，HTTP 200；项目自动化列表仍含该任务。
3. 再次手动运行，同一任务变为 `failed / EXECUTION_ERROR`，提示消息尚未发送。

定时运行进入同一个目录解析入口，删除后预计也会失败；这是代码推导，本探针实际验证的是手动运行，不冒充自然到点测试。脚本仅创建临时 home、合成账号和带唯一标记的工作目录，完成后已清理。

**来源：本轮新增组合缺陷。** 既有项目 HTTP 脚本测了删除保留文件，自动化 IPC 测了组织目标的正常运行，但后者的 `resolveCwd` 是 fixture 映射，未验证删除后真实 resolver。不能把手工测试表中“移除”和“自动化”两行均有覆盖等同这个组合已测。

影响：该组织关联自动化失效，属于核心功能的一个入口问题；其他项目的自动化、账号切换和 API 出口未见受影响。应局部处理组织移除与自动化引用的生命周期，不能静默删除/暂停任务或更换账号来掩盖失败。具体修复需保持“组织只影响表现形式”的既定原则。

### REV-03 / P2：浏览器存储写满时，已受理引导可能在刷新后消失

位置：`src/api/deliveryOutbox.ts:115–126`、`src/api/conversationDeliveryCache.ts:33–45`。

收到有效 ACK 后先尝试写显示缓存，随后清除发送 outbox。显示缓存为保障发送流程而吞掉写入错误；若 outbox 已写入、额外的显示缓存因容量不足写不进去，随后 outbox 又被移除，刷新时就没有正文可恢复。在原生历史尚未包含该引导内容、队列也不再含已受理消息时，正文暂时消失。

隔离探针按真实调用顺序验证：发送前可见 1 条；ACK 为 accepted、fetch 仅一次；刷新后的 outbox=0、显示缓存=0、可见投影=0。原用例 `useConversationDeliveries.test.ts:80` 只验证“缓存写失败不使 ACK 失败”，没有验证刷新可见性。

**来源：本轮引导显示功能未覆盖的边界。** 它不改变原生实际发送、账号、额度或重试策略；因此不能通过把 ACK 改为发送失败、自动生成新 ID 重发来修复。应保留可恢复正文/已确认状态的降级路径，同时保持显示记录永不驱动重发。普通空间充足情况下的切换、刷新、队列失败与原生回显用例仍通过。

### REV-04 / P2：问题摘要请求挂起时，“忽略问题”会持续占用

位置：`src/composables/useThreadInterruptions.ts:13–40`。

摘要 GET 只在卸载时 abort，没有自身截止时间；`refresh()` 始终返回尚未结束的旧请求。即使 SSE 已重连，ready 也不会发出新的摘要请求。用户忽略问题的 POST 成功后还要 await 同一摘要，`ignoring` 因此不释放；其他会话的忽略操作被直接挡回。

隔离探针挂起首次 GET，同时让后续 POST 和 SSE 正常返回：重连后摘要请求仍只有一次；第一次忽略已经在服务端得到成功响应、SSE 也清了问题，但前端仍处于 ignoring；第二个会话的忽略没有发出。放行原 GET 后才恢复。不是声称正常网络每次都会挂死，而是该故障条件下没有应用级恢复期限。

**来源：本轮新增问题台账 UI 的边界。** 已有两项 composable 用例覆盖迟到成功和显式失败，没有覆盖永久 pending。问题忽略 UI 受阻，但没有发现此等待占用账号 lease、阻挡实际聊天或 API 调度。最小处理为有界摘要读取和失效请求替换，忽略保存完成不应等待无期限的历史读取；仍需避免迟到快照覆盖新问题。
