# 0.2.19 稳定性收口与验收

以 `136a6c3`（含用户追加的提示动画、侧边栏和命令搜索 UI 修改）为基线；在 `feature/0.2.19-stabilization` 和 59001 上开发。生产 5900 当前运行追加修复后的 0.2.18，实际路径以实时进程为准。本轮不切换生产、不修改生产认证或调度配置。

## 不变的核心契约

账号选择、固定出口与默认出口的差别、切换/刷新/移除的阻塞范围、额度保护与刷新规则、自动化并发四槽、同会话占用、API HTTP/SSE/WS 及续接归属、发送去重和不确定结果不自动重发、自动激活向同账号正常工作让出，均沿用现行规则。不能以安全整改为由增设全局账号锁、扩大认证限制或强制串行化。

唯一明确的交互变更：用户要求 `/` 只在草稿字符 0 处触发命令搜索，正文中途、空白后和后续行不触发；保留其他 UI 修改。

## 分批范围

1. 固化阻塞与放行基线；当前完整基线为 738 passed / 1 skipped（4 workers，JSON 报告）。
2. SCH-01：发布专用激活冻结和只读活动统计，覆盖迟到资源清理；不复用普通 API 设置变更或账号切换的锁。
3. SCH-02：慢 inspect 离开调度串行区，用归属与状态校验拒绝迟到结果；不增加任务并发。
4. SCH-03：仅在取消可以贯穿准备链并证明占用不提前释放时实施超时；禁止单纯 Promise.race 后释放槽位或杀共享 worker。
5. SCH-04：八条检查上限内轮转，保留每轮最多一次提交及原有额度/会话准入。
6. 低风险未用代码与可复现打包独立评估；不顺带升级运行依赖。

MOD-01 大模块拆分、PERF-01 跨账号缓存合并、DATA-01 历史/防重索引清理留待 0.3 单独设计。SEC-01 主动预览的来源隔离不能以全局 CSP/CORS/认证限制替代；若不能证明预览与核心出口兼容，本版本保留已知风险。这符合用户“核心功能优先，可接受一定程度不安全”的明确取舍。
