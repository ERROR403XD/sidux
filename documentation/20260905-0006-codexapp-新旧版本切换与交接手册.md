# CodexApp 新旧版本切换与交接手册

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 项目/服务 | CodexApp |
| 文档目的 | 作为 CodexApp 每一轮“稳定版开发候选版 → 隔离验收 → 生产交接 → 开始下一轮”的长期标准操作手册 |
| 适用环境 | VUbuntu `192.168.50.46`；生产 `codexapp.service:5900`；候选容器 `codexapp-multi-account-dev:59001` |
| 创建日期 | 2026-09-05 |
| 最后更新 | 2026-09-05 |

| 维护者 | CodexApp 维护者 |

## 结论先行

开发循环成立，但生产切换必须分成两个阶段：

```text
稳定版 5900 指挥开发
  → 候选版在独立 CODEX_HOME + 59001 测试
  → Codex 准备并提交 release
  → 当前 turn 结束
  → 用户从独立主机终端执行 activate
  → 候选 release 成为新的 5900 稳定版
  → 59001 停止并留作下一轮候选环境
```

不能让承载当前 turn 的旧 CodexApp 同步停止自己。脚本因此把 `prepare` 和 `activate` 分开：前者可由 Codex 在对话中执行；后者必须等当前 turn 完成后，由用户从不依赖 CodexApp 的 SSH/本机终端执行。

> [!important] 每轮都要确认“真正切换了账号”
> 添加或重新登录账号只是把凭据加入账号池，不等于该账号已成为当前生效账号。必须在 59001 的账号卡上手动点击“切换”，等待其成为 active 后，再发起真实消息验收。本手册初次验收时的 401 已确认由未手动点击“切换”导致，点击后问题解决。

## 本手册的长期使用方式

本手册不绑定某一个 release 或某一次交接。以后每一轮都按下列六个阶段执行：

1. **建立稳定基线**：确认 5900 当前版本、生产 `CODEX_HOME`、回滚点和本轮开发分支。
2. **隔离开发与测试**：新版本始终在 59001 和独立 `CODEX_HOME` 中运行，不复制生产认证。
3. **完成真实账号验收**：登录或添加账号后手动点击“切换”，再验证账号 identity、配额、真实对话、线程连续性和刷新持久性。
4. **准备不可变 release**：所有门槛通过后提交代码，运行 `prepare`，记录 release 路径、提交和验证结果。
5. **独立终端交接**：结束当前 turn，关闭页面，由用户在独立终端执行 `check` 和 `activate`，随后完成生产验收。
6. **进入下一轮**：保留上一版 release 和事务快照，将新稳定版作为新基线，重复以上流程。

历史 release 路径、耗时、测试数量和 PID 只是当次证据；下一轮不得直接沿用这些数值，必须重新检查实时状态。

## 目标与范围

### 目标

- 候选版本通过测试后，以短维护窗口替换生产 CodexApp 代码。
- 生产继续使用 `/root/.codex`，保留主机 Codex CLI 的登录、账号池、会话和配置。
- 测试环境的独立账号、`auth.json`、sessions 和账号池绝不覆盖生产。
- 切换失败时自动恢复上一版服务定义和停服后的认证快照。
- 支持以后按相同流程重复“稳定版开发候选版 → 候选版接管生产”。

### 范围

- 包含：源码构建、npm tarball、版本化 release、systemd drop-in、空闲检查、测试容器停止、认证状态快照/比对、激活和回滚。
- 不包含：自动合并分支、自动推送 GitHub、生产账号重新登录、删除旧 release、删除认证备份、自动清空测试 volume。
- 不修改：`/etc/systemd/system/codexapp.service` 主 unit、`/home/docker/codexapp` 旧部署目录、主机 Codex CLI 安装和 Tailscale。

> 事务目录可能包含 `auth.json` 和账号配置档的备份。目录权限必须保持 `0700`，文件保持原有私有权限；不要把其内容粘贴到对话、文档、Git、日志平台或截图中。

## 0.2.20-dev.2 起执行的双区维护规范

5900 和 59001 是两个长期独立的维护区。版本更新只交接代码，不交接配置、账号或工作区状态；任何需要跨区复制状态的操作都必须视为越界，先停止并重新确认范围。

### 5900 生产区：只更新代码，不动配置和账号

生产版本更新允许变更的内容仅包括：已验收 release 目录、生产 systemd release drop-in，以及为停服/启动所必需的服务状态。以下内容必须原样保留，不得在版本更新过程中登录、注销、重新认证、切换账号、覆盖、迁移或删除：

- 生产 `CODEX_HOME=/root/.codex` 下的 `config.toml`、`auth.json`、`accounts.json`、`accounts/` 及其他账号/凭据状态。
- 生产会话、历史、队列、自动化状态和当前账号额度来源。
- 生产项目、线程、当前 `cwd`、保存的项目目录和工作区文件。

版本更新不得从 59001 复制或导入任何配置、认证、账号、session、历史或工作区数据，也不得为了验证新版而在 5900 执行 `codex login/logout` 或账号操作。允许对生产状态做只读检查，以及写入权限受保护、仅供回滚使用的备份；这些备份不是新版配置来源，不能反向覆盖生产状态。

切换完成后的运行期 token 正常轮换属于服务运行行为，不属于版本更新动作；回滚也不得用旧快照覆盖已经正常轮换的新凭据。

### 59001 测试区：固定维护自己的可复用状态

59001 必须持续使用自己的配置、账号、会话、历史和测试工作区，每次测试从同一套已配置状态开始，避免重复登录和重复配置：

| 状态 | 固定归属 | 维护要求 |
| --- | --- | --- |
| 测试账号与配置 | `CODEX_HOME=/codex-home` → `codexapp-multi-account-dev-home` | 只在 59001 添加/维护；重建容器不得换卷、清卷或复制生产状态 |
| 测试服务 | `codexapp-multi-account-dev:59001` | 可按候选版本替换容器，但必须保留上述 named volume |
| 测试工作区 | 固定卷 `codexapp-0190-test-workspace` → `/test-workspace/automation-0190`；其他测试线程的 `cwd` 指向 59001 专用测试目录 | 不使用 5900 当前项目或生产工作区；需要干净样本时另建临时工作区 |
| 测试源码 | 当前候选版本的独立 worktree/release | 不把生产运行目录 `/home/docker/codexapp` 当作测试源码目录 |

候选版本更新优先复用固定状态执行：

```bash
cd /home/Code/codexapp
CODEXAPP_REPLACE_DEV=1 ./scripts/run-multi-account-dev.sh
```

执行前确认容器、`CODEX_HOME` volume 和测试工作区归属；执行后确认版本已更新且账号、配置、会话、历史和工作区仍可读。除非明确要测试首次登录、失效认证或数据迁移，否则不得删除 `codexapp-multi-account-dev-home`、重新创建测试账号或重复初始化测试配置。需要全新状态时，使用单独命名的临时卷/工作区，测试结束后按该测试的清理规则处理，不得替换标准测试区。

### 每轮版本维护的硬性检查

1. 先确认 5900 的 service、端口、生产 `CODEX_HOME` 和当前 release；确认 59001 的容器、端口、固定状态卷和测试工作区。
2. 在 59001 完成候选版本测试，复用既有测试配置和账号；不得为了“方便测试”读取或导入 5900 账号。
3. `prepare` 只构建和登记 release，不写生产 `CODEX_HOME`；`activate` 只切换 5900 的代码 release，并按本手册执行空闲检查和状态不变性核对。
4. 更新前后分别记录非敏感元数据并核对生产状态未被维护动作改写；不在日志、截图或交接消息中展示认证内容。
5. 若发现配置、账号或工作区需要迁移才能完成版本更新，立即停止切换，把它作为独立迁移任务重新评估，不得混入版本发布窗口。

## 为什么切换不会主动改变登录状态

脚本采取以下边界：

1. `prepare` 只处理已提交源码、构建产物和 release 目录，不读取或写入 `/root/.codex`。
2. `activate` 先确认服务端没有进行中 turn、队列和待处理 approval，然后停止 59001 和 5900。
3. 生产服务停止后，才备份 `auth.json`、`accounts.json` 和 `accounts/`。
4. 新旧代码不互相覆盖；脚本只切换 systemd 的 `ExecStart`。
5. 启动后只请求首页 `/` 做健康检查，不调用账号、额度或对话 API。
6. 健康检查后将认证状态与停服后快照逐字节比较；任何变化都会触发自动回滚。
7. 测试 volume 从不挂载到生产，也不把测试账号导入 `/root/.codex`。

上述保证覆盖“代码交接过程”。新版本正式使用后，Codex 正常刷新 token 会合法更新生产认证文件；以后执行人工 `rollback` 时，脚本会保留当时最新的生产认证，而不会用旧快照覆盖正常的 token rotation。

## 脚本命令

### 查看状态

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh status
```

输出只包含服务状态、PID、当前 release、最近准备的 release、测试容器状态，以及生产认证文件是否存在、权限、大小和修改时间；不会输出凭据内容。

### 准备候选 release

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh prepare
```

`prepare` 会：

1. 拒绝存在未提交的已跟踪源码改动；未跟踪的用户文件不会自动提交。
2. 执行 `pnpm run build`。
3. 执行 `pnpm pack --pack-destination /tmp`。
4. 将 tarball 安装到 `/home/docker/codexapp-releases/codexapp-<版本>-<提交>-<时间>/`。
5. 验证 CLI 可加载、包含 `--strict-port`，且不再包含旧 tunnel/启动 login 参数。
6. 更新 `/home/docker/codexapp-switch-state/latest-prepared`。

此命令不停止 5900/59001，不修改 systemd，也不访问生产认证。

### 切换前检查

```bash
./scripts/codexapp-release-switch.sh check latest
```

检查范围：

- 生产 service 正常且 `CODEX_HOME=/root/.codex`。
- 生产首页可访问。
- 线程列表中没有 active/running/inProgress 状态。
- 持久队列为空。
- 待处理 approval/server request 为空。
- 候选 release 有完成标记和 CLI 入口。

检查最多分页读取 2000 个线程，避免无界扫描。它无法识别从其他终端直接启动的 Codex CLI 任务，所以用户仍需人工确认主机上没有正在执行的独立 `codex` 任务。

### 激活候选 release

```bash
./scripts/codexapp-release-switch.sh activate latest --confirm-idle
```

此命令必须从独立 SSH/本机终端执行。`--confirm-idle` 表示操作者已经确认：当前 Codex turn 结束、所有 CodexApp 页面关闭、没有独立 CLI 任务。

执行顺序：

1. 再次运行服务端空闲检查。
2. 停止 `codexapp-multi-account-dev`，保留其 volume。
3. 停止 `codexapp.service` 并确认 5900 已释放。
4. 创建认证状态快照。
5. 备份已有 release drop-in。
6. 原子安装指向候选 release 的新 drop-in；启动参数固定为 `--port 5900 --strict-port --no-password --no-open`。
7. `daemon-reload` 并启动生产服务。
8. 只检查首页、systemd active 状态、真实 ExecStart 和认证文件不变。
9. 写入事务结果；59001 保持停止。

## 每一轮交接中 Codex 应做什么

1. 在 feature branch 中完成离散提交，保留用户无关改动。
2. 跑全量单测、类型检查和构建。
3. 按 Provider/Auth Docker 工作流在 59001 验证打包版本。
4. 完成 light/dark、关键业务、刷新持久性和性能审计。
5. 让用户完成需要真实账号的测试，不代替用户登录，不记录凭据。
6. 确认用户登录/添加账号后已手动点击“切换”，并在 active 账号下完成了真实请求。
7. 所有验收通过后运行 `codexapp-release-switch.sh prepare`。
8. 报告 release 绝对路径、提交、测试结果、回滚入口和仍未验证内容。
9. 明确告诉用户当前 turn 已结束，可以从外部终端切换。
10. 不在同一个 turn 中直接执行 `activate`，也不安排依附旧 app-server 的后台 shell 来停止自己。

## 每一轮交接中用户应做什么

### 切换前

- [ ] 确认 Codex 已报告候选版测试通过并生成 release。
- [ ] 确认本轮在 59001 中登录/添加账号后，已手动点击“切换”，目标账号已显示为 active。
- [ ] 确认本轮 P6 真实请求成功；仅显示 ready、能读取配额或登录成功不算通过。
- [ ] 保存当前对话中的必要结论；等待 Codex 当前回复完全结束。
- [ ] 确认没有另一位浏览器/终端使用 CodexApp 或 Codex CLI。
- [ ] 关闭所有访问 5900、59001 的浏览器标签页，避免自动重连。
- [ ] 打开独立 SSH 或服务器终端；不要依赖将被停止的 CodexApp 内置终端。

### 执行切换

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh check latest
./scripts/codexapp-release-switch.sh activate latest --confirm-idle
./scripts/codexapp-release-switch.sh status
```

看到 `Cutover succeeded` 和 `Authentication state remained byte-for-byte unchanged` 后再打开网页。

### 切换后验收

- [ ] `http://192.168.50.46:5900/` 可访问。
- [ ] 原激活账号仍处于登录状态，没有启动登录弹窗。
- [ ] 原项目、线程列表、当前线程、cwd 和历史消息可读。
- [ ] 主机终端的 `codex login status` 正常。
- [ ] 执行一条明确标记的无害测试消息，确认只出现一个 live response/overlay。
- [ ] 检查 `journalctl -u codexapp.service` 没有新增启动、认证或 app-server 循环错误。
- [ ] 保留 59001 的 volume、旧 release 和事务快照，直到观察期结束。

## 回滚

### 何时回滚

- 5900 无法启动或访问。
- 新版出现循环重启、真实请求失败或重复 live overlay。
- 原账号、项目或线程无法读取。
- 账号 identity、额度来源或线程连续性与预期不符。
- 发现认证状态在仅代码切换阶段发生变化。

### 自动回滚

`activate` 在成功标记前发生错误时，会自动：

1. 停止失败的新服务。
2. 恢复之前的 drop-in。
3. 恢复停服后认证快照。
4. 重新启动旧生产服务。
5. 如果 59001 原本运行，则重新启动测试容器。

自动回滚只适用于尚未开始真实使用的新 release；因此可以恢复刚创建的认证快照。

### 人工回滚

开始使用新版本后需要回滚时：

```bash
cd /home/Code/codexapp
./scripts/codexapp-release-switch.sh rollback --confirm-idle
./scripts/codexapp-release-switch.sh status
```

人工回滚会先备份“此刻”的生产认证并确认代码回滚前后保持不变，不会默认恢复激活时的旧 token。回滚前同样必须结束任务并关闭页面。

## 开启下一阶段开发

生产切换通过后：

1. 将已经上线的提交作为下一阶段稳定基线；按项目 Git 流程合并或整理分支。
2. 不删除刚上线 release、上一版 drop-in 备份和认证快照。
3. 在新的 feature branch 开发下一阶段。
4. 重新构建候选镜像：

   ```bash
   cd /home/Code/codexapp
   CODEXAPP_REPLACE_DEV=1 ./scripts/run-multi-account-dev.sh
   ```

5. 59001 继续使用 `codexapp-multi-account-dev-home`；除非明确需要全新测试状态，否则不要删除 volume。
6. 重复“测试 → prepare → 结束 turn → 用户 activate → 观察/回滚”的流程。

## 配置与文件变更

| 文件/对象 | 作用 | 是否含敏感内容 | 回滚方式 |
| --- | --- | --- | --- |
| `scripts/codexapp-release-switch.sh` | 切换工具 | 否 | Git 回退脚本提交 |
| `/home/docker/codexapp-releases/<release>/` | 版本化应用代码和依赖 | 否 | 切回上一 release；暂不删除 |
| `/etc/systemd/system/codexapp.service.d/90-release-switch.conf` | 选择生产 release | 否 | `rollback` 恢复上一份或回到 base unit |
