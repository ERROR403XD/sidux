### 0.2.3 可靠发送、编辑与结果核对

#### 前提

- 使用独立 59001 或 4173；生产 5900 不参与。准备虚构 TestChat、浅深主题、两个浏览器标签页。
- 浏览器允许 localStorage 和 sessionStorage；需要故障注入时使用 Playwright 请求拦截。普通发送、排队和引导均使用协议 2 及稳定发送 ID。

#### 操作

1. 发送虚构消息。在请求尚未到达服务器时断开请求，确认草稿保留并显示“提交结果待确认”。刷新后点击“核对提交”，检查请求沿用同一 ID，最终只出现一个原生回合。
2. 让服务器接受消息后丢弃 HTTP 响应。刷新再核对，确认返回已保存的 turnId，没有第二次原生 turn/start。匹配的旧草稿清空；核对期间新输入的不同草稿保留。
3. 在运行中的会话排队两条消息，保存不同模型、强度和速度。切换界面模型，确认先前消息的执行设置不变。旧页面的 PUT 或无协议 POST 应拒绝，队列不变。
4. 编辑第一条队列消息。原 ID、位置和服务器原文继续存在，状态变为“编辑中”。修改草稿后刷新，确认内容与编辑关联仍在；保存更新原条目。取消编辑恢复原消息排队。
5. 两个标签页各进入同一条消息的编辑状态。第一页保存后，第二页修改并刷新再提交，必须提示版本已变化，保留其草稿；不得覆盖第一页，也不得转成普通新消息发送。
6. 对排队消息使用“引导”，检查服务端原条目转换为同一次投递，无 remove/add 恢复链。发送中禁用编辑与删除；待确认条目只有核对和停止跟踪，没有重试发送按钮。
7. 在独立实例模拟 CLI 响应丢失或发送期间重启。原 sending 恢复为 unknown；使用 clientId 核对最近最多 50 回合，无证据时保持待确认，不自动重发。停止跟踪弹窗说明不会中断已经执行的任务。
8. 发送前失败可手动重新排队。账号/供应方变化不得替换旧发送的身份；存在待发送、编辑中或待确认记录时账号和供应方切换被空闲检查阻止。
9. 在独立 CODEX_HOME 测试旧队列迁移、确认文件写入与待发送文件删除之间崩溃、损坏文件和第二写入者。损坏或租约失败时停止投递并显示错误，不当作空队列。
10. 分别检查 1440×900、375×812、768×1024 的浅深主题；无横向溢出，队列可滚动，实际新控件和确认弹窗可读。发送带唯一标记及 Markdown 文件链接的 TestChat，刷新后验证 href、title、可见文字。

#### 预期

- 区分浏览器未收到确认、服务器持久接收、CLI 接受及执行完成；仅收到 turnId/可靠 clientId 证据才确认原生接受。
- 新会话已加载时直接发送，只有 notLoaded 会话才 resume；不能因尚无 rollout 而阻塞首条消息。
- 断网、页面刷新、重启、模型报错均不导致自动重复执行。不再通过自动撤回并换模型重发修复执行错误。
- 队列恢复只处理 queued；editing/failed 需明确操作，sending/unknown 先核对。多个会话共享最多 4 个投递/核对工作；空闲检查不读取全文。

#### 清理与降级

- 结束虚构回合，处理测试队列及待确认记录，再归档测试会话；只停止本轮独立容器。清理浏览器测试上下文即可移除虚构草稿。
- 降级前核对新发送记录为空；保留独立 codexapp-delivery 目录及确认记录。旧版只读取已经迁走的旧队列字段，不能把 unknown 重新导回旧队列。生产服务与认证不变。
