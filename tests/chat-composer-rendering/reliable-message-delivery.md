### 0.2.3 可靠发送、编辑与结果核对

#### 前提

- 使用独立 59001 或 4173；生产 5900 不参与。准备虚构 TestChat、浅深主题、两个浏览器标签页。
- 浏览器允许 localStorage 和 sessionStorage；需要故障注入时使用 Playwright 请求拦截。普通发送、排队和引导均使用协议 2 及稳定发送 ID。

#### 操作

1. 发送虚构消息。在请求尚未到达服务器时断开请求，确认草稿保留并显示“提交结果待确认”。刷新后点击“核对提交”，检查请求沿用同一 ID，最终只出现一个原生回合。
2. 让服务器接受消息后丢弃 HTTP 响应。刷新再核对，确认返回已保存的 turnId，没有第二次原生 turn/start。匹配的旧草稿清空；核对期间新输入的不同草稿保留。
3. 在运行中的会话排队两条消息，保存不同模型、强度和速度。切换界面模型，确认先前消息的执行设置不变。旧页面的 PUT 或无协议 POST 应拒绝，队列不变。
4. 编辑第一条队列消息。原 ID、位置和服务器原文继续存在，状态变为“编辑中”。修改草稿后刷新，确认内容与编辑关联仍在；保存更新原条目。取消编辑恢复原消息排队。
5. 两个标签页各进入同一条消息的编辑状态。第一页保存后，第二页修改并刷新再提交，必须提示版本已变化，保留其草稿；不得覆盖第一页，也不得转成普通新消息发送。
6. 对排队消息使用“引导”，检查服务端原条目转换为同一次投递，无 remove/add 恢复链。发送中禁用编辑与删除；待确认条目只有核对和停止跟踪，没有重试发送按钮。
7. 在独立实例模拟 CLI 响应丢失或发送期间重启。原 sending 恢复为 unknown；使用 clientId 核对最近最多 50 回合，无证据时保持待确认，不自动重发。停止跟踪弹窗说明不会中断已经执行的任务。
8. 发送前失败可手动重新排队。账号/供应方变化不得替换旧发送的身份；存在待发送、编辑中或待确认记录时账号和供应方切换被空闲检查阻止。
9. 在独立 CODEX_HOME 测试旧队列迁移、确认文件写入与待发送文件删除之间崩溃、损坏文件和第二写入者。损坏或租约失败时停止投递并显示错误，不当作空队列。
10. 分别检查 1440×900、375×812、768×1024 的浅深主题；无横向溢出，队列可滚动，实际新控件和确认弹窗可读。发送带唯一标记及 Markdown 文件链接的 TestChat，刷新后验证 href、title、可见文字。

#### 预期

- 区分浏览器未收到确认、服务器持久接收、CLI 接受及执行完成；仅收到 turnId/可靠 clientId 证据才确认原生接受。
- 新会话已加载时直接发送，只有 notLoaded 会话才 resume；不能因尚无 rollout 而阻塞首条消息。
- 断网、页面刷新、重启、模型报错均不导致自动重复执行。不再通过自动撤回并换模型重发修复执行错误。
- 队列恢复只处理 queued；editing/failed 需明确操作，sending/unknown 先核对。多个会话共享最多 4 个投递/核对工作；空闲检查不读取全文。

#### 清理与降级

- 结束虚构回合，处理测试队列及待确认记录，再归档测试会话；只停止本轮独立容器。清理浏览器测试上下文即可移除虚构草稿。
- 降级前核对新发送记录为空；保留独立 codexapp-delivery 目录及确认记录。旧版只读取已经迁走的旧队列字段，不能把 unknown 重新导回旧队列。生产服务与认证不变。

### 0.2.19 引导内容跟随操作显示

前置：独立实例，两条 TestChat 会话，其中一条处于运行中；明暗主题，桌面、768×1024、375×812。故障场景使用 Playwright 拦截虚构请求，禁止对生产故障注入。

1. 添加一条排队消息，点击“引导”。在 HTTP 请求仍未返回时检查正文已出现相同内容及“正在提交”；切到另一会话再回来，内容仍在，且不串到另一会话。
2. 点击引导后立刻刷新；先恢复待确认的显示，读到服务端引导队列后显示“等待引导”。刷新不能发起第二次引导或中断。
3. 依次模拟 queued、sending、unknown、failed、editing；每种状态切换会话、刷新、断线重连，正文保持一条，图片/文件/技能保持原内容。普通队列条目仍只在队列中；点击引导才进入正文。
4. 同时令队列和历史接口返回 503；正文不能因 loading 或读取失败变空。恢复服务后按真实状态更新。
5. 让队列项消失，但原生历史仍旧。已知内容继续显示；只读回执证实 accepted 后标记“已送达”。回执缺失/读取失败不能推断取消，也不能自动重发。
6. 推送带相同 client ID 的原生 userMessage；显示记录替换为唯一原生消息。重复通知、迟到 HTTP 回执、旧队列快照、刷新都不能再生成第二条。同文不同 ID 的两次引导必须保留两条；无 client ID 的历史仅凭已确认回合与序号对齐，不能仅凭文字合并。
7. 接收回执时用户已切走；回来后显示正确。回执属于前一回合时放回该回合，后续原生历史决定实际顺序。
8. 删除尚未发出的队列项/停止跟踪后显示“已移除”；停止跟踪不得描述成中止已执行任务。发送前失败仍可使用现有队列编辑/重新排队；不新增自动重发路径。
9. 发送结果丢失后核对同一次浏览器提交，继续沿用旧 ID；本次显示意图并入旧 ID，不能多出一条。浏览器显示缓存写入失败不得把已经被接受的投递改判失败。
10. 检查唯一标记与 Markdown 文件链接的真实正文：href、title、文字均正确，明暗状态文字和附件清楚可见。

自动化入口：`node scripts/test-steering-visibility-ui.cjs`；单元/状态链位于 `useConversationDeliveries.test.ts`、`useDesktopState.test.ts`、`deliveryOutbox.test.ts`、`deliveryBridge.test.ts`。浏览器脚本不调用真实 turn/start 或账号切换；本地真实 adapter 的核心回归另行执行。截图 `output/playwright/0219-steering-*.png` 与 `testchat-steering-visibility-cjs.png`。

显示缓存 `codexapp.delivery-view.v1.*` 仅保存 UI 记录，永不用于决定是否投递；既有 `codexapp.delivery.v2.*`、服务端发送状态与租约仍是投递事实。回执 GET 最多 100 个 ID，仅查询当前需核对的会话，合并同会话并发；不读取账号、不 resume、不 reconcile、不写队列。原生证据出现后清除对应显示缓存。退出测试浏览器即可清理虚构 UI 数据，降级不需要迁移投递状态。

性能证据：2026-09-13 Chromium，在实际页面加载完成后，对 5,000 条历史与 100 条显示中的投递做 100 次投影；中位数 0.30ms、p95 0.50ms，无显示投递时复用原数组。结果保存在 `output/0219-final/steering-ui.json`。该数字只度量前端合并函数，不代表真实上游发送延迟或整页帧时间。浏览器脚本中引导变更请求恰好一次，无 turn/start、turn/interrupt 或账号切换请求。
