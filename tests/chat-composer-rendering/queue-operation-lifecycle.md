# 队列操作与回执的账号、停止生命周期

## 准备

使用隔离开发环境的合成账号A/B及排队消息，在Network或测试fixture中延迟队列读取、写入和delivery-status响应。无需读取生产认证。分别验证亮色和暗色界面。

## 操作与预期

1. 对A的排队消息执行立即发送或确认送达，延迟成功响应；停止并重新启动，或切到B后释放旧响应。旧结果不添加当前会话消息、不改投递状态、不排新的历史同步。
2. 延迟移除或开始编辑的成功响应，停止后释放。旧结果不向当前编辑器返回消息；当前上下文正常移除、编辑仍成功。
3. 分别延迟移除、编辑、排序和立即发送的失败响应，重新启动后释放。当前UI没有旧错误，也不因旧失败追加队列读取。
4. 延迟队列读取A，重新启动并令新读取B失败，再释放A的失败。当前错误仍是B的错误；成功写入已覆盖的旧读取失败也不重新显示。
5. 恢复一条steer消息后令队列为空，延迟旧回执读取；停止/重启或切账号，再刷新队列。新回执读取立即开始；释放旧回执不更改当前投递显示，也不释放新读取槽。新回执正常更新显示。
6. 通过回合开始/完成通知触发队列刷新A并延迟响应，停止/重启后发送新回合通知触发刷新B，再释放A；B仍占有processing标记，重复通知不启动额外读取，B完成后可以再次刷新。
7. 排队两个写操作，在第一个等待期间停止/重启；它们继续按接受顺序执行，旧结果不提交当前UI。停止接收UI结果不会撤回服务端已接受的操作。
8. 添加新队列消息，在 `/codex-api/delivery-context` 的响应头或 JSON body 等待期间切换账号或停止/重启。旧添加被拒绝，不发送队列 POST、不写 outbox；草稿仍可核对后重试。已有编辑/删除响应等待时排入新添加，再切账号，旧添加不启动 context GET。
9. 停止期间调用添加，即使在微任务执行前重新启动，也不发起读取或写入。仅改变当前会话选择时，正常添加仍使用原会话 ID。
10. 在添加意图已保存到 outbox 后切换账号：提交继续携带保存时的 `expectedContextId`，不会重新获取新账号上下文；旧完成不提交当前 UI。网络失败时保留待确认记录，不自动重建意图。

## 清理

解除延迟/失败fixture；确认已接受操作的实际状态，再手动移除合成队列和会话。保留标准测试卷，不修改生产5900。
