# 浏览器任务通知（0.2.22）

准备：HTTPS 或 localhost 浏览器，隔离候选 59001 或合成 4173。通知设置位于设置页的集成区域。覆盖浅深主题和两个同源标签页。

操作：
1. 点击“允许浏览器通知”，在浏览器授权。拒绝时应显示原因，不能自动重复弹出申请。
2. 各完成一个普通回合、中断回合、额度限制回合；核对通知标题及会话标题正文。
3. 对同一回合同时发送 error、turn/completed 或重放终态事件，两个标签页合计仅产生一条通知；willRetry=true 本身不通知。依次注入同一回合的额度 error（willRetry=true）和无 error 的 interrupted 终态，应通知“会话额度受限”；若重试后成功，应通知“会话任务已完成”。其他会话/回合的普通中断不应继承该额度原因。
4. 点击通知，窗口聚焦并打开对应会话。刷新后重放已通知的事件，不重复提醒。
5. 关闭设置开关，完成其他回合，核对不再提醒。关闭全部页面后不承诺送达。
6. 在非安全 HTTP 来源或无 Notification 支持的浏览器检查提示，界面不能崩溃。

预期：完成、中断、额度受限分别提示；浏览器授权只能通过明确点击触发。两标签页使用 Web Locks 和持久回执去重；不支持 Web Locks 的浏览器以同回合 tag 和本地回执尽力合并。

性能：消费既有 SSE 事件，无新增轮询/通知网络请求；单页及持久回执均限制为 256 项。暂存的额度原因只保存会话/回合标识，最多 256 项，终态到来时删除，不保留错误正文或历史快照。

清理：关闭合成验证页面，恢复通知开关/网站权限。不删除会话或生产认证。回退对应提交。

## 0.2.22-dev.5：会话状态通知

前提：使用隔离测试数据和本机 POST 接收器；POST 卡片已配置请求地址、含 `{{message}}` 的 JSON 请求体并启用。浏览器通过 localhost 或 HTTPS 访问。用户候选入口为 59001，合成工程验证为 4173。

操作：
1. 打开设置 → 集成，确认卡片标题为“会话状态通知”，有“浏览器通知”“POST通知”和“会话完成”“额度受限”“意外中断”“自动化任务”六个开关；没有原辅助说明文字。检查 1440×900、375×812、768×1024 的明暗主题，中英文标签及实际卡片边界。
2. 分别关闭浏览器、POST 通道，触发新的终态事件；只允许另一条已启用通道发送。原 POST 卡片控制通道配置和全局启用，会话卡片的 POST 开关控制是否向该通道提交会话状态。
3. 逐项关闭四个状态，产生相应完成、额度失败、中断、自动化完成；两种通道都不得发送被关闭的状态，其他状态不受影响。刷新页面后逐项检查开关仍保持保存值。
4. 自动化使用调度运行和外部 `POST /automation/execute` 各触发一次；绿点对应的成功终态归入“自动化任务”，关闭“会话完成”不应屏蔽它。自动化的额度错误/失败仍归入额度受限/中断。
5. 将会话命名为独特标题，完成回合；浏览器正文和 POST 的 `message` 都包含“项目名 · 完成时标题”。普通项目使用侧栏显示名（含自定义名称），虚拟管理项目使用其名称，无项目会话显示“无项目”（英文为“No project”）。分别验证三种归属以及两个普通项目同目录名时的区分。浏览器点击通知仍打开对应会话。侧栏未加载或隐藏的会话也应通过不含历史的元数据读取取得标题和项目归属，外部 POST 自动化同样适用。
6. 设置 POST 免打扰，完成回合后重命名会话及项目并重启隔离服务；免打扰结束后发送的内容仍含原项目名和完成标题；自定义请求体的 `{{project_name}}` 和 `{{title}}` 也保留原值。重放同一回合不得重复发送；含引号、换行或“周额度”的标题不得在 JSON 转义或旧文案迁移时被篡改。
7. 保留原重试额度原因、成功恢复、不同回合隔离和跨标签页去重用例。关闭某状态/POST 开关会移除该状态尚未发送的会话通知，账号额度提醒队列应保留。

自动验证：`pnpm exec vitest run src/composables/browserTaskNotifications.test.ts src/server/accountNotificationService.test.ts src/server/conversationNotificationBinding.test.ts src/server/apiProxy/gateway.test.ts`；真实本机 HTTP POST 用例覆盖事件绑定→持久队列→接收器。`node scripts/verify-conversation-notifications.cjs` 使用真实设置组件、合成账号/事件和 Notification 替身，覆盖六组视口/主题及设置刷新、四类筛选、项目名、标题和去重；不证明系统通知中心实际送达或真实外部调度执行。

性能：通知继续消费既有事件流，不增加轮询。浏览器支持且启用通知时，每次页面启动最多加载一次状态偏好，设置卡片复用同一请求；不支持/关闭时不主动加载。侧栏已有的会话上下文不新增 RPC；缺失时串行读取 `thread/read(includeTurns=false)`。跨标签页锁只保护同步回执，不等待元数据 I/O。浏览器待通知最多 256 项；服务端忽略逐字事件，复用 runtime 元数据快照，没有时才单并发读取元数据，去重、待取上下文和待发通知各最多 256 项；项目归属使用当前工作区设置，标题索引复用原签名缓存，复用原 5 秒、每批 16 条的 POST 队列。

清理/回滚：还原浏览器权限/开关、四项状态、POST 配置和免打扰设置；关闭测试接收器，不删除标准状态卷、会话或认证。源码可 revert 本次功能提交；此次没有生产激活。

## 0.2.22-dev.6：集成布局与手动停止静默

前提：沿用上面的独立接收器和浏览器权限准备；启用浏览器通知、会话 POST 通知、POST 全局开关和全部四项状态。用户测试入口为 `http://127.0.0.1:59001/#/settings`。

操作：
1. 在 1440×900 打开设置 → 集成，确认会话状态通知位于顶部并横跨两栏，内部左边为浏览器和 POST 两个开关，其下分隔放置“GOAL阶段性通知”，右边为四类状态；下方 POST 和 Telegram 两张设置卡片并排。分别检查明暗主题。
2. 在 375×812、768×1024 重复检查，两张下方卡片和会话卡片内部都纵向排列；状态组恢复顶部横向分隔线，无横向溢出，滚动后 Telegram 全部设置仍可访问。切换开关并刷新，保存行为沿用 dev.5。
3. 启动一个持续运行的普通会话，点击停止；同时观察已授权的浏览器和本机 POST 接收器，两边均不得收到该回合的通知。重放该回合的 `turn/completed(status=interrupted,error=null)`、`turn/cancelled`，仍保持静默。
4. 对同一回合先注入 `error(willRetry=true, quota exceeded)`，再从 HTTP RPC 执行手动 `turn/interrupt`。它的终态及重复事件携带 `interruptionReason=user`，即使终态保留额度/网络错误，两渠道仍保持静默；额度保护自动发出的中断不带该标记，仍发送额度受限通知。
5. 在同一会话启动新回合并正常完成，核对两渠道恢复通知；另一会话即使出现同名回合标识也不得继承手动停止标记。普通网络失败应归入意外中断。模拟停止 RPC 明确失败，后续真正失败的终态仍通知，不残留停止标记。

自动验证：`node scripts/verify-conversation-notifications.cjs` 覆盖桌面、手机、平板的明暗主题、真实集成组件布局、设置持久化和浏览器 Notification 替身；`src/server/manualConversationStop.integration.test.ts` 覆盖真实 HTTP→归属 IPC worker→POST 队列的静默路径；浏览器、POST 和 RPC 路由回归分别检查无元数据读取、无入队、原生参数不变及 RPC 失败回退。浏览器页面原有终态状态同步仍可能读取会话；这些读取与已跳过的通知元数据读取分开核查。

性能：不增加定时器、HTTP/RPC 调用、历史载荷或持久化缓存；手动停止标记按会话和回合保存，每个 runtime 最多 256 项，终态处理只做标识查找。普通流式增量不执行新增逻辑。停止请求失败时撤销对应标记，后续回合与其他会话不受影响。

清理/回滚：恢复通知开关和 POST 配置，停止独立测试接收器。回滚本轮两个功能提交后重新构建候选，保留 59001 标准测试卷；生产切换另行处理。本用例不要求向真实 Telegram 或外部 POST 服务发送消息。

## 0.2.22-dev.6：可选 GOAL 阶段性通知

前提：沿用 dev.6 的独立 POST 接收器和浏览器权限准备；启用两个通道及四项类别。在隔离测试会话中建立 GOAL，准备多个成功阶段和最终完成。已有 dev.5/dev.6 通知设置升级后，新增开关默认关闭，其他选项保留。

操作：
1. 打开设置 → 集成，检查会话通知内部左栏：浏览器通知、POST通知之后有横线分隔的“GOAL阶段性通知”。在 375×812、768×1024 的明暗主题下，顺序为浏览器、POST、GOAL阶段性通知、右栏四项通知类别，无横向溢出；英文显示“GOAL progress notifications”。
2. 保持 GOAL 开关关闭，运行一个状态仍为 active 的成功阶段。浏览器和 POST 均保持静默，通知路径不读取会话上下文、不入队。GOAL 最终状态变为 complete 后成功完成，仍按“会话完成”或“自动化任务”发送最终通知。
3. 打开 GOAL 开关并刷新，确认仍为开启。运行新阶段，两渠道明确标明“GOAL 阶段完成”；浏览器标题为该文案，正文仍为“项目名 · 会话标题”，POST 的 `{{message}}` 为“GOAL 阶段完成：项目名 · 会话标题”。英文浏览器标题为“GOAL stage completed”。重放阶段终态不重复通知。
4. 先在已有 GOAL 的会话完成一次阶段，再刷新/重新连接订阅且不重放早前 goal/updated 事件。新终态携带服务端缓存的 goalStatus，仍按阶段处理；缓存的 30 秒 UI 刷新期限不能让长回合丢失已知 GOAL 状态。GOAL 清除后普通完成恢复原行为。
5. 保持阶段开关开启，关闭“会话完成”，普通 GOAL 阶段不得发送；“自动化任务”开启时，自动化阶段仍发送带 GOAL 标识的通知，关闭该类别后静默。额度受限、网络中断继续由其各自类别控制，手动停止始终静默。
6. 在 POST 免打扰期间积累阶段、最终和账号额度通知，重启隔离服务后关闭 GOAL 开关。仅阶段待发项被删除，最终及账号通知保留；在等待会话上下文时关闭开关，也不得在稍后入队/弹出。恢复开关不会补发被屏蔽的历史阶段。

自动验证：`src/conversationNotifications.test.ts`、浏览器和 POST 测试覆盖偏好迁移、阶段/最终分类、文案、类别过滤和异步关闭；`src/server/goalConversationNotice.integration.test.ts` 使用隔离 IPC worker 和真实本机 HTTP 接收器，覆盖原生 GOAL 事件→共享缓存→新订阅终态→POST 的默认静默、开启标记及最终通知。`node scripts/verify-conversation-notifications.cjs` 覆盖真实七开关、刷新保存、六组视口/主题和中英文通知文本；不证明真实模型 GOAL 执行或操作系统通知中心送达。

性能：复用已有 GOAL 缓存及事件流，成功终态只同步读取状态并附加一个状态值，不新增 RPC/轮询、不等待 RPC、不调整原事件顺序。分类器最多保存 2000 个 GOAL 状态；逐字事件直接返回。阶段开关关闭时，通知路径不读元数据、不写通知状态文件；页面原有的终态同步请求单独核对。

清理/回滚：恢复 GOAL、类别、通道及免打扰开关，停止独立接收器，清理合成任务；保留标准候选卷、会话和认证。需要回滚时 revert 本次 GOAL 通知提交后重新构建候选，生产 5900 不受本轮验证影响。

## 0.2.22-dev.7：自动续跑启动通知

前置：独立测试 HOME/POST 接收器，或 4173 的接口和 Notification 替身。旧设置缺少新类别时应迁移为关闭，保留现有四类别、GOAL 和通道设置。实际用户入口为 59001；不向真实收件人发送合成消息。

1. 设置 → 集成 → 会话状态通知，右侧第五类别为“自动续跑启动”（英文 Automatic resume started），默认关闭。开启并刷新后保持开启；在 1440×900、375×812、768×1024 的浅深主题检查真实开关，无溢出或浅色残留。
2. 类别关闭时分别执行额度恢复续跑、定时续跑，两渠道均无启动通知。开启类别并启用对应通道后，收到“额度恢复续跑已启动”或“定时续跑已启动”；浏览器正文为项目名和会话标题，POST 消息保留 `【Sidux】` 前缀。POST 还需开启其全局配置和会话 POST 通道。
3. 添加标记、deadline 到达但仍排队、发送前失败、响应未确认且没有原生证据时，不发送启动通知。排队消息取得原生 turn ID 后才发送；GOAL 在原生恢复目标成功后发送，不要求额外 turn ID。目标预算/用量不能重置。
4. 重放启动事件、同时到达回执和 userMessage 证据、刷新/重启后重放已通知启动，均不得重复。相同会话下新一次有效续跑仍应通知。恢复响应丢失时仅在真实回合证据确认后通知，不能重发未知投递。
5. 启动后同一回合成功完成，仍按“会话完成”通知；GOAL 阶段开关不控制启动通知，仍单独控制阶段完成。关闭新类别时清除尚未发送的启动通知，保留完成/额度/账号提醒；重新开启不补发已屏蔽的旧事件。
6. 定时续跑完成后，已打开的侧栏时钟图标消失，刷新后仍不出现。批量重放 20 次标记变化，应合并为一次状态 GET；失败和未确认结果继续保留核对标记。原生 GOAL 仍等整个目标 complete 才清除。

自动验证：`src/server/automaticResumeNotice.integration.test.ts` 覆盖真实隔离 IPC→定时投递/原生 GOAL→事件绑定→POST 队列，以及无可读历史时完成标记清理。续跑 runtime、delivery、分类器、浏览器和通知服务测试覆盖排队/核对/重复回执和旧设置迁移。`node scripts/verify-conversation-notifications.cjs` 验证真实八开关、刷新保存、同回合完成通知及图标清除的六组视口/主题。Notification 和模型运行使用替身，不代表系统通知中心或真实云端模型已验收。

性能：启动通知沿用原事件流，没有新增轮询、原生续跑 RPC 或投递。去重在原生确认落盘后执行，运行时键最多 1000 项；持久/浏览器通知回执沿用 256 项。未开启类别时 POST 不读上下文或写通知队列；浏览器已有上下文不读 RPC，缺失上下文保持单并发。启动事件直接分发给通知通道，不使历史、搜索、会话列表或 live 缓存失效；POST 仍沿用免打扰及每批 16 条的既有发送器。

清理/回滚：还原类别及通道开关、关闭合成页面和接收器，保留标准卷。撤回本次通知提交后重新构建候选即可；字段为兼容追加，不删除会话、投递回执或已有通知设置。GOAL 投递账本原有 v3 回退边界继续适用。
