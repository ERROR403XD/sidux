# 0.2.19 调度可靠性与不变的核心契约

## 慢状态检查、通知与释放竞争

- 前置：隔离 home；四个并发名额；模拟 runtime，可挂起 inspect，禁止真实请求。
- 操作：运行一个任务，挂起状态检查；新增手动运行、冻结/恢复调度、推送完成通知或移除该执行账号，再返回旧的 running/turnId。另测等待审批时返回旧 running、连续 tick。
- 预期：手动请求及通知不等待 inspect；已结束/取消任务不复活、不重复释放；等待审批状态不被旧快照覆盖。同 run 只允许一个底层检查，最多四个未完成检查。每个 automation/target 占用及四槽限制不变，已有固定账号与默认出口的规则不变。
- 清理：解开所有挂起 promise，关闭测试 runtime 并删除临时 home；不读取生产会话。
- 性能：慢 inspect 从全局串行区移除；每轮检查间隔仍为 30 秒；查询并发最多四，原始调用超时未结束时不叠加同 run 查询。串行区只保留状态检查/持久化/领取。快响应可立即填补释放的任务槽；不增加任务并发。

## 等额度续跑的尾部公平性

- 前置：十条等待标记，前八条会话持续忙碌；另设九条 unknown 投递，仅第九条可核对为未提交。
- 操作：连续执行两轮 tick，随后测试额度不足、提交前拒绝、提交后断线及重启。
- 预期：尾部标记最终轮到；waiting/unknown 每批最多八条，最多发出一个续跑提交。unknown 无证据不重发；额度检查、会话占用、deliveryId 去重沿用现状。
- 清理：关闭续跑服务，删除 fixture；不改真实标记。
- 性能：数组枚举仍一次/状态，新增两个内存游标；不增加定时器、持久字段、每轮额度调用或提交上限。

## 账号与出口保护矩阵

运行 accountTaskRouting、accountRuntimeIntegration、accountAuthCoordinator、accountExecution、accountActivationAdmission/Runtime/Scheduler、apiProxy/gateway、automationDispatchIntegration 和 deliveryService。

同时断言：默认切换时固定账号流继续，默认流遵循既有关闭/拒绝规则；A 刷新不堵 B；账号移除只清理所属连接；同会话任务不被抢占；激活只向同账号正常工作让出；task auth 不写入主账号；故障后原有准入恢复。不得仅以“没有重复发送”作为通过标准。

## 准备期限、进程所有权和迟到结果（SCH-03）

前置：独立临时 CODEX_HOME，`src/server/fixtures/account-app-server.cjs`，虚构 A/B 账号；运行 `automationPreparation`、`automationPreparationIntegration` 及 `automation` 测试。默认准备期限 90 秒；测试注入较短期限，不修改生产设置。

1. 同时启动四项固定 B 账号的准备，在原生登录已生效、尚未返回确认处暂停；另保留一个 A 的普通运行会话。四槽占满时第五项拒绝进入；超时仅关闭本次新建的准备进程，核对四个真实 PID 均退出后再释放账号租约和名额，A 的 PID/回合及 auth.json 字节不变。新 B 任务随后能正常产生 OUTPUT:b。
2. 在已有 A 会话上准备固定 B 自动化，将已有进程的登录确认挂起。期限到达后已有进程仍在、B 租约仍忙，同会话提交继续被拒绝；另一个 A 会话能运行。返回登录确认后，准备以超时结束，不发送任务正文；既有会话的下一次正常操作恢复 A，原 PID 保留。
3. 挂起额度读取，期限到达后返回旧结果：不新建 worker、不重新登录、不继续投递。另一个新请求可正常获得账号。
4. 挂起准备使用的共享 config/read，连续五次准备超时：底层仍仅一个未返回的读取，pending 与专用读取表均保留它；返回后才清掉。不同只读请求每个进程最多四个；不因超时伪造底层请求结束。
5. 挂起新会话命名，超时关闭其准备进程。迟到 createThread 结果不进入 turn/start；无首回合的已丢失会话按原重试规则重新建立。已有 heartbeat 目标不能因此清空或改成新会话。
6. 四项准备被用户取消时可立即显示“已取消”，但 activeCount/交接活动仍计入四项，实际效果未结束或清理未完成时不释放租约。只放行一项清理后，第五个任务才取得空位。迟到准备结果不能复活已取消任务；取消不能被后到的期限改写成超时。
7. 清理失败必须保留占用并暂停调度，不能把未确认退出当成退出。服务停止会取消尚未提交的准备；已落盘提交意图的任务沿用原未知结果核对，不能自动重发。

边界：共享已有进程上已发出的非取消操作必须等待原操作返回，或由其原所有者显式关闭后恢复。此时可能继续占用名额；不以强杀共享会话换取恢复，也不声称所有底层挂死都能自动结束。该选择服从核心功能优先。未改变账号选择、全局准入、四槽、固定/默认出口、额度保护与提交后核对协议。

清理：只移除 fixture 自己的暂停文件以放行确认，再取消剩余测试准备，等待自己创建的所有进程退出，最后删除自己的临时 home。禁止停止生产或其它会话来让测试通过。

性能证据：准备增加一次期限定时器和常数次取消检查；读请求超时不释放实际 pending，按方法与参数合并仍未结束的准备读取，最多四个/进程。只影响准备期间的三类只读 RPC，不缓存成功结果，不改变正常 RPC。组合 66 项通过，包括真实子进程四槽/共享会话/迟到额度/命名与读请求恢复。

## REV-01：保存期间新增运行不丢失

前提：独立临时 CODEX_HOME、确定性 fixture runtime；使用 `src/server/automationPersistence.test.ts` 暂停一次后台 dispatch 的历史归档，不暂停账号选择或把 dispatch 放回控制串行队列。

操作：分别在保存挂起时手动提交新运行、推进到下一定时时刻；确认新运行已进入内存后放行保存。检查返回身份、磁盘和历史页；完成旧运行，重启引擎，执行新运行并重复 tick/相同 requestId。

预期：新运行在保存及重启后保留，手动请求仍复用原 runId，每条实际提交一次；原账号、出口、并发上限和准备期间的资源占用保持。原有归档分页/幂等与慢 inspect 用例同时通过。性能检查：保存仍串行、归档调用次数不增加，只按已归档对象移除，额外集合操作为线性，不新增 RPC 或将慢 dispatch 加回控制队列。

清理/回退：测试自动释放自己的引擎、锁与临时目录。回退仅涉及保存集合处理，不删除用户运行记录；不能用清空 state/history 消除竞争现象。
# 封版补测：记录写满与重启

前提：`pnpm exec vitest run src/server/automation.test.ts src/server/automationPersistence.test.ts`，只使用临时 CODEX_HOME 与模拟执行接口，不能填满真实磁盘。

操作：分别在已确认队列等待执行、提交意图保存前、上游已受理后注入 ENOSPC；检查停止调度和实际发送次数，恢复写入后重建引擎，用同一 requestId 查询并再次 tick。

预期：未持久化放行记录时不调用发送；已持久化队列重启后仅运行一次；提交边界存在不确定性时标记中断、人工核对，不自行重发。重复 requestId 保持原 runId。注入只作用于存储方法，不改调度或账号实现。

清理：恢复存储方法并销毁自有引擎、临时目录。三个新故障测试与已有竞争保存测试一并保留；不在生产注入写入失败。
